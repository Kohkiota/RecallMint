## P3 が最難関である理由(spec 設計時に最重視)

1. **安全網が最薄**。P0 の contract test は API/wire を固めたが、**client component の描画・interaction は cover していない**(component test ~13% / E2E 不在 = audit §6.4 検証済)。P0〜P2 で効いた「P0 golden が挙動不変を守る」保証は、**P3 の対象(client interaction / subscription / commit タイミング)には効かない**。golden が緑でも P3 の回帰は捕まらない。
2. **地雷が最密**(audit §6.3・現 HEAD で file:line 再スキャン必須):
   - **exam 詳細の単一 subscription 不変条件**: 2 つの `useLiveQuery` を view 分岐の conditional unmount で排他。side peek は新規 subscription を作らず liveData から派生して不変条件を維持している(壊すと二重購読)。
   - **inline-text-field の commit-on-unmount + dirty-guard** / **use-card-options の ghost merge** / **TagCell placeholder override** / **selection prune HS-2** / **scroll collapse + virtualizer の memo 凍結**。
   - **side peek の blur 依存 close commit(V6)**: Dialog `onOpenChange` が `activeElement.blur()` を命令的に呼び、InlineOptionCell が commit-on-unmount を持たない事実に依存して close 時 commit を担保。
   - **tags optimistic rollback の Dexie auto-rollback 依存**。
3. **調査後に対象が拡大**(audit §4.4): side peek 着地で**カード編集 UI が near-verbatim 複製**(`exam-card-side-peek.tsx` ⇄ `inline-card-list.tsx`)、タグ CRUD の被 import が **4 経路化**。P2 完了時点で「これ以上機能を積む前にやる」緊急性が最大。

## P3 の必須方針(P0〜P2 と決定的に異なる点)

- **UI 抽出は「正しさの前に既存 interaction の characterization が先」**(audit §6.3・Codex 指摘)。P0 golden が cover しない領域ゆえ、**動かす前に現挙動を test で固定する characterization が P3 の前提作業**になる。
- これが P0〜P2 の「既存 test + golden が回帰の正」と根本的に違う点 — **P3 は回帰網を自分で作ってから動く phase**。
- ゆえに **characterization 戦略(どの interaction を、どの粒度で、動かす前に固定するか)が P3 spec の最重要設計判断**。E2E 新規導入は新規依存ゆえ OT 事前相談(CLAUDE.md)— 採るなら spec で費用対効果を提示。

## P3 スコープ(audit §7 / §3.1 / §4.4 / §6.1-4 — **現 HEAD で必ず再スキャン**。特に side peek 着地後の複製実態・被 import 4 経路・地雷各所の現行 file:line)

- **V1**: タグ CRUD の `lib/tags` 移設(`card-tags-section.tsx` の client CRUD 約 430 行を presentation から。被 import 4 経路 = `exam-card-table` / `exam-card-table-tag-cell` / `card-tag-add-popover` 系 / `exam-card-side-peek`)。
- **V3**: card write use-case 集約(「空文字→null」正規化ルールの UI 埋め込み: `inline-card-list` / `inline-text-field` / `use-card-options`)。
- **§4.4-1**: side peek 複製の解消(`exam-card-side-peek` ⇄ `inline-card-list` の near-verbatim。「1 枚のカードを編集する UI」が card view と peek の 2 レイアウトに分岐)。
- **runOptimistic\* の application service 昇格**(D-1 / N-5): 現物は `lib/sync/optimistic-mutation.ts`(+ 各 consumer)。**新 repository 層は作らない = 唯一の pragmatic 判断点(N-5)**。mirror 書込 + outbox enqueue + flush kick を application transaction として明示昇格するだけ。**新クラスを重ねない**(repository で隠すと coalesce / rollback / pull-back の同期挙動が不可視化する — audit §5.3)。
- **inline primitive 統合**: `InlineTextField` ⇄ `InlineOptionCell` の `sharedBoxChrome` verbatim 重複 + dirty-guard / auto-resize / commit の並行実装。
- **V6**: commit セマンティクス知識の container 漏れ(上記「地雷 2」の side peek blur 依存)。
- **付随**: `session-runner.tsx:255`(現 HEAD 確認済)の stale `submit-review-tx` コメント(P1 の replay-card dangling と同種・P3 owning-phase 掃討候補・baseline §B 申し送り済)。

## P3 スコープ外(明示・§8 確定判断 / やらない N-1〜N-5 より)

- **二段構え(client pre-check = UX / server = authoritative)は保持**(P1 §4.1 と同原則。client を authoritative にしない)。
- **wire 変更系(N-1〜N-3)は今回除外**(競合解決統一 / outbox 2 系統統合 / pull generic 化)。
- **Dexie store/index 変更(N-4)は別 sprint**。ただし DB 全消可(D-6)ゆえ Dexie 移行コードは不要・**形の変更が要るなら別 commit 隔離**(D-6)。
- **新 client repository 層(N-5)は作らない**(= runOptimistic\* 昇格の裏面)。

## 進め方(P0〜P2 と同じ標準フロー + P3 固有の前提)

1. **現 HEAD で P3 対象を fact-finding(再スキャン)** — 特に side peek 着地後の複製実態 / 被 import 4 経路 / 地雷各所の現行 file:line / runOptimistic\* consumer 一覧。
2. **spec 起草**(brainstorming step6)。**characterization 戦略を最重要設計判断として明記**(どの interaction を動かす前に固定するか / E2E 要否は費用対効果を提示し OT 相談)→ self-review → **User Review Gate で OT 確認**。
3. plan 起草(writing-plans)→ **Codex plan cross-check(plan 確定前)** → OT 承認で確定。
4. subagent-driven で実装。canonical review 全 code task / Codex は risk task。**characterization test を先に置いてから抽出**する task 順序に注意。
5. Sprint 境界(P3 完了)で停止・OT 判断待ち。Critical 未解決 / 仕様解釈揺れ / 外部サービス設定変更要 で停止。

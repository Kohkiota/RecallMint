## 起草者・実装者(OT 決定)

- **P4 の spec/plan 起草は Fable**(P2/P3 と同じく起草 = Fable / 実装 = CC Opus・subagent-driven)。
- Fable 帯の理由 = outbox flush 層の非対称(review 系のみ retry controller / pullBack hook 保持)を壊さない「限定共通化 vs 統合」の括り判断を含むため。ただし P4 は純 infra の DRY で、P2/P3 のようなドメインモデリング判断は少ない(重複解消が主)。

## P4 スコープ(audit §7 / §4.2 / §6.1-7 — **現 HEAD で必ず再スキャン**)

- **outbox flush 層の限定共通化**: **Web Lock guard / result 分類のみ**共通化。retry controller・backoff・pullBack hook・session grouping は review-flush 固有ゆえ**統合しない**(entity-mutations ⇄ review-events の非対称を保つ = N-2)。※ P3 Task2 で entity-mutation-flush 側 helper 共有は一部既存(classifyFlushResults / withWebLock を review-flush から re-use)— 現 HEAD で共有済み範囲を再スキャンして残余のみ対象化。
- **pull server 内 factory 化**: 6 pull module の同型パターン(table + cursor 列 + mapper だけ違う)を factory 化。**wire に出ない範囲のみ**(N-3)。**card_tags の例外 cursor 意味論**(created_at cursor + cards.updated_at bump・解除は tombstone でなくカード更新側で補完)を落とさない。
- **retry・transient 統合**: `ai/ocr.ts callWithRetry` / `clerk runTransactionWithRetry`(P2 で lib/clerk へ移動済・局所 helper のまま)/ `review-flush backoff` の 3 実装 + `lib/retry`・`lib/transient` の並列ディレクトリを統合。
- **route 認証 wrapper**: 6 route の `getCurrentUser → 401/空/500 + no-store` boilerplate の共通化。
- **lib ディレクトリ再編**: 基準統一(P1〜P3 で lib/ に module が増えた後の整理 — lib/tags/tag-crud.ts / lib/cards/card-write.ts / lib/reviews/ingest-review-events.ts / lib/clerk / lib/stripe 等)。

## P4 で守る §8 確定の「やらない」(N-1〜N-5・SSoT 記録済・既存確定を守る)

- **N-1 競合解決統一** = 恒久にやらない(反 DDD)。P4 で outbox を触るが競合ポリシー(replay / LWW / server-wins)は統一しない。
- **N-2 outbox 2 系統統合** = defer。P4 の outbox 共通化は「Web Lock guard / result 分類」限定であり、2 系統を 1 本に統合するものではない(**限定共通化 ≠ 統合**)。
- **N-3 pull 完全 generic 化** = server 内 factory 化(wire に出ない範囲)は P4 で in scope。PullResponse 型そのものの wire generic 化のみ**任意 consider** — P4 spec 起草時に費用対効果を判断し、採らない場合は理由を P4 spec に記録。
- **N-4 Dexie 再設計** = 別 sprint。**P4 では Dexie schema(store / index)を触らない**。DDD リファクタ完了後に OT が別途検討(必須ではない・DB 全消可でリスクなし)。
- **N-5 client repository 新設** = やらない(P3 で runOptimistic* 昇格により完了済)。

## P4 が拾う前 phase の申し送り(P4 spec で in/out を判断)

- **P2 の measure 計測配管 revert 要否**(review-events の TEMP marker・P2 spec §8.2)。timing log イベント名は D-2 凍結だが、計測 campaign 後に revert する意図の TEMP 実装。P4 で revert するか温存継続するかを OT 判断で。
- **P3 の contact-form components→app 解消**(P3 判断点 4 で P4 送り。server action の配置問題)。
- **N-3 の PullResponse wire generic 化の任意 consider**(上記)。

## P4 の制約(P0〜P3 共通 + P4 固有)

- 挙動不変(behavior-preserving)。**P0 golden 全面 green(snapshot 更新ゼロ)+ 既存 test green が回帰の正**。凍結契約(D-2)不変。
- Dexie 触らない(N-4 別 sprint)。
- 実装 = CC(Opus)・subagent-driven。Codex cross-check は spec/plan phase・review phase とも。
- P4 は infra DRY ゆえ「**限定共通化 vs 統合**」の線引き(N-2 を守る)と申し送り 3 件の in/out が spec の主判断。P3 のような characterization 先行は不要(P4 対象 = server/lib で co-located test が厚い領域・audit §6.4)。

## DDD リファクタの出口(P4 完了後の全体像)

P4 完了 → dddrefactor 全 phase(P0〜P4)完了 → develop へ merge → **まとめ stg smoke**(§B(vi) に P0〜P3 が積んだ全 surface + E2E 残余 3 点が申し送り済)→ 異常なければ prod 判断。この merge・smoke・prod 判断は **P4 完了時に OT が行う**。DDD リファクタ完了後の次作業(N-4 Dexie 再設計の検討 / 画像系 / Grid-3 / FSRS 等)は別途 OT 判断。

## 進め方(P0〜P3 と同じ標準フロー)

1. **現 HEAD で P4 対象を fact-finding(再スキャン)** — 特に outbox flush 層の非対称実態(P3 Task2 後の helper 共有済み範囲)・pull 6 module の同型パターン・retry/transient 3 実装 + 並列 dir・route 認証 boilerplate 6 route。
2. **spec 起草**(brainstorming step6)。「限定共通化 vs 統合」の線引き(N-2)+ 申し送り 3 件(measure revert / contact-form / PullResponse generic)の in/out を主判断として明記 → self-review → **User Review Gate で OT 確認**。
3. plan 起草(writing-plans)→ **Codex plan cross-check(plan 確定前)** → OT 承認で確定。
4. subagent-driven で実装。canonical review 全 code task / Codex は risk task。
5. Sprint 境界(P4 完了 = DDD リファクタ完了)で停止・OT 判断待ち(merge / smoke / prod)。

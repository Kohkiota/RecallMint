## 1. ⚠️ 自分の理解と実コードが違った点(先に読む)

説明前にここだけは必ず頭に入れる。間違って言うと一番痛い箇所。

1. **OCR モデルは「Gemini 3.5 Flash」ではない**。本番で使っているのは **`gemini-3.1-flash-lite`**(`lib/ai/cost.ts` の `modelId()` が唯一の決定箇所)。経緯: 2.5-flash で開始 → コスト削減で 3.1-flash-lite に移行 → 3.5-lite も実測比較したが「解答の選択肢が重複する」品質問題が出て**移行を撤回**した。聞かれたら「実測比較して選んだ」と言える(比較スクリプトが `scripts/ai/ocr-compare.ts` に残っている)。
2. **「アップロード = まず R2 直 PUT」は PDF だけ**。OCR 用の**写真は R2 に置かず**、圧縮してサーバー(Server Action)に直接送る(合計 4MB 上限。Vercel のリクエストサイズ制限に合わせた設計)。R2 直 PUT なのは ① PDF(50MB/枚、合計 200MB まで)と ② カードに手動添付する画像、の 2 つ。
3. **cron の画像(asset)孤児 GC はまだ稼働していない**。稼働中なのは「スキャン元ファイル(src/)の掃除」レーンのみ。画像孤児 GC レーンは**今まさに実装中の sprint**(9 タスク中 4 つ commit 済み)。「実装中です」と正直に言うのが正解。
4. **FSRS の計算はサーバー側のみ**。クライアントは計算せず、「期日が来たカード」を IndexedDB の索引から選ぶだけ。多端末間で計算結果がズレるのを防ぐための意図的な設計。

## 2. 全体図

```
[ブラウザ]
 ├ 画面表示 ←── IndexedDB(Dexie)      ← サーバーを待たない(ローカルファースト)
 ├ 書き込み ──→ IndexedDB + outbox ──(裏で自動送信)──→ Next.js API
 ├ PDF アップロード ──(署名付き URL で直接 PUT)──→ Cloudflare R2(非公開バケット)
 └ ログイン ←→ Clerk

[Next.js(Vercel 東京リージョン hnd1 / Node 24)]
 ├ DB: Supabase PostgreSQL 17.6(東京)via Drizzle ORM
 ├ OCR: Gemini API(gemini-3.1-flash-lite、公式 SDK @google/genai)
 ├ PDF→画像: pdfium(WASM) / 画像切り出し・WebP 変換: sharp
 ├ 課金: Stripe(Checkout + webhook)
 └ cron: 毎日 03:00 JST に掃除ジョブ 1 本
```

## 3. アプリの仕様(何ができるか)

- 学習資料(写真 / PDF)をアップロード → AI が読み取り、**4 択問題(MCQ)カードを自動生成**
- 資料内の**図やグラフは AI が位置を検出**し、サーバーが元画像から切り出してカードに添付
- **FSRS**(忘却曲線に基づく間隔反復アルゴリズム)が「今日解くべきカード」を決めて出題
- 試験(デッキ)・タグ・学習統計(日別の学習記録)
- プラン制限: OCR ページ数/月が free **30** / standard **300** / pro **無制限**(`lib/auth/plan-limits.ts`)
- スマホ利用が主想定(画像はピンチズーム対応ビューア、モバイル実機での検証を必須にしている)

## 5. 一番大事な流れ ①: アップロード → カード生成

1. ユーザーが写真 or PDF を選ぶ。
2. **PDF の場合**: サーバーが「10 分だけ有効なアップロード専用 URL(署名付き URL)」を発行し、**ブラウザが R2 へ直接 PUT**(ファイル本体はサーバーを経由しない)。置き場所は `src/{ユーザーID}/{セッションID}/{ファイルID}.pdf`。
   **写真の場合**: ブラウザで圧縮してからサーバーに直接送る(合計 4MB 上限)。
3. サーバー側処理(応答を先に返し、裏で継続。クライアントは完了をポーリング):
   - PDF は pdfium でページごとに画像化(長辺 2048px の WebP)
   - **Gemini を 1 回だけ呼ぶ**(1 アップロード = 1 API 呼び出し): 読み取り + 問題生成 + 図の位置検出(座標)を一括で JSON 返答させる。タイムアウト 220 秒、リトライは最大 2 回、**429(レート制限)を受けたら即停止・リトライ禁止**
4. **prepare(下書き)**: 結果をまず DB に下書き保存。この時点ではユーザーに何も見えない。
5. **図の切り出し**: sharp が Gemini の返した座標どおりに元画像から切り出し、WebP にして R2 の `users/{ユーザーID}/{画像ID}.webp` へ保存。
6. **publish(公開)**: 1 つの DB トランザクションでカード・タグ・画像参照を一括作成して完了。**切り出しが失敗しても文字だけのカードは必ず publish される**(画像は諦めるが本文は守る、という順序設計)。
7. **後片付け**: 元ファイル(src/)は成功でも失敗でも処理終了時に削除。消し損ねは毎日の cron が回収(→ §8)。

安全装置: AI の日次上限(`GEMINI_DAILY_LIMIT` + `ai_usage` テーブルで全体・ユーザー別に計上)、ページ上限 40、生成はユーザーの明示操作のみ(自動生成なし)。

## 6. 一番大事な流れ ②: ローカルファースト(サクサクの仕組み)

- **読み**: 画面表示は全部ブラウザ内 DB(IndexedDB を Dexie 経由で使用、13 テーブル)から。サーバー往復ゼロなので一覧も統計も即表示。
- **書き**: 「まずローカルに書いて即画面反映 → 同時に **outbox(送信待ち箱)** に積む → 裏でサーバーへまとめ送り」。この一連を `runOptimistic*` という共通関数に集約(ローカル書きと outbox 積みは同一トランザクションなので、片方だけ成功する事故がない)。
- **送信タイミング**: 画面を開いた時 / タブがアクティブになった時 / オンライン復帰時。**ポーリング(定期送信)はしない**。同じ項目の連続編集は 1 件にまとめる(コアレス)。二重送信は 3 重に防止(ID の一意制約 + 実行中フラグ + ブラウザの Web Lock)。
- **受信(pull)**: カーソル(前回どこまで受け取ったかの印)を持つ差分取得。全消し再取得はしない。
- **競合**: サーバー優先。ローカルの書きが失敗しても次の pull でサーバーの値に揃う(学習記録は追記型イベントなので上書きで消えたりはしない)。
- **オフライン**: 開いているページなら閲覧・解答・カード編集は動き、復帰後に自動同期。ただし **service worker は未実装**なので、オフライン状態でアプリを新規に開くことはできない(意図的にスコープ外)。

## 7. 画像の扱い(R2)

- バケットは**非公開**。公開 URL は存在しない。
- 表示時は「短時間だけ有効な取得 URL」をサーバーが発行 → ブラウザが取得して **Cache API に保存**(2 回目以降はネット不要。オフライン学習でも画像が出る)。
- カードへの手動画像添付も PDF と同じ直 PUT 方式: ブラウザで圧縮 → サーバーに予約 → R2 へ直接 PUT → サーバーに完了報告(サイズ照合あり)。
- R2 の中身は 2 種類だけ: `src/…`(OCR の元 PDF、一時置き場)と `users/…`(カード画像、永続)。

---

## 8. 掃除(cron / ゴミ回収)

- cron は **1 本だけ**: 毎日 03:00 JST に `/api/cron/sweep`(`CRON_SECRET` で認証、なりすまし不可)。中に複数の「レーン」を並べられる設計。
- **稼働中**: src 掃除レーン — 6 時間を過ぎた元ファイルを削除。進行中のアップロードがあるユーザーは除外。72 時間を超えて残っていたら警告(Discord 通知)。
- **実装中(今の sprint)**: 画像孤児 GC レーン — どのカードからも参照されなくなった画像を検出 → 30 日の猶予 → 「削除中」に昇格 → R2 とDB から削除、という状態機械。順序は「R2 を先に消してから行を消す」で固定(逆だと参照切れ画像が残る)。
- 前提となる考え方: 削除は「その場で完璧に」ではなく「本処理は軽く + 掃除役が後から確実に回収」の 2 段構え。

---

## 9. 認証(Clerk)とデータの分離

- `/app` 以下は全ページログイン必須(`proxy.ts`、Next.js 16 の middleware に相当)。
- Clerk が本人情報の正本。webhook(署名検証あり)で自前の `users` テーブルに複製。退会 webhook で Stripe 解約 + 論理削除 + ユーザーデータ purge まで自動。
- **DB 側の守り = RLS(行レベルセキュリティ)**: アプリは権限を絞った専用ロール(`recallmint_app`)で接続し、「自分の user_id の行しか見えない・書けない」を **DB 自体が強制**する。アプリのコードにバグがあっても他人のデータには届かない、が売りポイント。
- これを**本物の PostgreSQL 17 を使った自動テスト(`pnpm test:iso`)で毎スプリント検証**している(2 ユーザー作って相互に見えないことを ~30 ファイルのテストで確認)。

---

## 10. 課金(Stripe)

- **Stripe Checkout** を使用(カードフォームは自前で作らない)。standard / pro × 月 / 年の 4 通り。
- webhook: 署名検証 + `stripe_events` テーブルで**同じイベントは 1 回しか処理しない**(二重課金・二重反映防止)。
- webhook はエラーでも 200 を返す(Stripe が延々再送してくるのを防ぐ)。失敗は Discord に通知して人間が対応。
- 本番キーとテストキーの取り違えは**起動時に即エラーで落ちる**チェック入り(Stripe・Clerk 両方)。

## 12. 開発環境(バイブコーディング体制)

「AI に書かせて人間が判断する」を規律化している、というのがこのプロジェクトの特徴。

- **AI**: Claude Code(Anthropic のコーディングエージェント)。VS Code の devcontainer(Docker コンテナ)内で動かす。コンテナには Node 24 + テスト専用のローカル PostgreSQL 17 + ブラウザ(Playwright/Chrome)が入っている。
- **手順の強制**: superpowers というプラグインで「要件整理 → 仕様 → 実装計画 → 実装 → レビュー」の順番を AI に強制。計画は人間が承認してから実装に入る。
- **レビューは AI 二重体制**:
  1. Claude 自身の別インスタンスがコードレビュー(読み取り専用を保証した手順で)
  2. **OpenAI の Codex CLI による独立レビュー**(`scripts/ai/codex-review.sh`)。別社の AI に同じ差分を白紙の状態で見せて、指摘の付き合わせをする。Critical / Important がゼロになるまで直してから commit
- **commit の規律**: 全 feat/fix commit に `[reviewed]`(レビュー済)か `[no-review]`(意図的スキップ)のタグ必須。タグなしで終了しようとすると **hook(自動チェック)が止める**。`git commit --no-verify`(チェック飛ばし)は設定で禁止済み。
- **品質ゲート**(スプリント完了ごとに全部通す):
  - `pnpm lint` — 警告ゼロで exit 0
  - `pnpm test` — ユニットテスト(vitest)
  - `pnpm test:iso` — 本物の PostgreSQL でテナント分離(RLS)テスト
  - `pnpm run audit` — 依存パッケージの脆弱性ゲート(重大度 high 以上は無条件で fail)
  - `pnpm build` — ビルド + WASM 同梱の検証スクリプトが自動連結
- **動作確認**: AI が Playwright でブラウザを実際に操作して staging 環境を検証し、スクリーンショット・通信ログ・IndexedDB の中身を証拠として報告 → 人間が確認してから本番反映を判断。
- **正本の置き場**: AI への恒久ルールは `CLAUDE.md`、設計の不変条件は `docs/architecture.md`、作業記録は `docs/superpowers/sessions/`。

## 13. 聞かれそうな質問と一言回答

- **Q: なぜローカルファースト?** — 学習アプリは連打操作(次々解答)が主で、毎回サーバー往復だと体感が悪い。表示は全部端末内 DB、同期は裏で。
- **Q: 複数端末で同時に使ったら?** — サーバー優先で揃える(最後に届いた値が勝ち)。学習記録は追記型イベントなので消えない。FSRS 計算をサーバーに寄せているのも端末間のズレ防止。
- **Q: 画像は公開されている?** — 非公開バケット。表示のたびに短命の署名付き URL を発行。
- **Q: AI 費用の暴走対策は?** — 日次上限(全体 + ユーザー別カウント)、プラン別の月間ページ上限、429 受信で即停止・リトライ禁止、生成はユーザーの明示操作のみ。
- **Q: 他人のデータが見える事故への対策は?** — アプリ層の `WHERE user_id = ?` に加えて DB の RLS で二重防御。RLS は本物の PostgreSQL を使う自動テストで毎スプリント検証。
- **Q: マイグレーションは?** — drizzle-kit で SQL を生成し、owner 権限の接続で適用。RLS ポリシーは別管理の SQL(適用/巻き戻しのペア)を運用者が手動適用。
- **Q: なぜ webhook でエラーでも 200?** — Stripe/Clerk は失敗応答だと再送し続けるため。処理失敗は Discord 通知で人間が拾う設計。

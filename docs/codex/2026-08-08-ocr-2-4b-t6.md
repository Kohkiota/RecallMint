The newly enabled PDF flow is not supported by the unchanged submit action, so PDF-only uploads fail and mixed uploads omit PDFs. Indeterminate submit failures also leave the client in a state that cannot successfully retry.

Full review comments:

- [P1] Add server-side handling for the PDF manifest — /workspaces/RecallMint/app/(app)/app/upload/_components/upload-form.tsx:733-734
  When any PDF is submitted, these fields are sent to `submitUpload`, but that action still reads only `files` and ignores both `orderManifest` and `uploadSessionId`. A PDF-only submission is therefore rejected as having no files, while a mixed submission accepts and processes only the images, silently dropping every PDF. The submit action and pipeline must consume the new manifest/R2 objects before enabling this client flow.

- [P2] Re-upload PDFs after an indeterminate submit — /workspaces/RecallMint/app/(app)/app/upload/_components/upload-form.tsx:740-745
  If `submitUpload` throws, this clears the session while leaving all PDF entries in `ready`. The form remains usable after the error, so another submit sends the same PDF manifest with an empty `uploadSessionId` and is guaranteed to fail validation; adding another PDF also creates a new session containing only that new object's namespace while the old ready PDFs remain referenced. Move existing PDFs back through reserve/PUT/finalize (as the terminal-failure path does), or otherwise prevent retry with stale ready entries.

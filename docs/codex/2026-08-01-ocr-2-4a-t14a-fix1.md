The stale-operation protection is inconsistent with the status-display fallback, and the newly introduced crop deadline does not actually bound an in-flight crop. Both can break the intended behavior under supported long-running or slow-I/O scenarios.

Full review comments:

- [P2] Keep live operations visible as processing — /workspaces/RecallMint/lib/exams/source-doc-status.ts:126-146
  When a source is older than 15 minutes but protected by this new live-operation exclusion, the database row remains `processing`, yet `getExamStatusMap()` still passes it to `deriveExamStatuses()`, which unconditionally reports any such old row as `failed`. Thus active retryable/prepared operations can display a failure badge for up to seven days even though this change deliberately prevents them from being failed; the status query or derivation also needs awareness of the protecting operation.

- [P2] Enforce the deadline during each crop — /workspaces/RecallMint/app/(app)/app/upload/_lib/publish-prepared-orchestrate.ts:300-310
  The budget is checked only before starting `cropFigureAndStore()`, so a crop begun with just over five seconds remaining may run arbitrarily past `deadlineAt` during R2 GET/PUT or image processing. In the slow-storage scenario this defeats the new absolute deadline and can still let the server action hit its platform timeout before publishing the text cards; each crop's asynchronous work needs to be bounded by the remaining budget, not merely gated before invocation.

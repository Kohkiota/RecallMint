The environment-variable and role split is incomplete across executable migration and operator paths, causing documented maintenance commands to fail or use the wrong role. The new dual-client cleanup also does not guarantee both clients are closed when the first close rejects.

Full review comments:

- [P1] Keep migration tooling aligned with the renamed admin URL — /workspaces/RecallMint/.env.example:18-20
  When an operator follows this new environment contract and supplies `DATABASE_URL_ADMIN`, `pnpm db:migrate`, `db:generate`, and `db:studio` still fail because `drizzle.config.ts` continues to require `DATABASE_URL`. The owner URL rename therefore needs to be applied to the Drizzle configuration in the same change.

- [P1] Migrate operator scripts before switching getDb to the app role — /workspaces/RecallMint/lib/db/index.ts:21-24
  With `getDb()` now requiring `DATABASE_URL_APP`, existing operator scripts such as `seed-perf-exam.ts`, `gc-image-assets.ts`, and both backfills still call `getDb()` and some validate the old `DATABASE_URL`. Existing invocations using the owner URL will now fail with `DATABASE_URL_APP is not set`; if both variables are present, these privileged maintenance jobs instead run under the least-privilege application role. Move these scripts to `getAdminDb()` and consistently validate `DATABASE_URL_ADMIN` before changing this shared factory.

- [P2] Continue closing the admin client after an app close failure — /workspaces/RecallMint/lib/db/index.ts:60-65
  If both clients were opened and `_client.end()` rejects, the `finally` clears the app singleton but the rejection immediately exits `closeDb()`, so the `_adminClient` branch is never reached and its connection leaks. This contradicts the stated independent-cleanup behavior; capture the first error while attempting both closes, or nest the admin cleanup in an outer `finally`.

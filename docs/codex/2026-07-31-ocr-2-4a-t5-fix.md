The verification and conditional-write flow is otherwise coherent, but a successful R2 promotion followed by a lost database CAS leaks an object that no database row references and therefore cannot be collected normally.

Review comment:

- [P2] Remove promoted objects when the CAS loses — /workspaces/RecallMint/app/(app)/app/upload/_actions/source-asset-actions.ts:180-182
  When this PUT succeeds but the subsequent reserved→ready update matches zero rows, the newly written final object can become permanently orphaned. This occurs if GC changes the row to `deleting` during verification, or if a concurrent finalize using a different image format wins the CAS; the row retains either the temp key or the winner's differently suffixed key, so the existing source-assets GC cannot discover this object. Delete the just-written object when the CAS loses and the current row does not reference `finalObjectKey`.

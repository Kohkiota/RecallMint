## 独立論点(調査結果 + 要件から導出)

- W2 の `y = n + k` が何を数えるのかを厳密に分ける必要がある。`n` は「今日中に due になるカード数」であり、「今日必要な回答回数」ではない。Learning / Relearning のカードは回答後も同日中の次ステップが設定されうるため、1 回回答しても `n` から減らない場合がある。
- したがって、「残り◯問」「約◯分」という表示語がカード数を意味するのか、回答回数・学習ステップ数を意味するのかを確定する必要がある。カード数なら所要時間との積算が過小評価になりうる。
- `k` は単なる「1日の上限値」だけでは定義できない。当日の消費済み新規数、消費を数えるイベント、再回答の除外、試験切替時の扱い、日界、複数端末での整合が必要。
- `k` 件の新規カードについて、件数だけでなく対象カード集合と順序を決める必要がある。そうしなければ W2 の表示集合と CTA の出題集合を一致させられない。
- W2 が未来時刻に due となるカードを朝から含める一方、現行 CTA は `due <= now` しか出題できない。単なる新規上限対応だけでなく、「当日 later-due の前倒し出題を許すか」という出題意味論が必要。
- 「苦手」の `lapses` と「定着」の用語関係を分離する必要がある。`lapses` は `state=Review` から Again のとき増えるが、本文の「定着」は `state=2 && stability>=21`。Review 状態と定着集合 C は同義ではない。
- 選択中試験の保存には、owner 分離だけでなく、サインアウト時の扱い、別ユーザーへの漏洩防止、複数タブ競合、URL変更時に保存値を更新する条件が必要。
- 週比較では「先週同期間の行が一部存在する」だけでは、全期間を観測できていた保証にならない。利用開始日、同期完全性、欠落日の意味を考慮しないと、部分期間と完全期間を比較する可能性がある。
- 直近30日の範囲は `[29日前の00:00, 明日00:00)` の暦日30日なのか、`now-30日` のローリング窓なのかを一意化する必要がある。
- L2 はサーバ由来 mirror なので、オフライン・同期失敗・最終同期時刻による陳腐化が起こりうる。ローカルに存在することと、新鮮・完全であることは別。
- L3 の陳腐値を表示するには、キャッシュの有無、取得時刻、試験切替時の旧値破棄、再試行方法までデータ契約が必要。
- ローカル `answer_events` の「有効100件まで走査」は、直近に無効値が大量にある場合に全件走査へ退化する。走査件数の上限や索引条件も必要。
- 異常データを除外して報告する規則には、報告先、集約単位、PII、rate limit が必要。定義だけがあっても「観測可能」の実装解釈が割れる。
- 暫定閾値を変更した際に比較へ注意書きを付けるなら、閾値の版・適用日時をどこで保持するかが必要。
- 削除やタグ付け替えで過去値が変わる仕様は、数値キャッシュを導入する場合の無効化条件にも影響する。

## plan ドラフトへの抜け・未考慮指摘

- 最大の内部不整合は §4-H の説明文である。定義 C の「定着」は `stability >= 21` だが、`lapses` は任意の Review 状態から増えうる。「定着後に2回以上忘れたカード」は、確定した述語 `lapses >= 2 && !定着(C)` を正確には説明していない。少なくとも「Review 到達後」と「定着(C)」を同一視してはならない。
- W2 の「回答すれば due が未来へ飛んで n が減る」という説明は常には成立しない。Learning / Relearning の次ステップが同日中なら、同じカードは引き続き `n` に残る。
- そのため、W2 の「残り◯問」と N の「1問あたり時間 × y」は単位が揃っていない可能性がある。`n` はカード数、実際のセッションは複数回答ステップを含みうる。
- §6-⑥へ委譲した `k` の責務には「対象となる新規カードの選出順・集合固定」が明記されていない。消費量だけ定義しても CTA との集合一致は保証できない。
- W5 の「10分」の母集合を `n+k` としているが、`k` は数値であってカード集合が未定義。したがって現状では母集合自体が一意でない。
- W5 の共通選出順 `due ASC` は、新規カードでは `due=作成時刻` のため実質的に古い生成順になる。この選択が新規 k の意図した順序であるか未確認。
- W2 の CTA 不一致は記載されているが、later-due の扱いが §6-⑥の責務に明示されていない。新規上限だけ直しても `n` と CTA は一致しない。
- §3.8 の「L1/L2 は client ローカルで失敗・陳腐が構造的に起きない」は不正確。Dexie 読み取りは失敗しうるほか、L2 はサーバ同期 mirror なので明確に陳腐化しうる。§3.6、§6-⑪とも緊張している。
- §6-⑪で L2 マージ規則が未定義なのに、O/Q/W7 を一意に計算可能な凍結済み定義として扱っている。少なくとも表示値の供給源と freshness/rollback 規則が決まるまでは、実装者の解釈余地が残る。
- Q の先週同期間判定は「行が1件でもあれば比較可能」と読めるが、途中利用開始や同期欠落を検出できない。全期間観測済みの条件が不足している。
- 「先週同期間比」という名称に対し、式は比率ではなく回答数の差分である。UI が「比」を百分率と解釈する余地があるため、「先週同期間との差」などとの区別が必要。
- P の「直近30日」は境界区間が式で書かれていない。§3.1参照だけでは30暦日と過去720時間のどちらかが確定しない。
- N は有効100件到達で停止するが、無効レコードだけが大量に並ぶ場合の走査上限がない。「無限成長への対処済み」という記述は過大。
- W4 の「陳腐なら取得時刻を添える」は、値の保存場所・取得時刻の保持元・試験切替時のキャッシュキーが定義されていない。
- W6 の「全7日が0なら非表示」は、§3.7の「意味のある0」と「データなしを区別する」原則との関係が不明。「予定なし」という有益なゼロを消す判断になっている。
- §3.12 は閾値変更日を記録するとするが、記録場所・版識別・過去比較への注記をどの指標に適用するかが未定義。
- `sync_meta` の owner-scoped key について、owner を複合キーにするのか値へ埋め込むのか、旧値の掃除、サインアウト時の処理が引き継ぎ事項にない。
- pin に以下が不足している。
  - Review と定着(C)が一致しない状態での苦手判定・説明
  - Learning/Relearning の同日次ステップ後も W2 の `n` に残るケース
  - 当日 later-due が W2 に表示されるが CTA ではまだ選ばれないケース
  - `k` の当日消費、日界、試験切替、複数端末
  - P の30日境界
  - 週途中で利用開始した場合の delta
  - L2 の同期失敗・巻き戻り・陳腐表示
  - N で無効イベントが100件以上連続するケース
  - owner 切替時に選択中試験が漏れないこと

## リスク / 対立しうる設計判断

- 「日単位で安定した処方」と「押した直後に全件実行可能な CTA」は対立する。未来 due を朝から数えるなら、前倒し出題機構か、CTAとの不一致を明示的に受容する必要がある。
- 「残りカード数の単純さ」と「実際の回答回数・所要時間の精度」は対立する。短期学習ステップを予測に入れるほど定義と実装は複雑になる。
- `k` を毎回再計算すると単純だが、複数端末や試験切替を含む厳密な日次上限にはサーバ側または同期可能な消費記録が必要になる。
- URL を正とする設計と、保存値による継続性・複数タブでの一貫性は対立する。URLごとに異なる試験を開けるなら、タブ間で保存値が最後の閲覧試験へ揺れる。
- owner-scoped `sync_meta` をローカルだけに置く方針は簡潔だが、端末間で既定試験が異なることを受容する必要がある。
- 週 delta を厳密に比較するには利用開始日や同期完全性が要るが、追加データなしで進めるなら非表示条件を広くして保守的にする必要がある。
- W4 の現在タグによる過去再分類は実装が簡単だが、数値の再現性と説明可能性を弱める。キャッシュ導入時には特に整合が難しい。
- L3 の陳腐値表示は可用性を上げる一方、選択試験をまたいだ誤表示の危険がある。キャッシュキーと freshness 契約がない段階では、失敗時非表示の方が安全。
- 暫定閾値を shared 定数として変更可能にする設計と、過去比較の連続性は対立する。表示時点計算だけでは、過去に使われた閾値を復元できない。
- 「v1 の L3 依存は W4 のみ」は計算層としては成立するが、選択中試験や日次新規上限の端末間整合まで求めると、別種のサーバ依存が増える可能性がある。

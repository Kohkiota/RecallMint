The rasterization path works for successful renders, but its advertised parallel-call handling allows queued work to access a destroyed PDFium document after an earlier render fails.

Review comment:

- [P1] Prevent destroying the document while renders remain queued — /workspaces/RecallMint/lib/media/pdf-rasterize.ts:89-92
  When parallel calls are awaited with `Promise.all` and one render rejects (for example, an out-of-range page index), the caller's `finally` can invoke `destroy()` while later calls remain in this internal queue. Those calls then execute `document.getPage()` against an already-freed PDFium document, potentially causing incorrect output or a WASM/native failure. `destroy()` should either wait for the queue to settle or mark the handle closed and make queued work reject without touching `document`.

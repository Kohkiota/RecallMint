The finalize flow leaks a temporary R2 object for every successful upload, and its image verification limit permits user-controlled decoding large enough to exhaust server memory. These are substantive storage and availability defects despite the added tests passing.

Full review comments:

- [P1] Bound image decoding below memory-exhaustion sizes — /workspaces/RecallMint/app/(app)/app/upload/_lib/source-image-verify.ts:117-119
  An authenticated client can upload a highly compressible image near the current 268,402,689-pixel limit, causing `sharp(...).toBuffer()` to decode and re-encode roughly a gigabyte of pixel data before the dimension check runs. A ≤5 MiB solid-color PNG/WebP can therefore exhaust a server process despite satisfying the upload-size cap; use a substantially smaller pixel limit aligned with the application's expected images, and reject oversized dimensions before performing a full output conversion where possible.

- [P2] Delete the temporary object after successful promotion — /workspaces/RecallMint/app/(app)/app/upload/_actions/source-asset-actions.ts:260-261
  On every successful finalize, the database row is changed from the temporary key to `finalObjectKey`, but the original `asset.objectKey` object is never deleted. Because the existing GC is row-driven, it can no longer discover that temporary object once the row points at the final key, so each finalized source permanently leaks its uploaded temp copy; perform a best-effort deletion of the original temp key after a successful/idempotent ready result.

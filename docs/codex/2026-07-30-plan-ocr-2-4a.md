## 独立論点(調査結果 + 要件から導出)

### 1. 成功・失敗の原子性と再試行単位

- 「同期一発」「途中状態を見せない」と、実際の外部副作用は同義ではない。少なくとも R2 source PUT、Gemini、cards INSERT、crop PUT、assets INSERT、refs INSERT が別々に発生する。
- 特に「cards INSERT 後に crop」は、crop 途中失敗時にカードだけ残る。operation を `failed` にして同一 key で再試行すると、カードの二重作成を防ぐ仕組みが仕様にない。
- crop asset ID と refs の決定性だけでは、card 自体・source document・AI 使用量・通知の冪等性は保証されない。
- 次を明示する必要がある。
  - crop 一部失敗は operation 全体の失敗か、警告付き成功か
  - Gemini 成功後に DB/R2 が失敗した場合、再試行で Gemini を再度呼ぶか
  - 再試行時に既存カードを再利用・置換・削除するか
  - `source_documents`、exam、usage counter、ops 通知の重複防止
- DB transaction に R2/Gemini を含めるべきではないため、完全 atomic より saga として各段階の再開可能性を定義すべきである。
- 「UI に途中状態を見せない」だけなら、カードを operation completion まで検索・同期・結果画面から不可視にする公開条件も必要。

### 2. source upload と source_document 作成順の循環

- source asset の reserve/finalize は `source_document_id` 必須だが、現行 `processUpload` は server 内で exam/source document を作る。
- 要件の「client 事前に source を保存」には、その前に source document を作る prepare フェーズ、または nullable な operation/session ID が必要。
- 新規 exam の場合はさらに exam 作成時点も問題になる。prepare 後に client が離脱すると、空 exam、processing source document、reserved/ready source asset が残る。
- prepare、PUT、finalize、process の各段階について abandonment GC と再開契約が必要。

### 3. `source_assets` schema が保存フローを満たさない

- 列定義に `byte_size` がない一方、finalize は R2 HEAD の byteSize 一致を要求している。予約時の期待値を永続化できない。
- R2 HEAD だけでは次を保証できない。
  - 実バイトの content hash
  - Content-Type／実ファイル形式
  - client 申告の width/height
  - EXIF orientation
- `content_hash`、decoded 寸法、MIME、orientation を安全保障や座標契約に使うなら、server が R2 GET 後に実バイトから再計算・再検証する必要がある。
- 巨大ピクセル画像や malformed image による decode bomb、CPU・メモリ消費への制限も必要。byte cap だけでは不十分。
- `source_id` は source document 内で一意であるべきだが、対応する unique 制約がない。
- `source_assets.user_id` と参照先 `source_documents.user_id` の一致を FK が保証しない。アプリ/RLSだけに依存するか、複合 FK 等で不変条件を持たせるか判断が必要。
- 入力順を保存する列がないため、後述の採用順を再現できない。

### 4. fingerprint の信頼境界

- fingerprint が client 申告の content hash に依存すると、誤実装・改竄により異なる R2 バイトを同一入力として扱える。
- fingerprint は finalized source の server 検証済み hash、安定した source 順序、正規化済み params から作るべき。
- 「sorted hash」だけでは、同一内容のファイルを複数含む場合や、入力順が意味を持つ場合の表現が曖昧。件数と順序を含む canonical encoding が必要。
- exam target には mode、新規/既存 exam の識別、OCR 設定など、結果を変える全パラメータを漏れなく含める必要がある。
- model 名だけでなく prompt/schema/crop codec の版管理境界も明示した方がよい。

### 5. ledger の状態機械と競合制御

- schema の status は `claimed|completed|failed` だが、フローは `completed_with_warnings` を書くとしており不整合。
- failed／TTL claim の再取得は、SELECT 後 UPDATE では競合する。fingerprint、status、期限を WHERE に含む原子的 CAS が必要。
- TTL は処理の最大 deadline より十分長くするか lease/heartbeat が必要。生きた処理を orphan と誤認すると Gemini が並行二重実行される。
- `completed` の「既存結果」が何を指すか不明。source document だけで十分か、exam/cards/警告集計を再構成するか、結果 snapshot を持つか決める必要がある。
- crash が Gemini 応答後・保存前なら、API 側に冪等キーがない限り再呼び出しを完全には防げない。「二重 Gemini なし」は保証範囲を限定して表現すべき。
- failure code、attempt count、lease 時刻、updated_at、警告集計など、運用調査に必要な情報が不足している。

### 6. EXIF／回転除外の契約

- 圧縮後バイトに orientation tag が残らず、ピクセルへ焼き込み済みなら metadata orientation は `undefined` になり得る。「orientation=1」と「欠測」の扱いが未定義。
- 逆に圧縮後に常に orientation が消えるなら、EXIF≠1 分岐は前提破綻検出器にならない。
- source を Gemini から完全に除外すると text 抽出もできない。画像は送信したまま「この source は figure を返すな」と prompt で制御するなら、その遵守不能時の server-side drop が必要。
- portrait/landscape と EXIF orientation は別概念。EXIF=1 の横向き画像や、ピクセルが物理的に回転済みだが EXIFなしのスキャンは除外できない。
- 「回転入力を除外」の実際の保証範囲を EXIF metadata 検出可能ケースに限定して明記すべき。

### 7. crop 幾何と codec

- px 丸め規則が単に「round」では境界包含を保証しない。通常は left/top=floor、right/bottom=ceil の方が切れを防ぎやすい。6% padding の思想とも整合確認が必要。
- sharp の EXIF自動回転を crop 前に適用するか否かを固定しないと、「同じバイト」でも座標空間が変わる。`rotate()` の暗黙使用禁止など、decoder pipeline を明文化すべき。
- ICC profile、animated WebP、multi-page WebP、alpha、CMYK JPEGなどの受理／正規化方針がない。
- WebPの quality、lossless、有効最大寸法、metadata除去を固定しないと、同じ asset IDに異なるバイトが対応し得る。
- asset IDに encoder/versionを含めるか、pipeline_versionがそれを包含する契約が必要。
- UUIDv5 namespace の固定値・保管場所・変更禁止条件も必要。

### 8. 検出結果とカードの対応

- AI出力の `source_id` は信頼できないため、重複、未知、形式不正、別 source の書き写し間違いを扱う必要がある。
- 8桁 UUID prefix は衝突可能であり、client が任意値を送れる。server生成または upload内 uniqueness 検証が必要。
- `option_{id}` の id がAI生成カード内で安定・一意であること、カード保存後も維持されることを確認する必要がある。
- ambiguous target を無条件で question に付けると誤表示を silent success にする。「安全な上位集合」という判断は、誤帰属リスクとの比較が必要。
- 同じ bbox の重複検出、figure同士の重なり、同一図を複数 target に付ける場合の dedupe 方針がない。
- `ordinal` の算出規則を、無効要素の除外前後・target変換前後まで固定する必要がある。

### 9. deterministic key と参照更新

- key に ordinal を含めると、AI出力順の揺れで同じ図が別 asset になる。
- 一方、refs PK は `(cardId, fieldKey, ordinal)` なので、同じ位置に異なる asset が来た場合 `DO NOTHING` では古い誤参照が残る可能性がある。
- 再試行時の期待動作を「既存値一致なら成功、不一致なら conflict」「置換」など明示すべき。
- R2 PUT 成功後DB失敗、DB成功後R2失敗、競合処理が同じ keyへPUTする場合の整合回復が必要。
- crop asset の `assets.status` を reserved/ready のどちらで作り、いつ表示可能にするかが未定義。
- audit metadata の保存先・schema・retention・RLS・削除カスケードが未決定。

### 10. 採用順と page 概念

- `source入力順`を保存する ordinal がない。
- imageで page を省略可能にすると、sort時の page既定値が必要。
- y/x が null・不正な figure は採用順決定前に除外する必要がある。
- AI配列順、card順、同一座標tieの最終 tie-breaker がないため、上限境界の採否が非決定的になり得る。
- crop上限 N、入力上限、出力token上限は「実装時確定」のままだとテスト期待値・UX・運用容量を凍結できない。

### 11. 一回の generateContent の容量・部分失敗

- 全画像を一度に送る場合の画像数、request bytes、model context、最大output tokens、カード数上限が未定義。
- JSON全体が途中でtruncate／syntax errorになれば、要素単位 safeParseに到達できない。要素隔離は「親JSONが解析可能」という条件付き。
- 一画像のR2 GET失敗時に upload全体を失敗させるか、そのsourceだけ除外するか未定義。
- model safety block、schema不適合、timeout、rate limitに対する状態遷移とユーザー表示が必要。
- 同期server actionがブラウザ切断・platform timeoutを受けても処理継続するか、再送時にどう結果取得するかを定義すべき。

### 12. quota・usage・既存同時実行 guard

- 「account quotaは②-5」としつつ、現行実装には quota、日次Gemini上限、1 user 1 OCR guard、AI usage計上が存在する。ledgerとの優先順位・統合が必要。
- claimを既存guardの前後どちらで取るかにより、拒否された操作や孤立claimが発生する。
- completed結果の再利用時に usageを再加算しない保証が必要。
- 一度の統合callに変わることで pages/cost算出、`pagesProcessed`、modelChain の意味も再定義が必要。

### 13. GDPR・GC

- DB cascadeを先に実行すると、R2 object keyを失い物理削除できなくなる。退会前列挙、削除outbox/tombstone、またはDB行を deleting で残す設計が必要。
- webhook処理中のR2障害に対する durable retry が必要。mockでdelete呼出を確認するだけでは、実運用の消去保証にならない。
- source document削除、exam削除、退会の三経路すべてを扱う必要がある。
- ready source assetが失敗operationに紐づいた場合のretentionが曖昧。
- 「参照ゼロ」の定義が source_assets にはない。source_document FKだけで判定するのか、operation状態も見るのか決める必要がある。
- crop asset GCでは cards.images とcard_asset_refsの二重持ち不整合を前提に、安全側の判定が必要。

### 14. セキュリティ・プライバシー・運用

- source画像を新たに永続化するため、既存inline OCRよりデータ保持面が大きく変わる。retention期間、利用目的、削除UI、プライバシー表示、ログ非出力が必要。
- presigned PUT発行には、ファイル数・予約総量・並行予約数のserver側制限が必要。未finalize orphanを大量生成するstorage abuseを考慮すべき。
- MIME allowlistだけでなく magic-byte検証が必要。
- R2 GET/PUTに明示timeout、response size上限、例外分類、retry方針が必要。
- original filename、AI応答、label、error messageをログや通知へ流す際のPII方針が必要。
- observabilityとして operation ID、source ID、段階、所要時間、除外理由、crop件数、R2/Gemini失敗率が必要。

## plan ドラフトへの抜け・未考慮指摘

### 重大な構造上の抜け

1. **T2を呼ぶ前提が成立していない**

   `reserveSourceAsset` が `source_document_id` を要求する一方、その作成task／prepare actionがない。新規examを含むライフサイクルも未設計。

2. **T1に `byte_size` がない**

   T2の「HEAD + byteSize一致」を実装できない。spec由来の直接的なschema欠落をplanも継承している。

3. **T11の再試行でcard重複が起こり得る**

   cards INSERT後のcrop失敗、DB失敗、timeoutについて、card IDの決定性・既存カード再利用・compensationがない。T9のasset冪等性では解決しない。

4. **「途中状態を見せない」の実現手段がない**

   T11は単に順番を記載しているだけで、cards INSERT後completion前のカードを他のread/sync経路から隠す仕組みがない。

5. **statusが不整合**

   T4は3値、T12は`completed_with_warnings`を書こうとしている。DB statusへ追加するのか、completed + warning countとするのか未決定。

6. **source入力順を保存できない**

   T12の採用順に必要なsource ordinalがT1にない。ランダムなsource_idでは代用できない。

7. **server GETがtask化されていない**

   現行R2 moduleにはGET helperがなく、T9/T11が要求する取得についてtimeout、最大byte、エラー契約、mockが定義されていない。

### Task別の不足

- **T0**
  - runtime deploymentでsharp native binaryが対象環境に適合する確認が必要。
  - loadだけでなく実decode/crop smokeが望ましい。
  - lockfile変更をlogic不変と分類する妥当性は、native runtime差を考えると弱い。

- **T1**
  - `byte_size`、`input_ordinal`、`ready_at`、必要なら`orientation`が不足。
  - `(source_document_id, source_id)` uniqueがない。
  - userとsource_documentのtenant一致保証がない。
  - page予約列を1 source rowに置く意味がPDFページ派生assetとの将来構造に合うか再確認が必要。

- **T2**
  - client申告hash/dimsのserver再検証がない。
  - HEADはContent-Type、hash、実画像性を検証しない。
  - presign成功前のDB insert失敗補償、PUT成功・finalize未達の扱いが弱い。
  - source_documentを誰がいつ作るか抜けている。
  - server側ファイル数・予約総量制限がない。

- **T3**
  - DB cascade後にobject keyを取得できない問題を扱っていない。
  - source deletionと退会を一括しているが、durable deletion retry/outboxがない。
  - `referenced>0`という概念がsource_assetsに定義されていない。
  - crop失敗で参照ゼロになったcrop assetとsource reserved GCは、状態機械が異なり同じ変更で扱うには危険。

- **T4/T5**
  - lease取得時刻／updated_at／attempt数がなく、created_atだけでTTLを測ると再claim後も即staleになり得る。
  - failed再claimとTTL回収の原子的UPDATE条件が具体化されていない。
  - completed結果の返却payloadが未設計。
  - server検証済みhashを使う条件がない。
  - 既存upload guard、quota、daily limitとの順序がない。

- **T6**
  - 「builderをwrap」しても元schemaを触らずper-card propertyを注入できるか、実際のschema構造上の方式が未記載。
  - sourceごとのfigure除外指示をどうGeminiへ伝えるかがない。
  - JSON全体truncate時の扱いがない。
  - `page`の型・範囲・imageで1を許すかが曖昧。

- **T7**
  - 重複source_id、重複figure、bbox重複、option id重複を扱わない。
  - ambiguousをquestionへ寄せた件数を警告にするか不明。
  - invalid boxの理由が「要素破損」なのかcrop失敗なのか、提示語彙に対応していない。
  - AI要素順をordinalへどう反映するか未定義。

- **T8**
  - `round`の具体規則が切れ防止と整合しない可能性がある。
  - NaN、Infinity、小数外、逆転bbox、範囲外bboxの入力責務が曖昧。
  - decoded寸法の正整数・最大値検証が必要。

- **T9**
  - sharpがEXIFをどう扱うかを固定していない。
  - WebP encoding設定とpipeline versionの対応がない。
  - PUT/DB/refs/cards.imagesを跨ぐsagaと回復がない。
  - `assets.status`、byteSize/hash/width/heightをどう埋めるか未記載。
  - cards.imagesとrefsの同一transaction更新が明記されていない。
  - ref PK conflict時に既存assetとの一致確認がない。
  - audit metadataの保存先が未決定なのに実装taskへ進んでいる。

- **T10**
  - `orientation=undefined`の扱いを完了条件に挙げるだけで、期待値がない。
  - Geminiへの画像はtext用に残しつつfigureだけ拒否する具体策がない。
  - AIが除外sourceのfigureを返した場合のserver-side rejectionがない。
  - EXIFなし回転スキャンは検出できないことが明示されていない。

- **T11**
  - failure matrixと各段階のstatus遷移がない。
  - crop失敗をwarningにするのかoperation failedにするのか不明。
  - AI usage、quota、通知、source_document statusの冪等性がない。
  - browser切断、server timeout、再poll/再取得導線がない。
  - 「deadline既存規律」だけではR2 GET/PUT・sharp・DB各段階のbudget配分がない。
  - source readiness、所有権、同一document所属の一括検証がない。

- **T12**
  - Nや入口制限値が未確定のまま実装taskになっている。
  - tie-breakerがなく完全に決定的でない。
  - card作成不能理由とfigure要素破損の提示が不足。
  - completed結果再利用時にも同じwarning payloadを返す保存先がない。
  - UIが「向き未対応sourceでもtextは作成済み」を誤解なく示す文言検討がない。

### テスト計画の不足

- crash pointごとの再実行テストが必要。
  - Gemini後、card INSERT前
  - card INSERT後、最初のcrop前
  - R2 crop PUT後、assets INSERT前
  - assets後、refs/cards.images前
  - completed更新直前
- 2 worker同時claim、stale reclaim、live leaseとの競合。
- client申告hash/dims/MIMEと実バイト不一致。
- decode bomb、corrupt JPEG、animated WebP、EXIF欠測。
- R2 GET/PUT timeout・5xx・不完全応答。
- GDPR削除途中失敗からの再開。
- JSON全体truncate／schema外応答。
- 上限境界で完全に同順位となるfigure。
- cards.imagesとrefsの不整合検知。
- completed retryでusage/cards/assetsが増えないこと。
- migration rollback／既存データとの互換性。
- 新規exam prepare後にclientが離脱したケース。

## リスク / 対立しうる設計判断

| 設計判断 | 利点 | 主なリスク・対立 |
|---|---|---|
| client先行R2 upload | server action body上限を回避 | prepare session、orphan、storage abuse、保持データ増加 |
| 同期一発 | UXが単純 | platform timeout、切断後の結果回収、長い処理の再送 |
| 1回のGemini call | 文脈共有、call数削減 | 全体truncate、画像数上限、1 source障害のblast radius |
| cards先保存→crop | card IDをcrop keyに使いやすい | crop失敗時の部分状態、再試行card重複 |
| crop完了後cardsを保存 | 公開状態が単純 | cropとrefsのcard ID確保、全体失敗時の作業損失 |
| deterministic keyにordinalを含む | 同一runで単純 | AI順序揺れで同じ図が別assetになる |
| ambiguous→question | 図を捨てにくい | 誤った場所へのsilent attachment |
| padding 6%固定 | 情報切れを減らす | 隣接図・本文・解答の混入、カード表示肥大 |
| EXIF≠1だけ除外 | 実装が限定的 | metadata消失、EXIFなし回転を検出不能、仕様名との乖離 |
| server再検証 | 座標・fingerprintの信頼性向上 | decodeコスト増、同期時間増 |
| source長期保持 | recrop・文書ライブラリへ拡張可能 | GDPR、storage cost、侵害時影響 |
| DB cascade中心 | schemaは単純 | R2 key消失により物理削除不能になり得る |
| outbox/deletion ledger | 削除の再試行・監査が可能 | table・worker・運用が増える |
| TTLだけのclaim回収 | 実装が簡単 | live処理との二重実行 |
| lease/heartbeat | orphan判定が堅牢 | 更新処理と監視が増える |
| crop失敗をwarning成功 | textカードを失わない | 後から同keyでcropだけ再試行しにくい |
| crop失敗をoperation失敗 | 完全成功の意味が明確 | Gemini再実行やcard補償が必要 |

最優先で閉じるべきなのは、①source_document作成順、②`byte_size`欠落、③cardsを含む再試行冪等性、④完了前カードの不可視化、⑤ledger状態機械、⑥GDPR物理削除のdurable化です。これらは実装詳細ではなく、現planのtask分割を変え得る設計前提です。

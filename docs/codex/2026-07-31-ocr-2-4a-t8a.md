The normalization accepts invalid or duplicate generated identities for cards and figures despite treating UUIDv4 staging as an invariant. Such payloads can pass preparation and then fail or behave incorrectly during persistence.

Full review comments:

- [P1] Validate generated card IDs before returning — /workspaces/RecallMint/lib/ocr/domain/normalize-prepared.ts:287-287
  When `nextId` returns an invalid UUID for `cardId`, or repeats the same valid UUID for multiple cards while returning valid unique option UIDs, normalization still succeeds. The later publisher will then reject the malformed/duplicate primary keys and fail the entire atomic upload instead of isolating the affected card; validate `cardId` as UUIDv4 and enforce uniqueness across the normalized response.

- [P1] Validate and deduplicate generated asset IDs — /workspaces/RecallMint/lib/ocr/domain/normalize-prepared.ts:220-222
  For any factory that emits a non-v4 or repeated ID for surviving figures, the value is accepted without the defensive validation applied to option UIDs. These IDs are subsequently used as asset identities, so duplicate IDs can conflate separate crops or cause persistence conflicts, while malformed IDs will fail at the database boundary; validate each `assetId` and ensure figure asset IDs are unique before returning the prepared card.

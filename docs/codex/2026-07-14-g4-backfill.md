The backfill can create cross-user asset references for malformed existing image rows and the targeted CLI path still performs an unbounded table scan. These issues should be fixed before relying on the script in production.

Full review comments:

- [P2] Scope asset status lookup by card owner — /workspaces/RecallMint/scripts/backfill-card-asset-refs.ts:257-257
  When a pre-existing or synced `cards.images` row contains a UUID for an asset owned by a different user, this global lookup marks that asset as ready and `replaceCardRefs` then writes a ref with the card owner’s `userId` pointing at another user's asset. That violates the owner-scoping invariant enforced by `handleImages` and can make GC treat another user's asset as referenced; the lookup/projection needs to verify the asset belongs to the same user as the card or classify it as missing.

- [P2] Push the --user filter into the cards query — /workspaces/RecallMint/scripts/backfill-card-asset-refs.ts:250-250
  In `--user` mode, this still selects every card and its JSON `images` payload before `runBackfill` filters in memory. On a large production table, a targeted backfill for one user can unnecessarily scan/load all tenants' cards and time out or exhaust memory; the production `fetchCards` should apply `WHERE cards.userId = userId` when the flag is supplied.

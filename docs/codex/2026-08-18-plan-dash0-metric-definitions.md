## 独立論点(調査結果 + 要件から導出)

- 今日の学習量は、単なるカウンタではなく「今日の計画集合」を先に定義する必要がある。
  - `y = 復習 n + 新規 k` をいつの時点で確定するか。
  - 学習中に FSRS 更新で `due` が変わっても、当初の分母 y を維持するか。
  - 日中に OCR でカードが追加された場合、y に追加するか。
  - 途中で試験を切り替えた場合、進捗をどう扱うか。
  - 現在の `study_days.distinct_card_count` は「今日一度でも解いたカード」であり、「今日の計画集合のうち完了したカード」ではないため、そのまま x にできない。

- 「新規カード導入なしポリシー」と W2 の `新規 k` が両立していない。日次導入数を設けないなら、k の決定規則が存在せず、今日の目標 y、残問数、所要時間、完了状態が連鎖的に未定義になる。

- 選択中試験を主体とする要件と、`study_days` の user 全体集計は意味論上両立しない。UI 注記だけでは、試験別 y と全体 x を同じ進捗バーに載せる問題は解消しない。少なくとも W2 は分子・分母を同一母集合にする必要がある。

- L2 のローカル即時値とサーバ照合値のマージ規則が必要。
  - 未送信 outbox とサーバ反映済みイベントの重複排除方法。
  - flush 中・失敗時・別端末回答時の優先順位。
  - mount 後にサーバ snapshot がローカル即時値を一時的に巻き戻さない保証。
  - セッション終了が異常終了・タブ閉鎖だった場合の照合タイミング。
  - 「applied」のローカル上の意味と、未適用イベントを表示に含めるか。

- 集計の評価時刻を一回固定する必要がある。各ウィジェットが別々の `now` を取ると、JST 00:00、due 到来時刻、週境界で W2・W3・W6 が相互に食い違う。

- 期限超過では次を確定する必要がある。
  - New を除外するか。
  - `due === 今日の開始` は超過でなく本日分でよいか。
  - Learning/Relearning の短期ステップも「期限超過」と呼ぶか。
  - 今日中の時刻を過ぎたカードは、翌日まで超過にしない現在案でよいか。現在案は「overdue」より「前日以前からの持越し」に近い。

- W6 の due 分布も New の扱いが必要。New は生成時から即 due なので、除外しなければ今日のバーが未学習総数に支配される。W2 の n/k、W3 の期限超過と同じ分類規則を共有しなければならない。

- 「明日は約◯問」は現時点の due だけでは安定して算出できない。当日の回答結果により次回 due が変わるほか、新規カード数も未定義である。「現在の予定に基づく見込み」なのか、今日完了後の確定値なのかを分ける必要がある。

- 初見・復習のイベント順序には、履歴完全性の前提が必要。
  - answer_events 導入以前に回答済みのカード。
  - `cards.answered=true` だがイベントが欠損している場合。
  - 遅延同期により古い `answered_at` のイベントが後着した場合。
  - 同時刻を `event_id` で決める規則が、実際の回答順を表すとは限らない。
  - `answered_at` をクライアントが生成するなら、端末時計のずれも影響する。

- 近似復習正答率と厳密版は別指標として扱うべきである。定義や計測開始日が異なるため、同じ表示名のまま将来切り替えると数値が不連続に変わる。バージョン、適用期間、minimum sample を明示する必要がある。

- 苦手タグの統計母集団が不足している。
  - 「30日回答 >= 15」は全 applied イベントか、復習イベントだけか。
  - 復習イベントが 0 件でも候補条件を満たし得るか。
  - 表示する復習正答率は直近30日か全期間か。
  - 同一カードへの複数回答をすべて分母にするか。
  - 複数タグ付きカードは各タグに重複算入するか。
  - タグ category をまたぐ同名タグの表示・順位決定。
  - 現在タグで過去を再分類する仕様による数値変動を利用者にどう説明するか。

- 苦手カードは、要件上の「累計不正解」と `lapses` を代替可能なものとして扱えない。これは性能上の実装選択ではなく、別の学習状態を表すプロダクト判断である。
  - `lapses >= 2`: Review 到達後に Again を付けた回数。
  - 累計 `is_correct=false >= 2`: 初学時の苦戦も含む。
  - FSRS モードでは rating と正誤が乖離する。
  - どちらを選ぶかで「苦手」の利用者向け説明も変える必要がある。

- 週次 delta は「進行中の今週」と「完了した先週」を比較するため、週前半は構造的にマイナスになりやすい。全週比較か、同じ曜日・同じ時刻までの比較かを決める必要がある。また「先週の行なし」は、本当にデータなしなのか有効な 0 件なのか `study_days` だけでは判別しにくい。

- streak の最大表示値に注意が必要。入力 window が today + 60 日なら、実際に61日超続いていても取得範囲以上を正確に示せない。61で打ち止めになるなら「61日以上」等の規定が必要。

- 推定所要時間には次のスコープが未定義。
  - 選択中試験か user 全体か。
  - applied のみか、未適用ローカルイベントも含むか。
  - `elapsed_ms=0` を有効とするか。
  - 「直近」は `answered_at` と `created_at` のどちらか。
  - 偶数件 median の定義。
  - 120秒超を除外するのか120秒に clamp するのか。
  - 10分演習で算出件数が0または session cap 超過になった場合。
  - 端末変更時の急変、タブ放置による偏り、端末時計の不正確さ。

- クイック演習は母集合だけでなく、選出規則が必要。
  - 「間違い10」「未出題10」「苦手10」で候補が10件超の場合の順序。
  - due 優先、古い誤答優先、ランダム等のどれか。
  - 同じカードが複数プリセットに属することの扱い。
  - 10分プリセットの母集合と n/k の配分。
  - オフライン時に L3 依存の集合が stale/取得不能な場合。

- L3 ウィジェットのエラー状態と stale 状態が空状態から分離されていない。「十分なデータなし」「通信不能」「集計失敗」「古いキャッシュ」は異なる。空として非表示にすると障害をデータ不足に見せてしまう。

- 履歴集計と hard delete の関係を確定する必要がある。カードや試験を削除した場合、過去の回答数・週次・タグ統計からも消すのか、活動履歴として残すのか。現在カードとの JOIN に依存すると、削除後に歴史が変わる可能性がある。

- exam/date の日付意味が未定義。試験日当日は「あと0日」「今日」「あと1日」のどれか、過去日は何を表示するか、exam_date を date 型として JST で扱うかを決める必要がある。

- 数値表記の共通規則が必要。正答率の丸め、分母表示、delta の符号、約分の丸め単位、Top3 の同率、0件と未知値を一貫させる必要がある。

- 暫定閾値は単に shared 定数にするだけでなく、指標定義のバージョンとして扱う必要がある。21日・2回・8カード・15イベントを変更すると同じ履歴から表示が突然変わるため、較正方法、変更承認、比較可能性を決める必要がある。

- client/server 共通関数は、同じコードを import するだけでは十分でない。日付・timestamp の復元、Dexie と PostgreSQL の数値型、イベントの並び順、`now`、ライブラリ版まで fixture で固定する必要がある。

## plan ドラフトへの抜け・未考慮指摘

- W2 は既知の「x と y の母集合不一致」を未確定事項にしているが、その状態で `max(y-x, 0)` を定義している。clamp は不整合を隠すだけで、進捗率を正しくしない。別試験の回答だけで選択試験が完了表示になり得る。

- W2 の y は現在時点の due 件数から毎回計算するように読めるが、今日の計画を固定する時点がない。回答後の due 更新や日中新規追加で分母が変動する問題が未記載。

- `今日分完了 = y === 0` は不十分。開始時に y>0だったカードをすべて終えた状態と、最初から due が0件だった状態を区別できず、x/y の不一致時には誤判定する。

- `新規/日の parameter` を前方参照しているが、裁定済み前提は「新規カード導入なしポリシー」。新規導入制御を後続タスクへ置くだけでは、Dash-0 の W2 定義自体が成立しない。

- W2 の `n = due <= now` は「今日の目標」を時刻依存にする。今日の後半に due になるカードを朝の y に含めない一方、時間経過だけで y が増える。日単位の処方なのか瞬間時点のキューなのかが未決定。

- W2 の「約◯分」に `max(y-x,0)` を使うが、x は distinct card、y は現在 due/new、CTA の実出題集合も別である。時間推定の残問数として成立しない。

- W4 は候補条件を「直近30日の applied イベント15件」としつつ、順位に使う復習正答率の期間を定めていない。全期間と30日では異なるランキングになる。

- W4 の「対象問数」がカード数を指す一方、正答率の分母はイベント数である。この二つを同じ行に表示する際の説明がない。

- W4 の minimum sample は全イベント15件だけで、復習正答率自体の最小復習イベント数がない。初見イベント中心でも極少数の復習結果でランキングされ得る。

- W5 は要件の「間違い10 / 未出題10 / 苦手10」から「10」を表示・定義上落としている。件数受け渡しだけでなく、10件を選ぶ優先順も未定義。

- W5 の10分計算は `floor` により遅い利用者で0問になり得る。minimum 1、最大件数、既存 session cap との優先順位がない。

- W5 の「10分」の母集合を W2 と同じ `n+k` としているが、W2 自体に固定された集合が存在しない。また復習と新規をどの比率・順番で選ぶかもない。

- W6 は日別条件だけでは、期限超過カードが7本のどこにも入らない。「今日に合算」を UI 判断としているが、これは表示だけでなく集計定義であり、Dash-0 で決めるべき事項。

- W6 は New を除外するか記載がない。現 schema では全 New が今日以前の due になり得るため、W2/W3との整合に重大な影響がある。

- W7 の「先週に行が1件もない場合はデータなし」は誤判定の余地がある。同期済み期間内で行がないことは正当な0回答でもある。観測期間・アカウント作成日など別情報が必要。

- W7 の delta は進行中週対完了週という比較バイアスを考慮していない。

- streak は61日 window による上限・切断表示を扱っていない。

- 初見正答率では event ordering を決定的にしたが、answer_events が完全な生涯履歴である保証や、イベント導入前カードの扱いがない。

- 復習正答率の近似版から厳密版への移行について「混ぜない」とあるだけで、v1 の表示期間、計測開始日、名称の区別、切替条件がない。

- `state !== 0 && last_review === null` について、「絞る順序を守れば到達しない」は誤り。state フィルタは null のカードを除外しない。構造的不変条件が壊れた場合は、throw、除外、診断記録のどれにするか必要。

- 平均Rの `default_w` は現時点の singleton と一致するが、将来パラメータが変更された場合、既存カードの stability とどのパラメータでRを計算するかが未考慮。さらに standalone 関数だけを import しても、実際の bundle 減少はビルド結果で確認しない限り保証できない。

- 推定時間の「120秒以下のもの」は除外であり、「clamp」という記述と一致しない。120秒に丸めて含めるのか、サンプルから捨てるのかを一意化できていない。

- 推定時間の直近100件について、試験スコープ、applied、並び列、0ms、同時刻、サンプル最低数が未記載。

- L2 の照合方針に、outbox と server snapshot の重複排除・巻き戻り防止がない。境界規則だけでは実装者が一意に実装できない。

- L3 の空状態閾値が、苦手タグ以外では具体値を持たない。「閾値未満」は成果物要件の「曖昧語を残さない」に反する。

- L3 の通信エラー、stale cache、初回ロードを「データ不足」と区別する規定がない。

- W1 は schema に存在しない `exam_date` を指標として定義しており、Dash-0時点の具体データ源を満たしていない。「—」ではなく、現状実現不能・必要な将来データ源を明示すべき。

- 「選択中の試験」の決定前に、既定スコープを選択中試験とする全定義を凍結している。試験削除、最後の試験が存在しない、複数タブで異なる試験を開く場合も未考慮。

- hard delete 後の answer_events、review_logs、週次・タグ履歴の扱いがない。特に「現在カード集合を基準に過去イベントを集計」すると削除によって過去値が変わる。

- harness は正常系中心で、次の境界 fixture が不足している。
  - state非Newかつlast_review null
  - FSRSモードで `rating` と `is_correct` が乖離
  - 遅延・順不同・重複イベント
  - 未送信ローカルイベントとサーバ反映済みイベントの併存
  - 複数試験を同日に回答
  - 週境界・年境界
  - タグ付け替え後の再集計
  - review_logs 蓄積開始日前後
  - 61日超streak
  - カード削除後の履歴
  - 120秒ちょうど、超過、0ms、偶数件median

## リスク / 対立しうる設計判断

- 試験別ホームを守るか、既存の user 全体 L2 を再利用するか。前者は schema/集計コスト、後者は進捗表示の意味的不正確さを伴う。W2だけは混在を許容しにくい。

- 「今日の処方」を固定スナップショットとして持つか、現在の due 状態から動的計算するか。固定なら保存・同期が必要、動的なら分母変動と完了判定の不安定さが残る。

- 新規カードの日次制御を導入するか、現状どおり全 New を即時候補にするか。前者は裁定済み前提との整合確認と保存先が必要、後者は W2 の k と大規模OCR時の処方性を失う。

- 苦手を `lapses` とするか累計不正解とするか。L1/オフライン性を優先すると利用者の直感から外れ、意味を優先するとL3依存・端末即時性の低下が発生する。別名称で両方持つ選択肢もある。

- L3 の鮮度とオフライン性。非表示にするとレイアウトと情報量が変動し、キャッシュ表示にすると古い診断を最新に見せる危険がある。

- タグ履歴を持たず現在タグで再分類する簡潔性と、過去指標の再現可能性・監査可能性は両立しない。

- 近似復習正答率による早期可用性と、Review状態に限定した厳密性は両立しない。同一名称での切替は利用者にも比較分析にも危険。

- 週次を「今週対先週」で単純比較する分かりやすさと、途中経過を公平に比較する統計的妥当性が対立する。

- elapsed_ms をローカル利用する即時性・実装の小ささと、端末間一貫性・品質管理が対立する。無限成長するローカルイベントを統計用途で読み続ける性能リスクもある。

- 期限超過から New を除外する意味の自然さと、形式的な `due < dayStart` の単純性が対立する。採用するなら「due」は全stateで同じ意味ではないことを仕様として明記すべき。

- shared SSoT の強化と client bundle 方針が対立する。特に ts-fsrs 依存を共有層へ置くと、意図せず client bundle に広く伝播する可能性がある。

- 暫定閾値を早く固定する実装安定性と、prod 分布未確認のまま意味を確定するプロダクトリスクが対立する。少なくとも「定義の凍結」と「数値の凍結」は分離した方がよい。

Unconditional source cleanup introduces a race that can break the winning pipeline execution, and PDF uploads record transformed output size instead of source upload size.

Full review comments:

- [P1] Delete PDF sources only after the owning execution finishes — /workspaces/RecallMint/app/(app)/app/upload/_lib/upload-pipeline.ts:440-442
  When a stale or duplicate pipeline invocation loses the start/count fence, it returns from `runOcrPhase` but still reaches this unconditional cleanup. Because invocations for the same operation use the same source keys, the loser can delete a PDF while the winning invocation is between its count and render GETs, causing the winner to fail with `pdf_source_unavailable`. Cleanup must be coordinated with ownership or deferred until no active execution still needs the source.

- [P2] Record original PDF bytes instead of rendered WebP bytes — /workspaces/RecallMint/app/(app)/app/upload/_lib/upload-pipeline.ts:773-776
  For uploads containing PDFs, `file_size_bytes` now records the rasterized WebP output size rather than the received source size promised by `upload_records` and used by the existing image path. The value can differ substantially based on rasterization/compression and therefore corrupts upload-size auditing; accumulate the actual PDF bytes fetched during count plus the original image buffers instead.

The new action generally type-checks, but idempotent replays can return a differently ordered reservation list, and malformed action arguments can cause an uncaught runtime error rather than the documented result.

Full review comments:

- [P2] Preserve the original reservation order on idempotent replay — /workspaces/RecallMint/app/(app)/app/upload/_actions/prepare-upload.ts:205-208
  When source IDs are not already lexicographically ordered (for example, inputs `page-10`, then `page-2`), the first response returns `reserved` in input order, while a replay sorts it by `sourceId`. This violates the stated idempotency contract that the same operation result is returned and can change client source-to-result positional mapping; either make the initial response use the same ordering or persist an explicit source ordinal.

- [P2] Validate the action input object before dereferencing it — /workspaces/RecallMint/app/(app)/app/upload/_actions/prepare-upload.ts:146-146
  Because Server Action arguments are untrusted at runtime, a direct call with `null` (or another non-object value) throws while evaluating `input.idempotencyKey` instead of returning the declared `invalid_input` outcome. Validate the outer input shape first, or safely extract the key, so malformed requests do not become server errors.

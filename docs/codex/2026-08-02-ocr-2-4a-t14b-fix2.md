The new source GC can still delete an object while a derivation is concurrently being committed, violating its provenance-retention invariant. Its unbounded candidate lookup can also make sufficiently large sweeps fail outright.

Full review comments:

- [P1] Close the derivation race before deleting the R2 object — /workspaces/RecallMint/scripts/gc-image-assets.ts:651-654
  If `cropFigureAndStore` inserts an `asset_derivations` row after this snapshot is read but before `deleteObject` runs, `derivedNow` remains false and the source object is still physically deleted; the subsequent row delete can then cascade the newly committed provenance. This is exactly the asynchronous crop race described in the surrounding comment, and a one-time pre-loop read only narrows rather than closes it. The final eligibility check and state transition/delete need database coordination with the derivation insert path (for example row locking or an atomic guarded operation) before irreversible R2 deletion.

- [P2] Batch the source derivation lookup — /workspaces/RecallMint/scripts/gc-image-assets.ts:908-911
  When a sweep contains enough pre-existing or newly promoted `deleting` source assets, passing every ID to one `inArray` query can exceed PostgreSQL's bind-parameter limit and abort the entire source lane before collection. The asset lane already batches the equivalent lookup with `COLLECT_BATCH_SIZE`; this lookup should do the same rather than issuing one unbounded `IN` query.

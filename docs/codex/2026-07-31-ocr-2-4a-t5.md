The finalize flow has a concurrency race that can make the immutable R2 object disagree with the metadata committed by the CAS winner. This violates a core integrity guarantee of the new implementation.

Review comment:

- [P1] Prevent concurrent finalizers from overwriting the winning object — /workspaces/RecallMint/app/(app)/app/upload/_actions/source-asset-actions.ts:251-253
  When two finalizations overlap, both can read `reserved` and PUT different bytes to the same final key before competing on the database CAS. The request that loses the CAS may perform its PUT after the winner, then observe `ready` and return success, leaving the final object bytes inconsistent with the winner's stored hash, MIME, and dimensions. The object promotion must be tied atomically to the winning attempt or use a unique/content-addressed key so a losing finalizer cannot overwrite it.

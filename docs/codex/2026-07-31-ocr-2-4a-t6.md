The claim path breaks completed-operation replay when the daily cap is reached and performs its security-relevant aggregate size check without synchronizing it with concurrent asset finalization.

Full review comments:

- [P1] Return completed operations before enforcing the daily cap — /workspaces/RecallMint/app/(app)/app/upload/_actions/claim-operation.ts:69-75
  When the global count has reached the limit, this early return applies even to an already `completed` operation. Retrying a completed request after later Gemini usage therefore returns `daily_limit_exceeded` instead of its stored `resultSummary`, breaking the promised idempotent replay despite requiring no new Gemini call. Classify non-claimable states, especially `completed`, before applying the claim-time cap.

- [P1] Make the size check atomic with the claim — /workspaces/RecallMint/app/(app)/app/upload/_actions/claim-operation.ts:84-99
  If an asset finalization changes another reserved row to `ready` after this SELECT but before the operation UPDATE, the claim succeeds using the earlier, smaller total even when the finalized aggregate exceeds `TOTAL_UPLOAD_LIMIT_BYTES`. Because the finalizer updates different rows, the operation-row CAS does not serialize that change, allowing the server-side anti-tampering limit to be bypassed by concurrent finalize/claim requests; the claim predicate or locking strategy must bind the measured ready set to the state being claimed.

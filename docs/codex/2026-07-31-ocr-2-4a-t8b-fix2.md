The stage commit can still accept a source manifest that changed during external I/O, potentially producing an unusable prepared payload. Multi-source processing also violates the documented deterministic ordering contract.

Full review comments:

- [P1] Revalidate the source manifest when committing the payload — /workspaces/RecallMint/app/(app)/app/upload/_actions/stage-prepared.ts:221-227
  If a source is deleted or transitions to `deleting` after `loadFencedSourceManifest` commits but during the R2/Gemini calls, this CAS still changes the operation to `prepared` because it checks only operation status and lease version. That recreates the documented claim-to-stage race and can persist a payload referencing a missing source; the manifest must be checked again atomically in the stage-save transaction before this update.

- [P2] Process unordered sources in deterministic source-id order — /workspaces/RecallMint/app/(app)/app/upload/_actions/stage-prepared.ts:160-160
  For uploads containing multiple sources, ordering by the random database `id` makes the Gemini parts order depend on insertion details, contrary to the repository's documented requirement that the unordered source set always be processed by `source_id`. Since model output can depend on image order, equivalent manifests can produce different OCR results; order these rows by `sourceAssets.sourceId` instead.

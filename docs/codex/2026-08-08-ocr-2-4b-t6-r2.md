The PDF flow leaves retryable UI state pointing at an invalidated session on several accepted-response exits, and its advertised compatibility fallback cannot satisfy server UUID validation. Both can prevent otherwise valid PDF uploads.

Full review comments:

- [P2] Recreate the PDF session on every recoverable accepted exit — /workspaces/RecallMint/app/(app)/app/upload/_components/upload-form.tsx:765-766
  Once an `accepted` response clears `uploadSessionIdRef`, only the terminal `failed` branch rebuilds the PDF session. If polling degrades due to repeated fetch failures/time limits, or an accepted replay has an empty `sourceDocumentId`, the form becomes enabled again while its ready PDF entries still reference the consumed session; the next submit sends an empty `uploadSessionId` and is guaranteed to fail validation. Re-upload those PDFs before exposing a retry, or keep the form non-retryable in these branches.

- [P2] Generate valid UUIDs in the compatibility fallback — /workspaces/RecallMint/app/(app)/app/upload/_components/upload-form.tsx:89-91
  In browsers where `crypto.randomUUID` is unavailable, this fallback produces strings such as `timestamp-random`, but the new reserve/finalize actions validate both `uploadSessionId` and `fileId` with `z.uuid({ version: 'v4' })`. PDF uploads therefore always fail with “入力内容が正しくありません” in those environments; the fallback must generate an actual UUID v4 or PDF support should explicitly require `randomUUID`.

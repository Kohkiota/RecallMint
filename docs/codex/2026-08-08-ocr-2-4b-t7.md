The new public PDF path accepts submissions although the pipeline explicitly ignores all PDF inputs. It also performs unbounded concurrent R2 validation before applying the manifest page limit.

Full review comments:

- [P1] Process PDF sources before accepting PDF submissions — /workspaces/RecallMint/app/(app)/app/upload/_lib/upload-pipeline.ts:174-181
  When `sourcePdfManifest` is non-empty, these arguments are discarded and `runOcrPhase` still receives only the image files. Consequently mixed uploads silently omit every PDF, while PDF-only uploads run the existing OCR pipeline with zero sources despite being returned as `accepted`; the inserted PDF sentinel fields are never resolved. PDF submissions should not be accepted until this pipeline consumes and renders the manifest.

- [P2] Reject excessive page manifests before issuing HEAD requests — /workspaces/RecallMint/app/(app)/app/upload/_actions/submit-upload.ts:360-362
  For an authenticated request containing more than `OCR_MAX_PAGES` PDF entries, the page-limit check occurs only after `Promise.all` has launched one R2 HEAD request per entry. Since the schema places no entry-count limit and `declaredBytes` may be as small as 1, a modest malicious manifest can create hundreds or thousands of concurrent storage requests even though it is guaranteed to be rejected. Compute and reject the echoed page total before this fan-out, while retaining the later trusted count-phase enforcement.

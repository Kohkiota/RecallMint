## 独立論点(調査結果 + 要件から導出)

### 1. cascade 前 purge だけでは、並行処理 race を閉じられない

単純な「列挙 → purge → exams DELETE」には次の窓がある。

1. source_document を列挙
2. 既存 source_assets を purge
3. 並行する upload/finalize が新しい object を PUT、または temp→final を進める
4. exams DELETE が行を cascade
5. 新しい R2 object だけが残る

外部 I/O 中に DB lock を保持できない制約があるため、削除開始時に永続的な deletion intent/fence を立て、prepare/finalize 側が新規処理を拒否または中止する仕組みが必要になる。少なくとも以下との競合を検証すべきである。

- prepare-upload の reserved 行作成
- presigned PUT 済みだが未 finalize の upload
- temp→final の CAS 更新
- OCR/派生処理による遅延した書込み
- 同一 exam の二重削除、Clerk webhook の再送

fence を追加しない場合は、purge 後に source_assets を再列挙し、空であることを削除 tx 内で検査するだけでも race は縮小するが、既に発行済み presigned PUT の後着までは防げない。

### 2. 「退会を続行して行を cascade」は net-safe 要件と直接衝突する

R2 DELETE 失敗後に退会 tx を続行すると、回収に必要な source_assets 行を意図的に失う。これは経路 C と同型であり、「prefix sweep が将来拾う」だけでは net-safe 順序を満たしたとはいえない。特に scheduler がなく手動実行のみなら、source の残存期間に上限がない。

退会を止めない要件と source 行を失わない要件を両立するなら、cascade の影響を受けない durable deletion ledger/outbox に、少なくとも以下を退会 tx 前に保存する設計が候補となる。

- user ID
- object key
- source asset ID
- 削除試行状態・回数・最終エラー
- 作成時刻、次回試行時刻

source_assets が cascade されても、この台帳を行駆動の再試行元にできる。prefix listing は未知 orphan の修復網として残せるが、通常の退会失敗を毎回 row-less orphan に変える主回収機構にはしない方が強い。

### 3. exam 削除中断にも部分成功がある

複数 source_document のうち途中で purge が失敗すると、exam は残る一方、先に成功した source は既に削除されている。また、全 purge 成功後に exam DELETE tx が失敗しても同じ状態になる。

新評価軸では provenance 消失は許容されるが、ユーザーから見ると「削除に失敗した exam の一部原画像だけ消えた」状態になる。この状態を明示的に許容するか、exam を削除処理中としてUI・再処理から隔離するかを決める必要がある。

### 4. purge の成否契約を明確にする必要がある

呼出側が安全に判断するには、次を区別する必要がある。

- R2 DELETE 成功
- 404＝既に不存在
- R2 DELETE 失敗
- R2 成功後の行 DELETE 失敗
- mark tx 失敗
- collect 前後の例外
- 対象なし
- 別処理が先に回収した場合

特に「R2 は消えたが行 DELETE が失敗」は source 残存リスクではない。exam 削除を中断する理由が整合性保護なのか、単なる summary の非ゼロ判定なのかを分けるべきである。

### 5. row-less sweep の誤削除防止条件が「行なし＋24時間」だけでは弱い

「行がない」は、次の状況でも一時的に成立しうる。

- finalize の CAS 切替中
- DB transaction と R2 listing の観測タイミング差
- 長時間停止した正規 upload
- 有効期間の長い presigned URL による遅延 PUT
- DB障害・レプリカ遅延・不完全な照会
- cleanup と再試行が並行している状態

安全条件として少なくとも以下が必要である。

- grace を presigned URL 最大有効時間、operation 最大実行時間、再試行幅、時計ずれより長くする
- key grammarを厳密に検証し、想定外 key は自動削除しない
- 削除直前に primary DB で存在を再確認する
- source_assets だけでなく、進行中 upload_operations/source_documents/deletion ledger との関係も確認する
- DB照会失敗時は fail closed
- 必要なら二回の独立した走査で orphan と観測されたものだけ削除する

24時間は根拠となる既存 TTL が示されない限り、安全境界ではなくヒューリスティックにすぎない。

### 6. listing sweep 自体の完全性

設計上確認すべき点は以下。

- `users/` と各 `src/` の両階層で全ページを最後まで辿る
- continuation token のエンコード・署名
- 1000件超、空ページ、token付き空ページへの対応
- XML namespace、entity、URL encoding、壊れた entry の扱い
- temp と final の双方を列挙する
- 旧形式・想定外形式の source key をどう検知するか
- prefix の境界検証により別 user を巻き込まない
- LIST後・DELETE直前に行が作られる TOCTOU race を防ぐ
- delete失敗、timeout、429/5xxを台帳に残す
- 404を成功として冪等に扱う

「2段 listing」は表示 asset を避ける効率化にはなるが、全 user prefix の列挙自体はアカウント数に比例する。運用時間、APIコスト、中断再開用 checkpoint も必要になる。

### 7. 手動 sweep は新評価軸の保証にならない

source 残存を「受容しない」なら、手動 opt-in sweep の存在だけでは時間的保証がない。最低限、以下を決める必要がある。

- 誰が、どの頻度で実行するか
- 失敗・未実行を誰が検知するか
- 最大許容残存時間
- backlog・最古 orphan・削除失敗数の監視
- 中断後の再開方法

自動化を別 task にする場合でも、T15完了時点でどこまでを「経路閉鎖」と表現できるかを限定すべきである。

### 8. PII cascade の検証範囲

FK定義だけでなく、退会処理が当該 user の全 exams を確実に削除することが前提になる。次を実PGで確認すべきである。

- 複数 exam・各状態の upload_operations
- retry/failed/terminal operation
- `prepared_payload IS NULL` と非NULL
- webhook 再送後も残らない
- tx rollback 時には中途半端な scrub/delete にならない
- prepared_payload の内容が integration failure やログに複製されない

### 9. 既知以外の残余経路

「source が消え残る」観点では、少なくとも次も棚卸し対象である。

- presigned PUT 発行後、行が cascade された後着 PUT
- temp削除の best-effort失敗
- lost-CAS cleanup失敗
- purge成功後の遅延 retry が同じ key を再作成する可能性
- deleteObject の timeout後、実際の成否が不明なケース
- source_document を直接削除・置換する保守script、migration、admin操作
- malformed/legacy key が `users/{uid}/src/` 外にあるケース
- multipart upload が使われる場合の未完了 multipart
- test/seed/import系がproduction credentialsを使用しうる経路

## plan ドラフトへの抜け・未考慮指摘

1. 最大の抜けは、purge と cascade の間、および cascade 後の遅延 PUT raceである。Task 1・2とも deletion fence や presigned URL の無効化相当がなく、「経路 C を閉じる」という完了条件を満たしきれない。

2. D3の退会設計は、失敗時に行を失わせるため、Global Constraints の「行をR2より先に消さない」と自己矛盾している。prefix sweep は事後修復であり、順序違反を解消しない。

3. 50件上限は、上限超過分を確実に row-less orphan にする仕様である。しかも sweep は手動なので、新軸に対する安全策として弱い。上限を置くなら durable queue/outbox へ全件登録してから webhook を完了すべきである。

4. `SourcePurgeTrigger` unionへの値追加は「呼出漏れをtypecheckが強制」しない。unionは許可される文字列を制限するだけで、削除入口が purge を呼んだことや、新しい入口の追加漏れは検出しない。

5. Task 3は continuation token を返す試験しかなく、Task 4が全ページを反復することを明記していない。両階層の1000件超を使った統合試験が必要である。

6. Task 4はLIST後のDB再確認がなく、LIST時点では行なしでもDELETE直前に正規行が成立するTOCTOU誤削除がありうる。

7. `ORPHAN_MIN_AGE_MS=24h` の根拠がない。presigned URL TTL、upload operation timeout、最大再試行期間との比較が必要である。

8. sweep のR2 DELETE失敗・timeout・404・台帳記録を完了条件で試験していない。dry-runやlisting失敗だけでは「削除失敗をsilentにしない」を pin できない。

9. exam purgeの試験に以下が不足している。

- purge途中の部分成功
- purge完了後のexam tx rollback
- 同時finalize/prepare
- 二重削除
- R2 404
- mark/row DELETE側の失敗
- 遅延PUT

10. 退会試験に以下が不足している。

- webhook再送
- 複数ページ・50件超
- purge途中のthrow
- source列挙自体の失敗
- 退会tx失敗後の再試行
- scrub後もledgerから回収可能か
- 同時upload

11. `source_assets.user_id` から distinct document を列挙すると、既にrow-lessになったobjectや、列挙直後にPUTされるobjectはinline purge対象にならない。これは既知のsweep依存だが、手動運用との組合せでは残存保証がない。

12. ListObjects XMLを「最小parse」する方針は、破壊的削除の入力としては注意が必要である。namespace、entity、encoding、欠損要素を含む実レスポンスfixtureで検証し、parse異常はページ全体をfail closedにする方が安全である。壊れたentryだけを落として走査継続すると、そのobjectが永久に不可視になりうる。

13. 「prefixがsourceを過不足なく囲む」は現行key生成コードについての主張に留まる。既存bucketにlegacy/malformed keyがないことは別途inventoryが必要である。

14. destructive scriptの既存作法として挙げられた「台帳記録」が、成功したorphan削除について明確でない。誰が何をいつ削除したかを残さないと、誤削除時の追跡が困難になる。

15. stg smokeの「既知1件がdry-runに出る」は、24時間条件、実際のkey prefix、DB不在を事前に固定しないと不安定である。また一度削除すると再現不能なので、再実行可能なfixtureも必要になる。

## リスク / 対立しうる設計判断

- 退会完走 vs net-safe：退会を止めないなら、cascadeされない削除台帳が最も素直。手動prefix sweepだけに委ねる設計は、退会可用性を優先してsource残存リスクを受容している。

- 外部I/Oをtx外に置く vs 並行処理遮断：長いDB lockは避けるべきだが、代わりに永続 deletion state と各書込み入口のfenceが必要になる。

- exam削除中断 vs 部分的source消失：中断はrowを保全する一方、purge済みsourceは戻らない。削除中状態をUIに出すか、部分消失を仕様として許容する必要がある。

- 誤削除防止 vs 迅速なorphan回収：graceを短くすると著作物の残存時間は減るが、正規の遅延uploadを消す可能性が上がる。固定24時間ではなく、実際の最大ライフサイクルから決めるべきである。

- sweepをT15に含める vs 最小実装：既存orphanとrow-less経路が現存するため含める合理性はある。ただし主経路の安全性をsweepに依存させると、repair toolが通常処理の必須構成要素になる。

- 手動運用 vs 「受容しない」の保証：手動実行は修復手段にはなるが、残存時間の上限を保証しない。新評価軸を厳密に満たすなら、自動再試行または運用SLOが別途必要である。

- prefix全走査 vs durable queue：listingは未知orphanも発見できる一方、高コストで誤削除判定が難しい。durable queueは既知失敗に強いが、既に行も台帳も失ったobjectは見つけられない。両者は代替ではなく、queueを主経路、listingを監査・修復網とする組合せが安全である。

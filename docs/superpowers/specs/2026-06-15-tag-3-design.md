## 1. 目的とスコープ

### 1.1 目的

1. OCR が抽出する `custom_props` を user の試験横断タグマスタ (`tag_categories` / `tag_options`) と card-option junction (`card_tags`) に分解保存し、 Tag-1 で失った「資料に明示記載のメタデータが card と紐づく」 機能を取り戻す。
2. find-or-create (同 user 同名再利用) で tag マスタを汚染しない。 UNIQUE(category_id, name) を活かす。
3. local-first 規律維持: 書込は server 直書き、 client mirror への反映は既存 pull cursor 6 本に乗せる (新経路追加なし)。

### 1.2 前提 (OT 確定、 本 spec で再検討しない)

- 付与モデル = OCR 抽出 → 即時自動適用 (preview/確認 UI なし)
- category 紐づけ = `custom_props` の key を category 名として find-or-create
- 新規 category の `select_type` = `'multi'`
- 複数 card = per-card 処理、 同 upload 内の同名 (category / option) は同 id 流用 (bulk 集約)
- 正規化 = OCR 自動タグの照合キーは **前後空白 trim のみ** (NFC・大小・全角半角は一切やらない)。 手入力タグは無加工 (Tag-3 対象外)
- 競合 = `INSERT ... ON CONFLICT (category_id, name) DO NOTHING` + 既存 id は別 SELECT で回収 (2 段)
- UNIQUE(category_id, name) は既存 (`migration 0020:43` / `schema.ts:723`) → 追加しない
- `@google/genai` は 1.x 維持 (2.x bump は別 task)
- DB は stg/prod とも全 truncate 済 → 既存 row 正規化 migration 不要、 新規作成ロジックのみ

### 1.3 スコープ

- `app/(app)/app/upload/_actions/process.ts` の cards INSERT tx (L533-549) に tag 分解書込を同梱
- 新規 helper `lib/tags/apply-ocr-tags.ts` を追加 (find-or-create のセマンティクスは既存 `apply-tag-mutation.ts` と異なるため module 分離)
- 受け入れ test (find-or-create / trim 照合 / per-upload 集約 / new category default / new option default / tenant isolation 構造)

### 1.4 スコープ外 (明示)

| 項目 | 受け入れ先 |
|---|---|
| OCR prompt / response schema 改修 | 既に discover mode で `custom_props` 出力済、 改修不要 |
| `@google/genai` 1.x → 2.x bump | 別 task (Tag-3 と独立、 本 spec scope 外) |
| 既存 row の正規化 migration | DB 全 truncate 済で母数 0、 不要 |
| confidence 閾値 / preview UI / 手動補正 UI | YAGNI (prompt L247「推測や事前知識からの補完は禁止」 で false positive を抑える)。 user は既存 tag UI で手動削除可 |
| 既存 manual category と OCR category の照合強化 (NFC 等) | OT 確定で trim のみ。 表記揺れ手動マージは別 sprint |

## 2. アーキテクチャ

### 2.1 書込 path 全体

```
processUpload (server action, process.ts)
  ├─ guard tx: advisory lock + exam/source_doc INSERT
  ├─ Gemini OCR (runOcrPipeline)
  └─ cards bulk INSERT tx (L533-549, 既存)
      ├─ tx.insert(cards) ... RETURNING id, title  (既存)
      ├─ applyOcrTags(tx, userId, insertedCards, pipelineResult.cards)  ★Tag-3 新設
      │   ├─ collect custom_props keys (trim) → per-upload unique categories
      │   ├─ find existing tag_categories (user_id + name IN (...))
      │   ├─ insert missing tag_categories (default: select_type='multi', color=null, sort_key=末尾)
      │   ├─ collect (category_id, value trim) pairs → per-upload unique options
      │   ├─ find existing tag_options (category_id + name IN (...))
      │   ├─ insert missing tag_options (default: color=null, sort_key=末尾)
      │   └─ bulk insert card_tags (card_id × option_id × user_id)
      └─ tx.update(exams) cardCount += N  (既存)
```

### 2.2 sync 伝搬 (既存経路、 追加なし)

`lib/sync/pull.ts` は cursor 6 本 (cards/exams/tombstone/tag_categories/tag_options/card_tags) で全 entity を pull する設計が既存 (Tag-1 / Tag-2b で完備)。 OCR 中に server で `tag_categories` / `tag_options` / `card_tags` を INSERT すれば、 次 pull で client mirror に増分反映される。 **新規 sync 経路は不要**。

cards の新規作成は新 `created_at` で cursor 増分に乗るため、 `cards.updated_at` の明示 bump は不要 (pull.ts L18-20 規約の「書込側は updated_at を bump」 は **既存 card の card_tags 集合を変えるとき** の規約。 OCR は新規 card のみ作成するため対象外)。

## 3. データフロー

### 3.1 find-or-create (2 段 SELECT + ON CONFLICT)

PostgreSQL は `INSERT ... ON CONFLICT DO NOTHING RETURNING id` で「衝突した既存行の id」 を返さない (DO NOTHING は新規 INSERT 行のみ RETURNING) ため、 2 段経路を採る:

```ts
// Step 1: 既存 SELECT (find)
const existing = await tx.select({ id, name })
  .from(tagOptions)
  .where(and(eq(userId), eq(categoryId), inArray(name, candidates)))

// Step 2: 未存在分を INSERT ... ON CONFLICT DO NOTHING (race 安全)
const missing = candidates.filter(n => !existing.some(e => e.name === n))
if (missing.length) {
  await tx.insert(tagOptions).values(missing.map(...)).onConflictDoNothing()
}

// Step 3: 念のため再 SELECT (race で並走 INSERT があったケースの id 回収)
const final = await tx.select({ id, name })
  .from(tagOptions)
  .where(and(eq(userId), eq(categoryId), inArray(name, candidates)))
```

Step 3 は通常不要 (advisory xact lock で同 user の並行 OCR は弾かれる、 process.ts L257-263) が、 同 user の manual create 経路 (entity_mutations) との race を理論上排除するため安全側に置く。

### 3.2 同 upload 内 bulk 集約

OCR が `[ {custom_props: {年度: '2024'}}, {custom_props: {年度: '2024', 分野: '微積'}} ]` を出した場合、 per-upload Map で `(category, trim(name)) → option_id` を構築し、 同名は同 option_id に集約する (5 card が同 `年度: '2024'` でも option は 1 個)。

```ts
const categoryByName = new Map<string, string>()        // trim(name) → category_id
const optionByPair = new Map<string, string>()          // `${category_id} ${trim(name)}` → option_id
```

### 3.3 sort_key 採番 (in-memory 累積)

`nextSortKey(existing)` (`lib/tags/next-sort-key.ts`) は起点 `'0'`、 `max(Number(v)) + 1`。 OCR で複数新規 category / option を一度に作る場合は、 既存 max を 1 回 SELECT したあと in-memory に累積する (advisory lock により並行 OCR なし、 drift 不可)。 manual create との race で +1 が drift しても次回 reorder で修正可 (T-B4 同様の 「perf 最適化 + 後追い修正可」 戦略)。

### 3.4 新規 category / option デフォルト値

| 列 | 値 | 根拠 |
|---|---|---|
| `name` | OCR key / value (trim) | OT 確定 |
| `select_type` (category) | `'multi'` | OT 確定 (OCR は同 key に複数 value 出すケースあり) |
| `color` | `null` | UI 側で `colorToClass(null) = COLOR_NULL_CLASS` (grey)、 user は manager UI で塗る |
| `sort_key` | `nextSortKey([...既存, ...同 upload 内 累積])` | 末尾追加、 既存 helper 再利用 |

## 4. トランザクション境界 (atomic 確定)

**OT 確定**: cards INSERT tx (process.ts L533-549) と同 tx で atomic。 tag 書込が予期せぬ DB エラーで失敗したら cards INSERT も rollback、 user は `SAVE_FAILED` を受ける。 best-effort 案は不採用。

理由:
- partial state (card だけ確定 / tag 落ち) を避ける。 user は OCR 結果が「全部成功 / 全部失敗」 のいずれか確定的に分かる。
- 既存の cards INSERT tx は cost も tracking 済 (Min4 sprint で fail-fast を確定済)、 tag 追加で時間 budget は数 ms オーダー (per-upload max 数十件 INSERT)。
- best-effort (tag は別 tx で握りつぶす) は、 失敗時 user が「OCR は成功したのに tag が無い」 を知る手段がなく silent な data loss になるため不採用。

**rollback トリガーの定義**:
- ここでの「失敗」 は **ON CONFLICT で握れない予期せぬ DB エラー** (接続断、 想定外の制約違反 = FK CASCADE 違反 / NOT NULL 違反 等) を指す。
- **UNIQUE(category_id, name) 競合は `ON CONFLICT DO NOTHING` + 再 SELECT (§3.1 Step 2-3) で握る正常系**であり、 rollback トリガーにしない。 find-or-create が race で衝突しても tag は確定状態に落ち着く設計が正常 path。
- 同様に「既存 row を find できた」 結果は正常系 = INSERT 不要、 INSERT 句自体を発行しない (`missing.length === 0` で skip)。

これにより、 UNIQUE race / find ヒットのような期待される衝突で cards INSERT を巻き込む過剰 rollback を避けつつ、 真の DB エラーで partial state を作らない atomic 保証は成立する。

## 5. 冪等性 / race

- **同 upload 二重起動**: process.ts L257-286 の advisory xact lock + in-flight check で 1 user 1 ジョブ。 構造上発生せず。
- **同 card への重複 card_tags**: PK `(card_id, option_id)` で重複不可。 同 upload 内同名集約 (§3.2) で同 option_id を 2 回 INSERT しない設計。
- **同名 category / option の race**: 並行 OCR は advisory lock で禁止。 manual create (entity_mutations) との race は ON CONFLICT DO NOTHING + Step 3 再 SELECT (§3.1) で吸収。
- **OCR retry / pipeline 失敗**: cards INSERT tx 前で fail → tag 書込も走らない。 cards INSERT tx 内で fail → 全 rollback (atomic)。

## 6. 主要モジュール

### 6.1 `lib/tags/apply-ocr-tags.ts` (新設)

```ts
export type ExtractedCardWithId = { id: string; custom_props?: Record<string, string | string[]> }

export async function applyOcrTags(
  tx: DbExecutor,
  userId: string,
  cards: ExtractedCardWithId[],
): Promise<void>
```

役割:
- 入力 cards から `custom_props` を集約 (per-upload Map)
- 既存 categories / options を find (2 段 SELECT)
- 不足分を bulk INSERT (ON CONFLICT DO NOTHING)
- `card_tags` を bulk INSERT (PK 衝突は構造上発生せず、 ON CONFLICT 不要)

`process.ts` の cards INSERT tx 内から呼ぶ。 `applyTagOptionCreate` (`lib/tags/apply-tag-mutation.ts:174`) は entity_mutations 経路の「id 指定 + 衝突 failed」 セマンティクスのため再利用しない。

### 6.2 `app/(app)/app/upload/_actions/process.ts` (改修)

L526 の捨却コメントを実コードに置換:
```ts
const insertedCards = await db.transaction(async (tx) => {
  const inserted = await tx.insert(cards).values(cardRows).returning({ id, title })
  await applyOcrTags(tx, user.id, inserted.map((row, i) => ({
    id: row.id,
    custom_props: pipelineResult.cards[i].custom_props,
  })))
  await tx.update(exams).set({ cardCount: sql`${exams.cardCount} + ${cardRows.length}`, updatedAt: sql`${exams.updatedAt}` })
    .where(and(eq(exams.id, examId), eq(exams.userId, user.id)))
  return inserted
})
```

## 7. 受け入れ条件 (test 戦略)

横断規律「完了条件二分」 (T-B5 / T-B6 / T-B7 と同形) を踏襲:

**(a) 構造 + 値 correctness**:
1. `applyOcrTags` の find-or-create が UNIQUE 競合を起こさない (per-upload 同名集約)
2. 既存 category / option が trim 一致で再利用される (新規 INSERT 0 回)
3. 新規 category default = `select_type='multi'`, `color=null`, `sort_key=末尾`
4. 新規 option default = `color=null`, `sort_key=同 category 内末尾`
5. `card_tags` PK 衝突なし (同 card × 同 option を 2 回挿さない構造)
6. `process.ts` の cards INSERT tx atomic (tag 書込失敗で cards 含め rollback、 unit で mock injection)

**(b-i) tenant isolation 構造**:
7. find-or-create の SELECT / INSERT 句に `userId` が必ず含まれる (snapshot で構造保証、 T-B4 流の `as unknown as unknown[][]` spy)

**(b-ii) wall-clock 非劣化**:
- OCR pipeline 本体 (Gemini 呼出) は秒オーダーで dominant、 tag 書込は数 ms オーダーで誤差。 wall-clock 計測は対象外。
- 代わりに「OCR `cards` 配列件数 N に対し SELECT 回数 = 2 (category find / option find)、 INSERT 回数 ≤ 3 (category / option / card_tags)」 を test で固定 (N に依存しない bulk 構造)。

## 8. 設計判断の確定記録 (OT 判断確定)

### 8.1 トランザクション境界 = **atomic 確定**

cards INSERT tx と同一 tx で実行、 予期せぬ DB エラー時は cards INSERT も rollback。 best-effort 案 (tag を別 tx で silent skip) は不採用。 §4 詳細 + rollback トリガー定義参照。

### 8.2 find-or-create helper = **独立 module 確定**

`lib/tags/apply-ocr-tags.ts` 新設で確定。 `apply-tag-mutation.ts` は entity_mutations 経路の id-specified / 衝突=failed セマンティクスのため再利用しない (§6.1)。

### 8.3 sort_key race = **受容確定**

in-memory 累積採番で発生し得る manual create との sort_key drift は受容。 correctness を壊さず、 user が reorder UI で修正可。 advisory lock は OCR 側のみで manual create 経路 (entity_mutations) との並走は理論上残るが、 sort_key は order 表現の派生値で衝突しても integrity に影響しない (`lib/tags/sort-comparator.ts` の `sortByKeyThenCreated` 不変条件で created_at fallback も担保済)。

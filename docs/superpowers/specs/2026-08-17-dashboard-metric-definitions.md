## 1. 目的と凍結範囲

Home v1 の 7 ウィジェットが表示する指標を、**実装者が解釈の余地なく計算できる粒度**まで一意化する。凍結するのは以下 4 つ。

1. 語彙(§4)— 「定着」「期限超過」「苦手」等が何の集合を指すか
2. ウィジェット別の指標(§5)— 表示名・式・データ源・空状態
3. 共通規約(§3)— 日界・母集合・正誤の二系統・層
4. shared 化の対象(§7)— client / server drift を機械検出する単位

**凍結しない**(Dash-1 以降へ明示的に引き継ぐ): UI 設計 / design token / `GET /api/stats/summary` の形 / 分析ページの節構成 / 新規/日の値と実装 / 選択中の試験の持ち方。未確定点は §6 に集約する。

### 1.1 裁定済み前提(再議論しない)

- トップ = 処方・固定 7 ウィジェット / 分析ページ = トップ非重複デフォルト + 節単位カスタム
- 新規カード導入なしポリシー(= 現状 daily new limit は存在しない)。recommendation 系はこの前提で定義
- `get_retrievability()` / `forgetting_curve()` は client 側 API
- `origin` 列(セッション開始経路)が成功指標。**滞在時間は不採用**
- 学習分析ダッシュボードの一般的効果への過大主張はしない(Paulsen & Lindsay 2024 / Kaliisa et al. 2024 の裁定済み文脈)。本 doc も「この指標を出すと成績が上がる」とは書かない

## 3. 共通規約

以下はすべての指標に無条件で適用する。個別定義では繰り返さない。

### 3.1 日界

**`lib/jst.ts` の 2 関数が唯一の日界**。`todayInJst(now)` が JST 'YYYY-MM-DD'、`jstDayRange(day)` が `[startAt, endAt)` を UTC instant で返す。TZ はハードコード JST でユーザー別 TZ は存在しない。

- 「今日の開始」= `jstDayRange(todayInJst(now)).startAt`
- `study_days.day` は既にこの規則で切られている。**日界を二重定義しない**(分析 doc v2 §4.1 の指示どおり)

### 3.2 正誤の二系統(R-1 / R-2)

repo は既に 2 つの正誤を別物として扱っている。定義もこれに乗る。

| 系統 | 源 | 用途 | 備考 |
|---|---|---|---|
| **選択の正誤** | `answer_events.is_correct` | **本 doc の「正答」「不正解」はすべてこちら**。`cards.last_correct` / `cards.current_streak` もこの系統 | 選択肢の集合一致(順序非依存)。両モードで意味が一定 |
| **評価(rating)** | `answer_events.rating` (1〜4) | FSRS scheduling の入力。`cards.lapses` / `stability` / `difficulty` / `due` はこちら由来 | 通常モードは is_correct から自動写像、FSRS モードは user 直接入力で乖離しうる |

**帰結**: 「正答率」と名の付く指標に `rating` を混ぜない。「lapse」「定着」「R」に `is_correct` を混ぜない。

### 3.3 母集合とスコープ

- 既定スコープ = **選択中の試験に属するカード**(`cards.exam_id` 一致)。例外は §3.4。
- 割合指標の**分母は常に対象スコープの総カード数**(分析 doc v2 §4.1 の「分母は常に総数で統一」)。「学習済みのうち」等の部分分母を作らない。

### 3.3a 削除済みカードと履歴の非対称性

cards は hard delete で、`answer_events.card_id` には **FK が無い**(`lib/db/schema.ts:623` — 「card 削除後も履歴は残る」dangling 正規)。したがって:

| 指標の型 | 削除後の挙動 |
|---|---|
| `cards` を引く L1(A〜J、M) | 削除カードは即消える |
| `study_days` 由来の L2(O・Q・R) | **削除しても過去の日次値は変わらない**(cards を join しないため) |
| `answer_events` × `cards` / `card_tags` を join する L3(K・L・P) | **削除カードの履歴が集計から落ち、過去の数値が遡って変わる** |

**規約**: L3 の集計は**現存カードとの join を正**とする(過去値の再現性より、表示中のカード集合との一致を優先する)。この帰結として **L3 の過去値はカード削除で動く**。これは仕様であり不整合ではない — §3.5(タグ付け替え)と同じ性質。UI で過去値の不変性を約束しない。

### 3.4 試験スコープの例外(R-3)

`study_days` に `exam_id` が無いため、**それを源とする指標は user 全体でしか出せない**。該当は「今日の進捗の照合値」「今週の回答数 / 学習日数」「連続日数」。

v1 の扱い = **user 全体のまま出し、UI で試験別でないことが分かる表記にする**(§6-① で Dash-1 へ引き継ぐ。schema 変更を伴う試験別化は本 doc の範囲外)。

### 3.5 タグ集計の時制(R-9)

タグ別集計は**集計時点の `card_tags` で過去イベントを分類する**。タグを付け替えれば過去の数値も変わる。これは仕様であって不整合ではない — 履歴付きタグ付けは持たない。

### 3.6 層(L1〜L4)

分析 doc v2 §3 の定義をそのまま使う。境界規則 = **現在状態(カード由来)= ローカル計算 / 履歴(イベント由来)= サーバ集計**。L2 のみ境界事例で、同一デバイス内はローカル即時反映、mount 時とセッション終了時に study_days 由来のサーバ値で照合。

### 3.7 空状態の一般規則

分析 doc v2 §5.2 を正とし、個別指標には**そこからの逸脱だけ**を書く。

| 状態 | 規則 |
|---|---|
| 試験 0 | hero CTA のみ。ウィジェットを描画しない |
| カードあり・学習 0 | 「最初の 10 問を解く」+ 未学習総数 |
| 今日分完了 | 「今日は完了 ✓ 明日は約◯問」+ 副導線。**先取り復習は勧めない** |
| 履歴僅少 | L3 系は個別 degrade。閾値未満は**非表示**(0% と表示しない) |

**0 と「データなし」を同じ表示にしない**を全指標に課す。特に割合指標は分母 0 のとき `0%` ではなく非表示 / 「まだ十分なデータがありません」。

### 3.8 4 状態の区別(空 / 不足 / 失敗 / 陳腐)

「非表示」を 1 つに束ねない。指標ごとに次の 4 つを別状態として扱う。

| 状態 | 意味 | 表示規約 |
|---|---|---|
| **空** | 母集合が構造的に 0(カードが無い等) | §3.7 の空状態 |
| **不足** | 母集合はあるが閾値未満(§4-P の 8 / 15 等) | 「まだ十分なデータがありません」 |
| **失敗** | 取得・集計が失敗した | **データ不足として見せない**。失敗と分かる表示にする |
| **陳腐** | 取得済みだが古い(オフライン等) | 値を出してよいが取得時刻を添える |

**この区別が要るのは L3 のみ**(L1 / L2 は client ローカルで失敗・陳腐が構造的に起きない)。v1 の L3 は W4(苦手タグ)だけなので、**適用対象は W4 の 1 箇所**。

### 3.9 評価時刻

**1 回のレンダリングで `now` を 1 度だけ取り、全ウィジェットに同じ値を渡す**。ウィジェットごとに `new Date()` を呼ぶと、JST 00:00 / due 到来 / 週境界の各瞬間に W2・W3・W6 の数字が互いに矛盾する。

### 3.10 表記規約

| 対象 | 規約 |
|---|---|
| 割合 | 整数パーセント(小数を出さない)。四捨五入 |
| delta | 符号を必ず付ける(`+18` / `-4`)。0 は `±0` |
| 所要時間 | 分単位に切り上げ、「約◯分」。0 分にしない(最小 1 分) |
| 件数 | 素の整数。桁区切りなし |
| 同率 | 各指標の定義に決定規則を書く(§4-P)。「順不同」を残さない |

### 3.11 履歴完全性の前提と、崩れる経路

初見 / 復習の分割(§4-K / §4-L)は「`answer_events` が当該カードの生涯全履歴を持つ」ことに依存する。現物で崩れうる経路は次の 3 つ。**いずれも「検出したら初見扱いにしない」で統一する**(誤って初見にすると初見正答率が汚れるため、判定不能は集計から落とす)。

| 経路 | 状態 | 扱い |
|---|---|---|
| `cards.answered === true` だが当該カードの applied event が 0 件 | 発生しうる(cards は pull で来るが event は上り専用で端末固有。server 集計なら本来一致するはずで、不一致は異常) | **そのカードを K / L の母集合から除外**し、除外件数を記録する |
| 遅延同期で古い `answered_at` の event が後着 | 起こる(outbox は再送で遅延しうる) | 集計は都度再計算なので**後着で過去値が変わるのは正常**。K / L に「確定値」の意味を持たせない |
| `answered_at` は client 生成(server で `min(raw, created_at)` に clamp) | 端末時計のずれが残る(未来方向のみ clamp される) | 順序の厳密性を主張しない。§4-K の 2 段規則で決定性だけ担保する |

### 3.12 暫定値は定義と分けて凍結する

`S_MATURE`(21)・苦手カード閾値(2)・苦手タグ閾値(8 / 15)・所要時間の既定値(20s)と上限(120s)は **prod 分布未確認のまま置いた暫定値**(§2.4)。

**本 doc が凍結するのは「定義」であって「数値」ではない。** 数値は §7.1 の shared 定数として 1 箇所に置き、変更は定義の変更ではなく **較正**として扱う。較正すると同じ履歴から表示が変わるため、変更時は変更日を記録し、それ以前の期間との比較に注意書きを付ける。

## 4. 語彙定義

各語は「名称(UI 表示名)/ 定義 / データ源(層)/ 空状態 / 未確定」で一意化する。式中の `card` は §3.3 のスコープ内カード、`now` は評価時刻。

### A. 未学習

- **名称**: 未学習
- **定義**: `card.state === 0`(New)
- **データ源**: L1 / client(Dexie `cards`)
- **空状態**: 総カード 0 のときウィジェットごと非表示(§3.7)。未学習 0 は「0」を表示してよい(意味のある 0)
- **備考**: R-10 により `answered === false` と同値。canonical は `state`

### B. 学習中

- **名称**: 学習中
- **定義**: `card.state === 1 || card.state === 3 || (card.state === 2 && card.stability < S_MATURE)`
- **データ源**: L1 / client
- **空状態**: A に同じ
- **備考**: Relearning(3)は stability の値によらず学習中。lapse 直後の元・定着カードはここに落ちる(N-7 の実測どおり `2→3` 遷移)

### C. 定着

- **名称**: 定着
- **定義**: `card.state === 2 && card.stability >= S_MATURE`
- **データ源**: L1 / client
- **空状態**: A に同じ
- **`S_MATURE` = 21**(単位 = 日 = `stability` の単位)。Anki の mature 慣例の借用で**暫定値**。§7 の shared 定数に置く
- **備考**: A / B / C は `state` と `stability` だけで **MECE**(全カードがちょうど 1 つに入る)。この 3 区分に「期限超過」を並べると二重計上になる(§4-D)

### D. 期限超過

- **名称**: 期限超過
- **定義(裁定要)**: `card.due < jstDayRange(todayInJst(now)).startAt` **かつ `card.state !== 0`**
- **データ源**: L1 / client
- **空状態**: A に同じ
- **`state !== 0` を条件に含める理由(R-5)**: 新規カードは `due = 作成時刻` で生成されるため、素の `due < 今日の開始` だと**昨日 OCR した 500 問が翌朝すべて「期限超過」として表示される**。これは「溜まった復習」という語の意味と一致せず、catch-up バナー(Dash-2、暫定閾値 50)も初回 upload で必ず発火する。**未学習は「まだやっていない」であって「遅れている」ではない**、という切り分けを定義に入れる。
- **境界**: `due === 今日の開始` **ちょうどは期限超過に含めない**(本日分)。厳密に `<` で比較する
- **短期ステップの扱い**: Learning / Relearning は分〜時間単位の `due` を持つため、当日中に何度も「過ぎた due」になる。**この定義では日をまたがない限り期限超過にならない**(`due < 今日の開始` なので)。すなわち本指標は overdue というより「**前日以前からの持越し**」を意味する。名称「期限超過」がこの意味とずれないか要確認(§6-③)
- **A/B/C との関係**: 期限超過は B・C と**直交**する(4 番目の区分ではない)。ウィジェット 3 の 4 カウンタは「MECE な 3 区分 + 横断 1 指標」であり、合計は総カード数にならない。UI 側でこれが誤読されない表記が要る(§6-③)
- **`due` の意味が state で一定でないことの明示**: New の `due` は「作成時刻」であって「復習期限」ではない。この定義が `state !== 0` を条件に持つのはそのため。**`due` を state 横断で同じ意味として扱う指標を作らない**
- **未確定**: `state !== 0` を含めるかは OT 裁定。含めない場合は catch-up 閾値と空状態文言の再設計が要る

### E. 間違い(集合)

- **名称**: 間違い
- **定義**: `card.answered === true && card.last_correct === false`
- **データ源**: L1 / client(`cards.last_correct`)
- **空状態**: 0 件ならクイック演習の当該ボタンを disable(非表示にはしない — 「間違いが無い」は良い情報)
- **備考**: **「直近が不正解」であって「過去に間違えたことがある」ではない**。既存カスタム演習の `answerState='incorrect'` と同一定義(`lib/cards/card-filter-predicates.ts:63-65`)。分析 doc v2 §4.1 の「最新 applied イベントが is_correct = false」と同値だが、**イベントを引かずに `cards` 1 列で判定できる**(L3 ではなく L1)

### F. 未出題

- **名称**: 未出題
- **定義**: `card.answered === false`(= A 未学習と同値)
- **データ源**: L1 / client
- **空状態**: E に同じ
- **備考**: 既存カスタム演習の `answerState='unanswered'` と同一。クイック演習の「未出題」母集合。**「未学習」と同じ集合を指すが UI 文脈が違う**(状態サマリでは「未学習」、演習ボタンでは「未出題」)。名称を分けたまま定義は 1 つにする

### G. 連続正解数

- **名称**: 連続正解数
- **定義**: `card.current_streak`(直近の連続 `is_correct === true` 回数。1 回でも不正解で 0 リセット)
- **データ源**: L1 / client
- **備考**: 既存カスタム演習の `matchesStreakFilter` が消費する列。Home v1 では直接表示しないが、苦手カード定義の候補材料として定義しておく

### H. 苦手カード

- **名称**: 苦手
- **定義(裁定要 — 2 案)**:
  - **案 1(L1・client 完結)**: `card.lapses >= 2 && !定着(C)`
  - **案 2(L3・server 集計)**: 当該カードの applied イベントのうち `is_correct === false` の**累計件数** ≥ 2 かつ `!定着(C)`
- **データ源**: 案 1 = L1 / client、案 2 = L3 / server
- **空状態**: 該当 0 件ならクイック演習「苦手」を disable
- **論点(N-7 / R-2)**: 分析 doc v2 §4.1 は「累計不正解 ≥ 2 かつ非・定着。cards に lapses があればそれを優先」としているが、**`lapses` と「累計不正解」は別物**であることが実測で確定した。
  - `lapses` は **state = Review を Again で評価したときだけ** +1。学習中に何度間違えても増えない。意味は「**定着してから忘れた回数**」= leech の原義に近い
  - 「累計不正解」は `is_correct` 由来で、学習中の誤答も数える。意味は「**通算で何回間違えたか**」
  - さらに FSRS モードでは rating と is_correct が乖離する(R-2)ため、両者はモード依存で一致しない
  - **案 1 の利点**: client 完結・即時・オフライン可・追加 endpoint 不要。**欠点**: 学習中に苦戦しているカードを拾わない(state が Review に到達しないと永遠に lapses 0)
  - **案 2 の利点**: 直感どおり。**欠点**: L3 endpoint 必須・オフライン不可・OCR 直後の大量カードで集計コスト
  - **推奨 = 案 1**(v1)。理由: 7 ウィジェットのうち苦手は「クイック演習の母集合」であり、**L1 に置ければウィジェット 5 全体が client 完結**になる(ウィジェット 4 の苦手タグだけが L3 に残る)。「学習中の苦戦」は 案 2 を Dash-3 の分析ページで別語(「通算不正解数」)として足せばよく、v1 で両立させる必要がない
- **未確定**: 案の選択と、選んだ場合の閾値 2 の妥当性(実データ較正は §2.4 の制約により未実施)

### I. カバー率

- **名称**: 着手率
- **定義**: `count(card.state !== 0) / count(全カード)`(§3.3 のスコープ内)
- **データ源**: L1 / client
- **空状態**: 分母 0 → 非表示
- **備考**: R-10 により `answered === true` の比率と同値。**Home v1 の 7 ウィジェットには含まれない**(分析ページ B 節向け)。定義だけ凍結する。名称は「カバー率」より「着手率」が UI 語として明確 — **裁定要(軽微)**

### J. 定着率

- **名称**: 定着率
- **定義**: `count(定着(C)) / count(全カード)`
- **データ源**: L1 / client
- **空状態**: 分母 0 → 非表示
- **備考**: I と同じく Home v1 非搭載。分母は総数(部分分母にしない)

### K. 初見正答率

- **名称**: 初見正答率
- **定義**: 対象カード集合の各カードについて、applied イベントを `answered_at` 昇順に並べた**最初の 1 件**を取り、その `is_correct === true` の比率
- **データ源**: L3 / server(`answer_events`)
- **空状態**: 対象イベント数が閾値未満なら非表示(§3.7)
- **備考**: MCQ の当て推量下駄(4 択で 25%)がここに乗る。**「素材の難易度シグナル」であって学習成果ではない** — UI 文言で成果と読ませない
- **同時刻の扱い**: `answered_at` が同値のときは順序が一意に定まらない。**`answered_at` 昇順 + `event_id` 昇順**の 2 段で決定的にする(§7 の shared 規則)。`event_id` は UUIDv4 なので**実際の回答順を表さない** — これは「再現性のある一意化」であって「真の順序の復元」ではない。同時刻 event が初見判定を分ける確率は無視できるほど小さいため受容する
- **履歴完全性の前提(§3.11)**: 「最初の applied」は `answer_events` が当該カードの**生涯全履歴を持つ**ことを前提にする。この前提が崩れる経路は §3.11 に集約した

### L. 復習正答率

- **名称**: 復習正答率
- **定義(近似・v1)**: 対象カード集合の applied イベントのうち、各カードの**最初の 1 件を除いた**すべてについて `is_correct === true` の比率
- **定義(厳密・R0 蓄積以降)**: `review_logs.state_before === 2`(Review)であるイベントに限定した `is_correct === true` の比率
- **データ源**: 近似 = L3 / server(`answer_events`)、厳密 = L4 / server(`review_logs` ⋈ `answer_events`)
- **空状態**: K に同じ
- **近似版と厳密版は別指標として扱う(同じ表示名で切り替えない)**:

  | | 近似版 | 厳密版 |
  |---|---|---|
  | 判定条件 | 各カードの 2 件目以降 | `review_logs.state_before === 2` |
  | 対象期間 | 全期間 | **`review_logs` 蓄積開始以降のみ** |
  | v1 の用途 | **W4(苦手タグ)が使う** | v1 では使わない |
  | 差 | Learning / Relearning 中の再回答を含む | Review 状態の回答だけ |

  - **厳密版が使えるのは `review_logs` 蓄積開始以降のイベントのみ**。それ以前の履歴には `state_before` が無く、遡及もできない(R0 spec §1「今日記録しないものは永久欠損」の裏返し)
  - **同じ「復習正答率」という名前で v1 → v2 に差し替えると、同じ履歴から数値が不連続に変わる**。切り替える場合は名称を分ける(例: 「復習正答率」/「実測保持率」)か、適用期間を併記する。**どちらにするかは Dash-3 の裁定**(v1 は近似版のみなので判断を先送りできる)
- **備考**:
  - `is_correct` 側で定義するので、FSRS モードでも意味が一定(R-2)
  - 厳密版は `review_logs` に読み取り index が無い(PK のみ・R0 spec §3.2 が意図的にそうしている)。**index 追加は最初の消費者の spec で行う**という R0 の申し送りが Dash-3 に係る(§6-⑩)
  - **最小標本**: 分母が閾値未満のとき値を出さない。閾値は消費側(§4-P)が定める — 単体で表示する用途は v1 に無い

### M. 平均保持率(R)

- **名称**: 定着度
- **定義**: 母集合を **`state !== 0` のカードに限定**し、各カードについて `R = forgetting_curve(default_w, max(floor((now - last_review) / 1日), 0), stability)` を求めた**算術平均**
- **データ源**: L1 / client(ts-fsrs)
- **空状態**: 母集合 0 → 非表示
- **必須の例外規定(N-2 / N-3 / N-4)**:
  - **`state === 0` を必ず除外する**。含めると R = 0 が混入して平均が崩れる
  - **`last_review === null` を別途除外する**。`state !== 0` のフィルタは null 判定を含まないので**これだけでは throw を防げない**(state = 2 かつ last_review = null の行は state フィルタを通過して `date_diff` で throw する)。母集合は `state !== 0 && last_review !== null` の**論理積**で定義する
  - 上記の 2 条件目に該当する行は**構造的に存在しない**(`replay-card.ts:94` が `lastReview: next.last_review ?? now` で必ず埋める)。したがって除外は防御ではなく**不変条件違反の検出点**であり、除外件数が 0 でないことを検知したら loud に扱う(集計を静かに続けない)
  - 経過日数は整数日切り捨てのため、**当日復習したカードは R = 1.00 に張り付く**。R を「今日の進捗」の指標に使わない
- **実装上の推奨(N-6 / N-8)**: `FSRS` クラスではなく公開関数 `forgetting_curve(default_w, t, S)` を使う。インスタンス `get_retrievability` と数値が完全一致することを確認済み。厳密一致のため `stability` は `+stability.toFixed(8)` を通す(`get_retrievability` の内部処理に合わせる)。**ただし「bundle が小さくなる」は tree-shaking の結果に依存する主張であり、実測はビルド後に確認すること**(本 doc は一致の実証までしか担保しない)
- **パラメタ変更時の扱い**: R は評価時の `default_w` で計算する。将来パラメタが変わると、**同じ `stability` から出る R が過去に遡って変わる**。R を時系列で比較する指標(推移グラフ等)を作る場合はパラメタ版を添える — v1 は R を時系列表示しないため問題にならない
- **UI 表記(§1.1 の正直さ原則)**: 「R」「retrievability」の生語を出さず**「定着度」**に翻訳する。生値は分析ページの折りたたみのみ
- **備考**: **Home v1 の 7 ウィジェットには含まれない**。ウィジェット 6(今後 7 日)が due ベースであり、R はその背後の量。定義だけ凍結する
- **目標保持率**: `request_retention = 0.9`(N-5)を基準線として参照できる。**設定値であって成果目標ではない**

### N. 推定所要時間

- **名称**: 約◯分
- **定義**: `1 問あたり所要 × 残問数`。`1 問あたり所要` は次で一意に定める。
  1. **標本**: ローカル `answer_events` のうち自 owner(`user_id` 一致)かつ `elapsed_ms` が存在する行を**新しい順**に走査し、有効化条件を満たすものを先頭から最大 **100 件**取る。「新しい順」の順序キーは **`local_id` 降順**とする — `local_id` は Dexie の auto-increment 主キーで、`recordAnswerEvent` が回答確定ごとに即 add する(debounce なし)ため**挿入順 = 回答順で単調**であり、`answered_at` 降順と実質同値。かつ `answered_at` に index が無いのに対し主キー逆走査は index が効く
  2. **有効化条件**: `0 < elapsed_ms <= 120,000`。**120,000 を超える行は標本から除外する(clamp ではない)**。`elapsed_ms === 0` も除外する(計測不能の縮退値であり実測 0ms ではない)
  3. **中央値**: 標本を昇順に並べ、件数が奇数なら中央の 1 件、**偶数なら中央 2 件の算術平均**
  4. **既定値**: 有効標本が **0 件のときのみ** `20,000ms`。1 件以上あれば件数によらず中央値を使う
  5. **スコープ**: **選択中の試験に絞らない**(user 全体のローカル履歴)。試験ごとに標本を割ると新しい試験で常に既定値になり、推定が悪化するため
  6. **`applied` は問わない**。ローカル `answer_events` に `applied` は無く(server 側の列)、体感所要時間は適用可否と無関係
- **データ源**: L2 / client(ローカル `answer_events`)
- **空状態**: 有効標本 0 でも既定値 20s/問で表示する(この指標は非表示にしない — 「何分かかるか」は CTA の一部)
- **備考(R-8)**:
  - **`elapsed_ms` は端末ローカルにしか無い**(answer_events に下り pull が無い)。したがって**端末を変えると「約◯分」が変わり、新しい端末では既定値 20s から始まる**。これは受容する(表示は「約」で分に丸めるため実害が小さい)。server 集計に寄せる判断は Dash-1/Dash-3 へ
  - 120s の上限は**この指標の標本条件**であり、wire schema の上限(`elapsed_ms ≤ 86,400,000` = 24h・`lib/sync/shared/answer-event-schema.ts:20`)とは別物。両方を混同しない
  - `elapsed_ms` は card 表示 → submit の wall-clock で、**タブ非表示時間を含む**。中央値 + 120s 除外はそのノイズ対策
  - ローカル `answer_events` は無限成長する(R-8)。**全件走査せず、`answered_at` 降順で 100 件に達した時点で打ち切る**
  - 表示は §3.10(分に切り上げ・最小 1 分)

### O. 連続日数(streak)

- **名称**: 連続日数
- **定義**: `study_days` のうち `review_count > 0` の day 集合について、今日(JST)から遡って連続する日数。**今日の行が無ければ昨日を起点にフォールバック**する
- **データ源**: L2 / client(Dexie `study_days` mirror・window 61 日)
- **空状態**: 0 日なら表示するが**最下段の脇役に置く**(§1.1 原則 4「activity を state より上位に置かない」)
- **上限 61 日(実装由来の切断)**: window が today + 過去 60 日 = 61 日なので、**実際に 62 日以上続いていても 61 で頭打ちになる**(`lib/client/streak.ts:20` の `STREAK_WINDOW_DAYS = 61`)。値が 61 のとき「61 日」と断定表示すると誤り。**61 に達したら「61 日以上」と表記する**か、window を広げる。v1 は前者(表記で解決・実装変更なし)
- **備考**: 既存 `lib/streak-core.ts:computeStreak` の 1 定義を server/client 双方が import 済み。**新規定義を作らずこれを正とする**。R-3 により **user 全体**(試験別ではない)

### P. 苦手タグ

- **名称**: 優先して復習
- **定義**: 対象スコープのタグ(= `tag_options` の 1 行)のうち候補条件を満たすものを、**復習正答率(L・近似版)の昇順**で並べた上位 3 件。
  - **候補条件(両方を満たす)**:
    1. `対象カード数 >= 8` — 「対象カード」= **選択中の試験に属し、そのタグが現在付いているカード**(§3.5 / §3.3a)
    2. `直近 30 日の復習イベント数 >= 15` — **全 applied イベントではなく、復習正答率(L)の分母に入るイベント(= 各カードの 2 件目以降)に限る**。初見だけ大量にあるタグをランキングに乗せないため
  - **順位に使う復習正答率の期間 = 直近 30 日**(候補条件と同じ窓。全期間にすると「候補は直近・順位は過去」というねじれが出る)
- **データ源**: L3 / server(`answer_events` ⋈ `card_tags` ⋈ `cards`)
- **空状態**: 候補 0 件 → **ウィジェットごと非表示**(「苦手なタグはありません」も出さない — 閾値未満は判定していないだけで「苦手が無い」ではない)。取得失敗・陳腐は §3.8 で空と区別する
- **数え方の一意化**:
  - **複数タグが付いたカードは、各タグに重複算入する**(タグごとに独立した集計。合計が総イベント数を超えるのは正常)
  - **同一カードへの複数回答はすべて分母に入る**(カード単位に畳まない)
  - **「対象問数」はカード数、正答率の分母はイベント数**で単位が違う。UI で同じ行に並べる際は単位が読み取れる表記にする(Dash-1)
  - **カテゴリをまたぐ同名タグは別タグとして扱う**(`tag_options` の行が別なら別)。表示はカテゴリ名を添えて区別する
- **同率順位**: 復習正答率が同値のときは `対象カード数` 降順 → `tag_options.id` 昇順で決定的にする(`sort_key` は nullable のため順序キーに使わない)
- **備考**:
  - 閾値 8 / 15 は**ノイズ回避のための暫定値**(2 問しかないタグの 0% を拾わないため)。§3.12 により定義とは分けて扱う
  - **復習正答率(L)を使う**。初見正答率(K)は素材難易度が混ざるため使わない
  - タグは user 単位のマスタで exam に属さない(fact-finding §6)。**選択中の試験のカードに付いたタグ**に絞って集計する
  - 「30 日」の日界は §3.1 に従う(`todayInJst` 起点で 30 日)

### Q. 週の集計

- **名称**: 今週
- **定義**: `study_days` のうち今週に属する day について、`回答数 = sum(review_count)` / `学習日数 = count(review_count > 0)`。**週の起点は月曜 00:00 JST**(裁定要)
- **データ源**: L2 / client(90 日 mirror で足りる)
- **空状態**: 今週の行が 0 件 → 「0 問」を表示してよい(意味のある 0)
- **先週比 delta**: `今週の回答数 − 先週の回答数`。**先週の行が 1 件も無い場合は delta を出さない**
  - **判別できないことの明示**: `study_days` は**イベントがあった day にしか行を作らない**(`recomputeStudyDays` は applied event 由来の day 集合だけを再集計する)。したがって「先週の行が 0 件」は「先週 1 問も解かなかった」と「先週はまだ利用していなかった」を**区別できない**。区別するにはアカウント作成日等の別情報が要る。v1 は区別せず**どちらも delta 非表示**にする(誤った `-124` を出すより無表示が安全)
  - **比較バイアスの明示**: 「進行中の今週」と「完了した先週」を比べるため、**週の前半は構造的にマイナスに寄る**。v1 はこれを受容し、UI 文言で「先週(同時点比ではない)」と誤読されない表記にする。同曜日・同時刻までの比較に変えるかは Dash-1(§6-⑦)
- **備考(R-3)**: user 全体。試験別ではない
- **`review_count` の意味**: 行数であり distinct card 数ではない。**同一カードを 1 セッション内で複数回 submit すると複数回進む**(fact-finding §4)。「回答数」という名称はこの意味と一致している

### R. 今日の学習量

- **名称**: 今日の学習問題数(現行ラベル・R-12)
- **定義**: `study_days` の今日(JST)行の `distinct_card_count`(= その日 1 回でも回答した unique card 数)
- **データ源**: L2 / client
- **空状態**: 行不在 → 0
- **備考**: 現行実装(`lib/client/streak.ts:getStreakStatsFromDexie`)と同一。**`review_count` ではなく `distinct_card_count`** を使うため、同一カードの複数回 submit で膨らまない。R-3 により user 全体

## 5. ウィジェット別 指標定義

分析 doc v2 §5.1 の 7 ウィジェット。各ウィジェットが消費する指標は §4 の語彙を参照する(再定義しない)。

### W1. ヘッダ

| 項目 | 内容 |
|---|---|
| 表示 | 試験名(切替)+ 試験日設定済なら「あと◯日」 |
| 指標 | **あと◯日** = `exam_date`(JST の暦日)と `todayInJst(now)` の**暦日差**。試験日当日は **「今日」**(「あと 0 日」と書かない)。過去日は「あと◯日」を出さない |
| データ源 | **現状実現不能**。`exams.exam_date` は現 schema に存在せず(exams は 6 列のみ・fact-finding §6)、Dash-2 で追加される前提の**前方参照**。**Dash-1 時点では常に未設定として扱い、この行を描画しない** |
| 空状態 | `exam_date` 未設定 → 「あと◯日」を出さない(ヘッダは試験名のみ) |
| 未確定 | 列の型(`date` か `timestamptz` か)と過去日の表示は **Dash-2**。**「選択中の試験」の持ち方も未実装**(R-11 / §6-②)。試験が 0 件・削除された・複数タブで別試験を開いた場合の挙動も §6-② に含む |

### W2. 今日の学習(主役・唯一の primary CTA)

| 項目 | 内容 |
|---|---|
| 表示 | 「◯問・約◯分」/ 進捗バー x/y / 内訳「復習 n(超過 m 含む)・新規 k」 |
| **y(今日の目標)** | `y = n + k` |
| **n(復習)** | `count(card.state !== 0 && card.due < jstDayRange(todayInJst(now)).endAt)`(L1 / client) |
| **m(超過)** | `count(期限超過(D))`(L1 / client)。**n の内数**(D の定義が `state !== 0` を含むため n ⊇ m が構造的に成立) |
| **k(新規)** | 新規/日 の parameter 値と `count(未学習(A))` の**小さい方**。**parameter の値と実装は未確定**(§6-⑥) |
| **x(進捗)** | **今日の学習量(R)**(L2 / client)。ただし R は user 全体・distinct card 数(R-3) |
| 所要時間 | **推定所要時間(N)** に `残問数 = max(y - x, 0)` を与える |
| データ源 | L1 + L2 |
| 空状態 | `y === 0` → §3.7「今日分完了」 |

**n を `due <= now` ではなく「今日の終わりまで」で切る理由**: `due <= now` にすると **y が時間経過だけで増える**(朝に 12 問だった目標が夕方に 18 問になる)。「今日やる量」の処方としては日単位で確定していなければならないため、**当日中に due になるカードは朝の時点で y に含める**。これは現行スマート復習の選定条件(`due <= now`)とは**意図的に異なる** — 処方(表示)と出題(実行)で切り方が違うことになる。

**未確定(W2 は本 doc で最も穴が多い)**:

| | 内容 |
|---|---|
| a | **x と y の母集合が一致しない**。y は選択中の試験の L1、x は user 全体の L2(R-3)。**他試験を解くだけで進捗バーが進み、`y - x` が負にもなる**。`max(..., 0)` の clamp は表示を壊さないだけで不整合を解消しない — **他試験の回答だけで「今日は完了」と表示されうる**。§6-① の裁定に従属する |
| b | **CTA が y と同じ集合を出題しない**。スマート復習の選定は `due <= now` の 1 本のみで state 除外も新規上限も無く(`lib/cards/get-dexie-session-cards.ts:25-45`)、新規カードは生成時点で即 due(R-5)。したがって CTA を押すと `k` を無視して未学習カードが全部プールに入る。**y の表示と実際の出題が一致するには新規/日の制御弁が要る**(§6-⑥) |
| c | **y を固定するか毎回計算するか**。毎回計算だと、回答して due が未来に飛ぶ / 日中に OCR でカードが増える / 試験を切り替える、のいずれでも分母が動く。固定するなら「今日の計画集合」をどこかに保存する必要がある(現状そのような保存先は無い)。**v1 は毎回計算**とし、分母が動くことを受容する。ただしこれは (d) と連動する |
| d | **「今日分完了」の判定**。`y === 0` では「やり切った」と「最初から 0 件だった」を区別できず、(a) の母集合不一致下では誤判定もする。**判定条件の確定は Dash-1**(§6-⑧) |
| e | **「明日は約◯問」**(空状態文言・§3.7)の定義が無い。当日の回答で明日の due は変わるため、**「今日の残りを全部やった後の確定値」なのか「現時点の見込み」なのか**で意味が違う。Dash-1 |

**選出規則(母集合だけでは一意にならないので定める)**:

- **既定件数 = 10**(「間違い10 / 未出題10 / 苦手10」)。母集合が 10 件未満ならその全件
- **並び順 = `due` 昇順**。既存スマート復習の並び(due ASC・shuffle なし)に合わせる(簡潔性規律「既存パターンに乗る」)。同値は `cards.id` 昇順で決定的にする
- **10分プリセットの件数は最低 1**(`floor` だけだと 1 問 10 分超の利用者で 0 問になる)
- **`user_settings` の cap との関係**: プリセット件数が cap を超える場合は **cap を優先**する(cap は user の明示設定であり、プリセットの既定値より強い)
- **カードが複数プリセットに属することは許容**(排他にしない。「間違い」かつ「苦手」は普通に起こる)

**未確定**: **件数を渡す仕組みが現状に無い**(R-7: 件数指定 UI 不在・cap のみ)。**deep link も不可**(R-6: カスタム演習が `searchParams` を読まない)。母集合と件数の受け渡し方は Dash-1(§6-④)。オフライン時に苦手を案 2(L3)にした場合の degrade も同時に決める。

### W6. 今後 7 日

| 項目 | 内容 |
|---|---|
| 表示 | due 件数のミニバー 7 本 |
| 指標 | 日 `d`(今日を含む 7 日)ごとに **`count(card.state !== 0 && jstDayRange(d).startAt <= card.due < jstDayRange(d).endAt)`**。ただし **今日のバーだけは `count(card.state !== 0 && card.due < jstDayRange(today).endAt)`**(= 期限超過(D)を今日に合算する) |
| データ源 | L1 / client |
| 空状態 | 全 7 日が 0 → ウィジェットごと非表示 |

**New を除外する(`state !== 0`)理由**: 除外しないと**全未学習カードが「今日」のバーに入り、他の 6 日が見えなくなる**(R-5: 新規カードは生成時点で即 due)。W2 の n・W3 の期限超過(D)と**同じ `state !== 0` の分類規則を共有する**。

**期限超過を今日に合算する理由**: 合算しないと過去日の due がどのバーにも入らず、7 本の合計が「今後やるべき量」と一致しない。また **今日のバー = W2 の n と一致する**ようにも揃う。**超過分を今日のバー内で視覚的に区別するかは UI 判断(Dash-1)** だが、**集計上は合算で確定**する。

### 7.2 pin(分析 doc v2 の指定を具体化)

- **client / server 同一分類 pin**: fixture カード集合 → 3 区分の分類が client 経路と server 経路で一致(iso)。**「同じ関数を import する」だけでは足りない** — Dexie(ISO 文字列)と PostgreSQL(timestamptz / double precision)で値の復元経路が違うため、**両側の実データ型から入力を組み立てて一致を確認する**
- **fixture events → 期待集計値 pin を最低 3 本**(分析 doc v2 の指定):
  1. **タグ別**(§4-P の閾値境界を含む — 対象カード 7/8、復習イベント 14/15 の両側)
  2. **初見 / 復習別**(§4-K/L。同時刻イベントの決定性を含む)
  3. **日界跨ぎ**(JST 00:00 の前後 1 分のイベントが別 day に入る)
- **本 doc 由来で追加すべき pin**:
  4. **未学習カードが期限超過に入らない**(§4-D。R-5 の再発防止 — `due = 作成時刻` の新規カードを翌日評価して 0 件)
  5. **未学習カードが今後 7 日の「今日」バーを支配しない**(W6。同上)
  6. **平均保持率の母集合から state=0 が除外される**(§4-M。N-2 の再発防止 — state=0 を 1 件混ぜても平均が変わらない)
  7. **`state !== 0 && last_review === null` の行が母集合から落ち、throw しない**(§4-M。N-3 の再発防止。state フィルタ単独では防げないことの実証)
  8. **`forgetting_curve(default_w, t, S)` が `get_retrievability(card, now, false)` と一致**(N-6。ts-fsrs bump で壊れたら loud に落とす)
  9. **FSRS モードで `rating` と `is_correct` が乖離した event**(R-2)。正答率が `is_correct` 側、lapses が `rating` 側に載ることの実証
  10. **`lapses` が Learning での Again で増えない**(N-7。§4-H 案 1 を採る場合、これが「苦手」の意味そのもの)
  11. **境界値**: `elapsed_ms` が 0 / 120,000 ちょうど / 120,001、標本が偶数件、標本 0 件(既定値へ落ちる)
  12. **streak が 61 で頭打ちになる**(§4-O。62 日連続の fixture で 61 が返り、表記が「61 日以上」になる)
  13. **カード削除後の非対称**(§3.3a。削除で L3 は変わり L2 は変わらない)

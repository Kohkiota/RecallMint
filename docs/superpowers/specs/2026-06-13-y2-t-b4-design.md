## 1. 目的とスコープ

### 1.1 目的

1. `/app/exams` 初期表示の dominant cost (T-B1 計測 ~3,655 ms = 96.7%) を解消、 launch 前 hardening の体感遅延を圧縮する。
2. 真因 = exam-list-live.tsx の `db.cards.where('user_id').toArray()` で user 全 cards (~2k 件以上) を JS object 化 (nested field 含む) する materialization コストを構造的に回避する。
3. owner isolation (test #6) を index 構造で担保し、 client 側防御層を撤去しない (perf のためにセキュリティガードを削らない)。

### 1.2 前提変更 (plan T-B4 の制約見直し)

旧 plan 制約「Dexie index は既存 (新規 migration 不要)」 は本 spec で見直す。 理由:

1. **archive 軸が運用上機能してない** (Step 0 事実確認結果):
   - `exams.archivedAt` 列は schema 上存在 (`lib/db/schema.ts:245`)、 read 側は完備 (exam-list-live filter / 詳細 page バッジ / upload 投入拒否 / pull mirror)
   - しかし archived_at を SET する write 経路が存在しない (delete-exam は物理 DELETE + FK CASCADE、 `app/(app)/app/exams/_actions/delete-exam.ts:48-90`)
   - → 本番 DB の archived_at IS NOT NULL exam は 0 件、 `anyOf(activeExamIds)` で archived 除外する subset 化は **効果ゼロ**

2. **真因は row 件数ではなく materialization コスト**:
   - cards 2023 件の `toArray()` で images / options / correct_answer_ids 等 nested field を JS object 化するコストが dominant
   - row 件数の削減軸 (active/archived 区別) が存在しない以上、 materialize の構造的回避が唯一効く手

3. **migration 制約解除の前提**:
   - ユーザー 0、 stg/prod DB はいつでも破棄可能 (OT 確認済)
   - 過去 migration v2 〜 v5 と同形の純粋 index 追加で既存データ保持
   - → 本 sprint 内で Dexie v6 を追加して最も効果的な fix を採る

### 1.3 スコープ

- Dexie v6 schema 追加: `cards` table に compound index `[user_id+exam_id]` 追加 (`lib/client-db.ts`)
- exam-list-live.tsx の useLiveQuery 内 query 経路を per-exam `where('[user_id+exam_id]').equals([userId, examId]).count()` の Promise.all 並列に置換
- 既存 test 6 件全 pass + per-exam count() 経路 regression test 1 件追加 (`materialize ゼロ` / `count() 呼出回数 = N_exams` を assert)
- Y-2 Sub-plan B T-B4 plan の制約 + 完了条件を本 spec の方針に書き換え (writing-plans で反映)

### 1.4 スコープ外 (明示)

| 項目 | 受け入れ先 |
|---|---|
| server 側 (Drizzle/Postgres) per-exam 集計 SQL の最適化 | **対象なし** (Step 0 確認結果: `getActiveExamsWithCardCount` は exam-list-live 切替で撤去済、 `/app/exams` 表示 path に server 集計 SELECT は存在しない) |

## 2. アーキテクチャ

### 2.1 全体構造

```
RSC (page.tsx) ──→ ExamListLive (client component)
                       │
                       ▼
                  useLiveQuery
                       │
                       ├─ db.exams.where('user_id').equals(userId).toArray()  (旧経路維持)
                       │      │
                       │      ▼
                       │   archived フィルタ + updated_at DESC sort
                       │      │
                       │      ▼
                       │   activeExams
                       │
                       └─ Promise.all(activeExams.map(e =>
                              db.cards
                                .where('[user_id+exam_id]')
                                .equals([userId, e.id])
                                .count()
                          ))
                              │
                              ▼
                          counts: number[]
                              │
                              ▼
                          countByExam: Map<string, number>
                              │
                              ▼
                          活性 exam rows + cardCount を return
```

旧経路 (`db.cards.where('user_id').toArray()`) を完全撤去。 cards mirror への subscription 契約は `where('[user_id+exam_id]')` 経由でも維持される (Dexie useLiveQuery は触った table を subscribe するため、 server pull で cards が書き換わったら自動再描画される)。

### 2.2 Dexie schema migration (v6)

`lib/client-db.ts` に v6 を追加:

```typescript
this.version(6).stores({
  cards:
    'id, exam_id, user_id, due, updated_at, content_version, sync_status, [user_id+exam_id]',
})
```

- 過去 v2 / v4 / v5 と同形の純粋 index 追加 (store drop なし、 既存データ保持)
- 単独 index (`exam_id` / `user_id` / `due` 等) は維持 (他 path で使われている)
- compound index `[user_id+exam_id]` を追加するだけ

### 2.3 owner isolation の構造的保証

旧経路:
```typescript
db.cards.where('user_id').equals(userId).toArray()
// → user 全 cards を materialize → JS で countByExam Map
// owner isolation は client filter (test #6 防御層)
```

新経路:
```typescript
db.cards.where('[user_id+exam_id]').equals([userId, examId]).count()
// → compound index 第 1 要素 (userId) が equals fix → 他 user の cards に index 経路で構造的に到達不能
// owner isolation は index 構造で担保 (防御層強化、 JS filter 不要)
```

これにより test #6 の防御層を **撤去せず構造的に強化**する。

### 2.4 materialize 回避の確証 (Dexie source 確認結果)

- `Collection.count()` (`dist/dexie.js:2108-2132`) は `isPlainKeyRange(ctx, true)` true なら native `coreTable.count({range})` に直送
- `coreTable.count` (`dist/dexie.js:3629-3642`) は native `IDBIndex.count(IDBKeyRange)` を呼ぶ → B-tree 範囲 count、 row 本体 fetch なし
- `.equals([userId, examId])` は filter 不要なため `isPlainKeyRange` true → native path に直送 → **row materialize 0 達成**

### 2.5 候補 (a) (1 query + cursor 集計) との比較

| 観点 | 候補 (a) 1 query + cursor | 候補 (b) per-exam count() N 並列 (本命) |
|---|---|---|
| 経路 | `where('[user_id+exam_id]').between([U,MIN],[U,MAX]).keys()` → JS Map | `Promise.all(exams.map(e => where('[user_id+exam_id]').equals([U, e.id]).count()))` |
| row materialize | 0 (`.keys()` は values:false cursor) | 0 (`IDBIndex.count(range)` native) |
| IDB request 数 | 1 | N_exams |
| IDB cost / request | cursor iteration × N_cards | B-tree range count × 1 |
| array allocation | keys N_cards × [string, string] | counts N_exams × number |
| owner isolation | index 構造で担保 | index 構造で担保 |
| code 複雑度 | 中 (cursor + Map fold + 型 cast) | 低 (Promise.all map) |
| 想定運用 (N_exams ≤ 数十) での優位 | N_cards 線形 cursor advance | μs オーダー native count × 少数並列 |

本命 = **候補 (b)**。 ただし 100 exam 規模になった場合に逆転する余地はあるため、 plan の完了条件に「stg 実機 fixture (exam 数増加 seed) で実測比較」 を入れて (a) への切替余地を残す。

## 3. データフロー

### 3.1 mount 時

1. RSC が `getAuthContext` で userId を取得し ExamListLive にプロパティで渡す
2. ExamListLive mount → useLiveQuery が undefined を 1 回返す → skeleton 表示
3. useLiveQuery 内非同期処理:
   1. `db.exams.where('user_id').equals(userId).toArray()` で user の exams 全件取得 (件数少、 軽い)
   2. JS で `archived_at == null` filter + `updated_at` DESC sort → `activeExams`
   3. `Promise.all(activeExams.map(e => db.cards.where('[user_id+exam_id]').equals([userId, e.id]).count()))` で並列発火 → counts: number[]
   4. `Map<string, number>` 構築 → 各 active exam の cardCount を解決 → 表示用配列を return
4. useLiveQuery が解決 → list 表示

### 3.2 cards mirror 変更時 (server pull 反映)

- Dexie の useLiveQuery は触った table (`exams` + `cards`) を subscribe する
- server pull で cards に書込が走ると `cards` table change が dispatch される → useLiveQuery callback が再実行 → 新しい counts で再描画
- subset 化前後で subscription 契約は不変 (cards table を触っている事実は変わらないため)

### 3.3 optimistic mutation 時 (client 側 card create/delete)

- 既存 path: card mutation を Dexie cards mirror に直接反映 → entity_mutations outbox に積む → server 確定で sync_status='synced'
- exam-list-live は cards mirror を読むため、 optimistic 反映が即時 list に出る (旧経路と同じ挙動)
- per-exam count() でも反映タイミング不変 (cards table 変更が useLiveQuery を trigger するため)

## 4. エラーハンドリング

### 4.1 Dexie migration 失敗

- v5 → v6 は純粋 index 追加 (store schema は既存維持 + index 追加のみ)
- 既存データ保持 (v3 のような store drop なし)
- Dexie 内部 `upgrade` callback 不要 (index 追加のみのため自動 reindex で完結)
- 万一失敗時は IDB が v5 で残存 → 旧経路の query が一致しない → useLiveQuery が throw → React error boundary に到達 (既存挙動)

### 4.2 Promise.all 内の reject

- 1 つの `count()` が reject した場合 `Promise.all` 全体が reject → useLiveQuery callback 全体が throw → React error boundary
- 個別 fallback は不要 (試験単位で count() が reject するシナリオは Dexie の内部エラー = 全体異常)
- 旧経路の `toArray()` reject と同じ挙動を維持

### 4.3 empty examIds の Promise.all

- activeExams が 0 件 → `Promise.all([])` = 即解決 `[]` → 既存「空状態 CTA」 path に到達 (exam-list-live.tsx:68-85)

## 7. risk + 確認事項

1. **Dexie の index hot-reindex 挙動**: v5 → v6 migration 時に既存 cards 2000 件以上を reindex する負荷が IDB 上で発生する。 user の最初の page load で 1 回だけ発生、 fixture 計測 + stg smoke で確認。
2. **Promise.all の同一 transaction 制約**: useLiveQuery callback は単一 transaction context 内で動く想定。 Promise.all で並列発火しても IDB 上は逐次化される可能性あり (実装依存)。 native count() ならば逐次でも μs オーダーで実害なし。 実測で確認。
3. **exam 数が三桁規模になった場合の逆転**: 100 exam 規模では (a) cursor 経路の方が round trip 数で有利になる可能性。 plan の完了条件に「stg 実機 fixture で実測比較」 を入れて (a) 切替余地を残す。

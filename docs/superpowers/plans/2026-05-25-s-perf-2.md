## Task 2: click → skeleton 表示遅延の切り分け (実装なし、 計測のみ)

**目的:** S-perf-1 で観測した click → URL 変更 + skeleton 表示の 1.3〜1.8 秒が、
以下のどれに由来するかを実測で切る:
- (a) server SSR 待ち (RSC fetch + getCurrentUser + page 固有 SELECT)
- (b) layout (`/app/(app)/app/layout.tsx`) の再 evaluate (`getCurrentUser` + redirect 判定)
- (c) client transition 機構 (React 18+ `startTransition`、 next router の suspense 解決)
- (d) Next.js の chunk lazy load (route group `(app)` 配下の lazy chunk)

**対象遷移:**
- `/app` → `/app/exams`
- `/app` → `/app/settings`
- `/app` → `/app/study/smart`
- `/app` → `/app/upload`

**計測時系列:**
1. click 時刻 (`t0`)
2. URL 変更時刻 (`location.pathname` 変化を 30 ms 間隔で polling、 厳密ではないが
   実測に耐える)
3. loading skeleton 表示時刻 (`[aria-label="読み込み中"]` / `[role="status"]`
   MutationObserver で検知 — S-perf-1 の `aria-label="loading"` は Minor #4 で次の
   polish に回したが、 計測 selector は両対応にする)
4. content 表示時刻 (page 固有 keyword、 ただしヘッダの link テキストと重ならない
   keyword を選ぶ。 `/app/exams` なら 「アップロード 2026-」 等 fixture 由来の文字列)

**切り分け方:**
- `[server SSR 待ち]` 仮説検証: 同じ page の direct `?_rsc=` fetch TTFB + body と
  click → skeleton の差が ±200 ms 以内なら server SSR が主因
- `[layout 再 evaluate]` 仮説検証: next.js は同 segment 内 navigation で layout を
  再 render しない仕様。 ただし `(app)` route group 内で layout が含まれる場合は
  navigation 時に再評価される可能性 — `[browser_evaluate]` で
  `performance.getEntriesByType('measure')` などから React 計測点を確認
- `[client transition]` 仮説検証: warm cache (2 回目以降 click) で時間短縮するなら
  fetch の cold 性が主因、 短縮しなければ client transition 由来
- `[chunk lazy load]` 仮説検証: 1 回目 click と 2 回目以降 click の差が大きく、
  かつ Network tab で `.js` chunk fetch が走っていれば該当

**完了条件:**
- 4 遷移 × 時系列 4 点を表形式で追記
- 切り分け結論 (a/b/c/d のどれが主因か、 もしくは複合か) を 3-5 行で記述
- T3 で検討する分離方式の選択肢を絞る

**やらないこと:**
- この task では実装変更しない

### T2 計測結果 (2026-05-25 、 stg `dfe706e` 時点、 各遷移 1 回 cold)

`/app` → 各 page click の時系列:

| 遷移 | click→URL | click→skel | click→content | Δ(URL→content) |
|---|---|---|---|---|
| 試験 | **3065** | **3065** | 3960 | 895 |
| 設定 | 1532 | 1532 | 1822 | 290 |
| スマート復習 | 1071 | 1071 | 1559 | 488 |
| アップロード | 1952 | 1952 | 2442 | 490 |

**click→URL と click→skel が完全一致** = Next.js client router は「最初の RSC chunk
が到達したら URL を更新 + Suspense fallback (loading.tsx) を render」 の構造。
つまり click→skel の遅延 = **RSC fetch start → first byte 到達まで**。

### RSC fetch / JS chunk Resource Timing 内訳

| 遷移 | fetch 開始 | fetch 完了 | ttfb | dur | 重複 fetch |
|---|---|---|---|---|---|
| 試験 | 3 ms | 3602 ms | **1671** | 3599 | あり (start=1705 で 2 本目、 dur=2251) |
| 設定 | 1 ms | 1358 ms | 884 | 1357 | あり (start=898 で 2 本目) |
| スマート復習 | 1 ms | 1141 ms | 408 | 1140 | あり (start=420 で 2 本目) |
| アップロード | 1 ms | 1162 ms | 568 | 1161 | あり (start=574 で 2 本目、 dur=1851) |

**JS chunk fetch**: 全 4 遷移で dur 2-5 ms (チャンク lazy load の影響は無視可能)。

### 切り分け結論

仮説 (a)〜(d) の判定:

- **(a) server SSR 待ち = 主因**: 全遷移で click→URL ≈ 1 本目 RSC fetch 完了時刻。
  「試験」 は ttfb 1671 ms + body streaming で 3599 ms 全体、 これが click→skel
  3065 ms の本体。 cold 時 server 並列処理が走っている可能性 (Vercel serverless
  cold start、 ttfb 1671 ms は T1 の dashboard ttfb 438 ms と乖離 → server 側の
  並列接続待ちか、 fetch の queueing と推測)
- **(b) layout 再 evaluate**: layout は同 segment 内 navigation で再 render しない
  仕様だが、 各 RSC fetch ごとに `getCurrentUser` の auth + users SELECT が走る
  (React.cache は同 RSC tree 内のみ) ことが主要 cost に効いている可能性は残る
- **(c) client transition**: アップロードのみ fetch #1 完了 1162 ms vs URL 変更
  1952 ms で **790 ms の謎の間隙** あり。 React 18 startTransition / Suspense
  解決 / RSC payload parse のオーバーヘッドの可能性。 他 3 遷移は ~0-170 ms で
  顕在化していない
- **(d) chunk lazy load = 否**: chunk fetch dur 2-5 ms で却下

**新たな発見**: 全 4 遷移で `?_rsc=` の **重複 fetch** が観測 (1 click あたり
2-3 本)。 1 本目 click 直後 + 2 本目 click 後 400-1700 ms 後追加。 これは Next.js
の client router 内部挙動 (stale data 検出 → 再 fetch、 もしくは
prefetch={false} 環境下の fallback fetch)。 1 本目の方が時間がかかる傾向
(cold)。 これは server SSR が「同 path に対して 2 回走っている」 ことを意味し、
server 負荷の 2 倍化に寄与している可能性が高い。

### T3 への影響

server SSR (a) が dominant、 chunk lazy load (d) は否。 重複 RSC fetch という
追加問題が浮上 (server 側でも click 1 回につき 2 SSR が走っている)。 T3 の分離
方式比較は以下を考慮する必要:

- 重複 fetch の原因特定 (Next.js dev / prod 動作差異、 prefetch={false} との関係)
- (a) を attack するなら dashboard 統計分離だけでなく、 重複 fetch の抑制も検討
- アップロードの 790 ms 間隙は別軸 (T4 後の T5 で再評価)

## Task 2.5: 重複 RSC fetch の原因切り分け (1 巡、 実装なし)

**目的:** T2 で観測した「1 click あたり 2-3 本の `?_rsc=` fetch」 が、 Next.js
正常挙動 / 計測ノイズなのか、 実アプリ側の二重 navigation / refresh なのかを
1 巡で確定する。

**確認項目 (要件):**
1. 各 `?_rsc=` の URL / params / initiator / startTime / dur / transferSize /
   decodedBodySize
2. 1 本目 / 2 本目が navigation fetch vs prefetch/refresh/stale 再取得 のどれか
3. `router.refresh()` / `revalidatePath` / 遷移直後の `useEffect` refresh の有無
4. `<Link>` + `router.push` の二重 navigation
5. 計測コード / `waitForText` の重複誘発

### 実機計測結果 (/app → /app/exams、 1 click)

PerformanceObserver で `?_rsc=` を生で観察:

| # | start (ms) | end (ms) | dur (ms) | transferSize | decodedBodySize | `_rsc` value |
|---|---|---|---|---|---|---|
| 1 | 2 | 2267 | 2265 | 3095 | 12633 | `1e618` |
| 2 | **417** | 2153 | 1737 | 4532 | 18694 | `tyzv0` |

- 両 fetch とも pathname=`/app/exams`、 searchKeys=`['_rsc']` のみ、
  initiatorType=`fetch`、 nextHopProtocol=`h2`
- **`_rsc` value が異なる** = 同 navigation 内の重複ではなく、 2 つの異なる
  context での RSC request
- 2 本目の decodedBodySize 18694 > 1 本目 12633 = 2 本目はより大きな RSC tree
  (revalidate 後の fresh data 全件、 1 本目は部分 tree)
- 2 本目の **start 時刻 417 ms** が、 後述する server action RTT と一致

### 要件 1〜5 判定

| # | 確認 | 結果 |
|---|---|---|
| 1 | URL/params/initiator/timing | 上記表参照、 2 本とも純 `?_rsc=...` の RSC fetch |
| 2 | navigation vs refresh | **1 本目 = navigation fetch、 2 本目 = revalidate 後の stale 再取得** |
| 3 | router.refresh / revalidate / useEffect | **app-header.tsx 全 nav + dashboard-actions.tsx に `onClick revalidateAppPath`** |
| 4 | Link + router.push の二重 | **否**。 nav Link は純 Link、 `router.push` は upload-form / delete-card-button のみで遷移文脈が別 |
| 5 | 計測コード重複誘発 | **否**。 MutationObserver / waitForText は read-only、 router を触らない |

### 結論

**Next.js の正常挙動内だが、 アプリ側が能動的に二重 navigation を発火している**。
具体的経路:
1. click → Link の navigation で fetch #1 開始 (start ~2 ms)
2. 同 click の `onClick={() => void revalidateAppPath('/app/exams')}` が server
   action 発火 (Clerk auth + getCurrentUser + revalidatePath、 RTT ~400 ms)
3. server action 完了 (~417 ms) → Next.js client router が「対象 path が stale」
   と判定 → **fetch #2 を自動発火**
4. fetch #2 は revalidate 後の fresh RSC tree を取得 (より大きな decodedBodySize)
5. fetch #2 完了後、 client router が新しい RSC を採用 (= URL 変更 + skeleton)

**= server SSR が click 1 回につき 2 回走り、 server 負荷も体感遅延も両方悪化**。

### 修正候補 (T3 着手前に検討)

- **C-1**: header / dashboard CTA の `onClick={() => void revalidateAppPath(...)}`
  を撤去 (revalidate.ts の `revalidateAppPath` server action 自体も dead code
  化、 削除候補)
- 撤去の根拠 (前回 lesson より引用):
  - 既存設計の意図は「navigation 時に最新 server state を見せる」 ための保険
  - Next.js 15 default `staleTimes.dynamic = 0` で dynamic page は client cache
    されないため、 そもそも navigation で fresh fetch される
  - `revalidateAppPath` は元々 dev 期の保険、 prod でも残っていた
- 影響:
  - server SSR 並列度 2x → 1x (click あたり)
  - click→skel の time 改善見込み: 「試験」 で 3065 → ~1700 ms (2 本目の不要
    revalidate 分を削減、 ただし 1 本目自体の TTFB ~1671 ms は変わらない)
- リスク: 「navigation 時にコンテンツが古いまま見える」 ケースが出る可能性。
  ただし staleTimes.dynamic=0 で問題ない設計 (前回 lesson §3.3 でも撤回可と
  判定済)。 server action や client mutation 経由の revalidatePath は別 (これは
  各 server action 側で個別 revalidate しているので影響なし)

| 3 | click→URL/skel/content が T2 baseline からどれだけ改善 | **大幅改善** (click→URL -26〜-77%) |

期待値「試験 click→URL 1700 ms 前後」 に対し実測 **725 ms** で **期待値を大幅に

#### 残る遅延要因 (T3 へ送る)

- 試験 click→content 2918 ms 差分 = server body streaming (≒ DB query +

## Task 3: dashboard 統計の分離方式を比較検討 (実装なし、 設計判断)

**目的:** dashboard `/app/page.tsx` の SSR 重さ (修正前 2046 ms、 streak.ts 2 SELECT
+ dueCount SELECT が主) を改善する分離方式を、 T1/T2 結果を踏まえて選ぶ。

**候補:**
1. **Server Component 内 Suspense 分離**: stats 部分を別 server component に切り出し、
   `<Suspense>` で wrap。 ヘッダ等が早く描画され、 stats だけ後追い
2. **`/api/dashboard/stats` + client fetch**: stats を Route Handler に移し、 client
   が dashboard mount 後に fetch、 値が来るまで skeleton 表示
3. **`getReviewStatsForUser` の 2 SELECT 統合 + 既存 SSR 維持**: SQL を 1 本に集約
   し、 SSR 時間自体を短縮

**比較軸:**
- 体感改善 (T2 切り分けで「server SSR 待ち」 が click→skeleton の主因と確定した
  場合、 (1) Suspense は streaming 境界を明示するだけで TTFB は変わらない。 (2)
  client fetch は SSR を軽くするが mount 後 fetch で遅延が見える)
- 実装コスト
- session/Clerk と整合 (api route で Clerk auth 必要、 既存 `/api/exams/status` /
  `/api/review-events/bulk` 系と pattern 整合)
- Dexie 移行 (S-cache-3) との整合: (2) を選ぶと S-cache-3 で「Dexie 派生統計」 に
  置き換える時 API endpoint を活用できる

**完了条件:**
- 3 候補について 「体感改善 / 実装コスト / Dexie との整合」 を表で比較
- 採用 1 案を選定、 採用理由を 5-10 行で記述
- T4 で書く実装の File / 変更点を列挙

**やらないこと:**
- API 化を前提にしすぎない。 (1) Suspense で済むなら (1) を採用、 (2) は必要時のみ

### T3 分析 (2026-05-25、 C-1 後 baseline 確定済)

#### 現状の dashboard server fetch (`/app/page.tsx`)

1. `getCurrentUser()` — Clerk auth + users SELECT (layout でも呼ばれるが React.cache で同 render 内集約)
2. `db.select({c:count()}).from(cards).where(...due<=now)` — **dueCount** (1 SELECT、 cards_due_idx で軽量)
3. `getReviewStatsForUser(user.id)` (`lib/db/streak.ts:67-97`) — **2 SELECT**:
   - `SELECT distinct_card_count FROM study_days WHERE user_id=? AND day=?` (todayCardCount)
   - `SELECT day::text FROM study_days WHERE user_id=? AND day>=? AND review_count>0 ORDER BY day DESC` (直近 61 日 streak 用)

合計 **4 SELECT を server で逐次実行**。 T1 計測 `/app` total 1413 ms - `/app/settings` (基底) 895 ms = **~500 ms** が dashboard 固有 query 相当。 そのうち dueCount は軽量で大半は streak 系 2 SELECT。

#### 3 案比較

| 候補 | /app RSC body 短縮 | click→content 体感 | 実装リスク | S-cache-2/3 衝突 | Dexie-first 整合 |
|---|---|---|---|---|---|
| **1. Server Component 内 Suspense 分離** | △ 全体時間は同じ、 partial reveal で UX 改善のみ | △ CTA は先に flush だが stats は同等遅延 | 低 (Next.js native、 既存 loading.tsx と組合せ可) | なし | △ Dexie 化で不要、 過渡的 |
| **2. `/api/dashboard/stats` + Client fetch** | ◎ stats 分が server SSR から外れる (~500 ms 短縮見込) | ○ server SSR 短縮分 click→URL 改善 + stats は mount 後 fetch で遅延 | 中 (Route Handler + Clerk auth + Cache-Control + client fetch component) | なし | ◎ Dexie 派生統計の endpoint として再利用可、 fallback 経路として残せる |
| **3. SELECT 統合 (2 SELECT → 1)** | ○ 1 RTT 削減 (~150-250 ms 短縮見込、 実測次第) | ○ /app SSR 短縮分そのまま体感 | 中 (SQL 統合設計 + test、 純関数 computeStreak への入力形変更可能性) | なし | △ Dexie 化で捨てる SQL、 過渡的 |

#### 詳細評価

**候補 1 (Suspense)** の制約:
- `click→URL` は変わらない (Next.js client router は最初の RSC chunk 到達で URL 更新するため、 streaming 全体時間は同じ)
- partial reveal の UX 改善はあるが、 「server SSR の重さ」 自体は変わらず
- 体感より「stats が後から出る」 違和感を出すリスク

**候補 2 (API + Client fetch)** の制約:
- dueCount は CTA `<DashboardActions>` の enable/disable に必要 — client 化すると CTA が一瞬 disabled になる UX 劣化リスク
- 解決策: dueCount は **server SSR に残し**、 streak/todayCardCount のみ client 化 (最小実装)
- これにより `/app` server fetch は `getCurrentUser` + dueCount の 2 query のみ → settings 基底 (895 ms) + 軽量 dueCount で ~950-1000 ms 程度になる見込
- Route Handler は既存 `/api/exams/status` (`/api/exams/status/route.ts`) と同 pattern で実装可

**候補 3 (SELECT 統合)** の制約:
- Neon serverless では connection establish + RTT が dominant、 SELECT 2 → 1 で純粋に 1 RTT (~100-200 ms) 削減効果
- ただし統合 SQL の設計と test 整備で工数嵩む
- Dexie 化 (S-cache-3 想定) で `study_days` SELECT 自体が消える可能性が高く、 投資が短命

### 採用案: **候補 2 + dueCount は server SSR 残置 (ハイブリッド)**

採用理由:

1. **server SSR 短縮効果が最大** (T1 計測の dashboard 1413 ms 中 ~500 ms が
   streak 由来、 これを除けば settings 同等 ~895 ms へ近づく見込み)
2. **click→URL 短縮に直結** (server body streaming の最初の chunk が早く来る)
3. **Dexie-first 整合性が最良** (S-cache-3 で Dexie に `study_days` を pre-sync
   したら、 同 API endpoint で「Dexie 派生統計を server から fallback で返す」
   migration path が clean)
4. CTA UX を守るため dueCount だけ server SSR 残置 → CTA は最初の chunk で
   即 enable/disable 状態確定
5. 候補 1 は server SSR 重さの根本解決にならず、 候補 3 は短命投資

# S-perf-2: dashboard SSR / click-skeleton 遅延の切り分けと最小実装

> **For agentic workers:** 本 plan は **計測駆動**。 T1 / T2 の実測結果が確定するまで T3
> 以降の実装方針 (Suspense 分離 vs API 化 vs SELECT 統合) は決めない。 「計測 → 切り分け
> → 最小実装 → 再計測」 のサイクルで進める。

**Goal:**
1. dashboard 統計 (`/app` SSR、 修正前計測 2046 ms) の重さを切り分ける
2. click → skeleton 表示遅延 (S-perf-1 後の stg で 1.3〜1.8 秒) の原因を切り分ける
3. 実装は計測結果に基づいて最小限に行う
4. manual / hover prefetch は最後の手段として扱う (T6 で条件付検討)

**Architecture:** 本 sprint は cache 戦略 (`staleTimes` / `unstable_cache`) や Dexie
移行を**触らない**。 範囲は SSR ↔ Suspense ↔ client fetch の責務分割と DB query
最適化のみ。

**Tech Stack:** Next.js 15 App Router / React 19 / TypeScript strict / Drizzle ORM /
Neon serverless / Vitest + Testing Library + jsdom / Playwright MCP for 実機計測

## Task 2: click → skeleton 表示遅延の切り分け (実装なし、 計測のみ)

**目的:** S-perf-1 で観測した click → URL 変更 + skeleton 表示の 1.3〜1.8 秒が、
以下のどれに由来するかを実測で切る:
- (a) server SSR 待ち (RSC fetch + getCurrentUser + page 固有 SELECT)
- (b) layout (`/app/(app)/app/layout.tsx`) の再 evaluate (`getCurrentUser` + redirect 判定)
- (c) client transition 機構 (React 18+ `startTransition`、 next router の suspense 解決)
- (d) Next.js の chunk lazy load (route group `(app)` 配下の lazy chunk)

**対象遷移:**
- `/app` → `/app/exams`
- `/app` → `/app/settings`
- `/app` → `/app/study/smart`
- `/app` → `/app/upload`

**計測時系列:**
1. click 時刻 (`t0`)
2. URL 変更時刻 (`location.pathname` 変化を 30 ms 間隔で polling、 厳密ではないが
   実測に耐える)
3. loading skeleton 表示時刻 (`[aria-label="読み込み中"]` / `[role="status"]`
   MutationObserver で検知 — S-perf-1 の `aria-label="loading"` は Minor #4 で次の
   polish に回したが、 計測 selector は両対応にする)
4. content 表示時刻 (page 固有 keyword、 ただしヘッダの link テキストと重ならない
   keyword を選ぶ。 `/app/exams` なら 「アップロード 2026-」 等 fixture 由来の文字列)

**切り分け方:**
- `[server SSR 待ち]` 仮説検証: 同じ page の direct `?_rsc=` fetch TTFB + body と
  click → skeleton の差が ±200 ms 以内なら server SSR が主因
- `[layout 再 evaluate]` 仮説検証: next.js は同 segment 内 navigation で layout を
  再 render しない仕様。 ただし `(app)` route group 内で layout が含まれる場合は
  navigation 時に再評価される可能性 — `[browser_evaluate]` で
  `performance.getEntriesByType('measure')` などから React 計測点を確認
- `[client transition]` 仮説検証: warm cache (2 回目以降 click) で時間短縮するなら
  fetch の cold 性が主因、 短縮しなければ client transition 由来
- `[chunk lazy load]` 仮説検証: 1 回目 click と 2 回目以降 click の差が大きく、
  かつ Network tab で `.js` chunk fetch が走っていれば該当

**完了条件:**
- 4 遷移 × 時系列 4 点を表形式で追記
- 切り分け結論 (a/b/c/d のどれが主因か、 もしくは複合か) を 3-5 行で記述
- T3 で検討する分離方式の選択肢を絞る

**やらないこと:**
- この task では実装変更しない

## Task 3: dashboard 統計の分離方式を比較検討 (実装なし、 設計判断)

**目的:** dashboard `/app/page.tsx` の SSR 重さ (修正前 2046 ms、 streak.ts 2 SELECT
+ dueCount SELECT が主) を改善する分離方式を、 T1/T2 結果を踏まえて選ぶ。

**候補:**
1. **Server Component 内 Suspense 分離**: stats 部分を別 server component に切り出し、
   `<Suspense>` で wrap。 ヘッダ等が早く描画され、 stats だけ後追い
2. **`/api/dashboard/stats` + client fetch**: stats を Route Handler に移し、 client
   が dashboard mount 後に fetch、 値が来るまで skeleton 表示
3. **`getReviewStatsForUser` の 2 SELECT 統合 + 既存 SSR 維持**: SQL を 1 本に集約
   し、 SSR 時間自体を短縮

**比較軸:**
- 体感改善 (T2 切り分けで「server SSR 待ち」 が click→skeleton の主因と確定した
  場合、 (1) Suspense は streaming 境界を明示するだけで TTFB は変わらない。 (2)
  client fetch は SSR を軽くするが mount 後 fetch で遅延が見える)
- 実装コスト
- session/Clerk と整合 (api route で Clerk auth 必要、 既存 `/api/exams/status` /
  `/api/review-events/bulk` 系と pattern 整合)
- Dexie 移行 (S-cache-3) との整合: (2) を選ぶと S-cache-3 で「Dexie 派生統計」 に
  置き換える時 API endpoint を活用できる

**完了条件:**
- 3 候補について 「体感改善 / 実装コスト / Dexie との整合」 を表で比較
- 採用 1 案を選定、 採用理由を 5-10 行で記述
- T4 で書く実装の File / 変更点を列挙

**やらないこと:**
- API 化を前提にしすぎない。 (1) Suspense で済むなら (1) を採用、 (2) は必要時のみ

## Task 6 (条件付): manual / hover prefetch 検討

**目的:** T5 で主要導線 click → skeleton が 800 ms を超え、 かつサーバー負荷が
許容できる場合のみ、 部分的に prefetch を復活させる。

**着手条件 (満たさなければ skip):**
- T5 計測で `/app` → `/app/exams` / `/app/settings` のどちらかが click → skeleton
  800 ms 超
- T1 / T5 比較で server SSR は十分短縮済 (= prefetch のサーバ並列負荷増加が
  許容できる状態)
- 「アイドル時の並列 prefetch でサーバが圧迫される」 リスクが S-perf-1 lesson と
  整合する範囲内

**候補:**
- `<Link prefetch="hover">` (Next.js 15 で導入): user の意図的 hover / focus 時のみ
  prefetch、 自動 viewport prefetch は無し
- 特定 link (例: dashboard の最重要導線 「スマート復習」 CTA) のみ prefetch=true
  に戻す

**完了条件 (実施時):**
- 着手判定の根拠を本 task に明記 (なぜ 800 ms 超か / サーバ負荷見積もり)
- 実装後の click → skeleton を再計測、 prefetch 並列度との trade-off を表で示す
- review + commit (`feat(perf): S-perf-2 T6 hover prefetch [reviewed]`)

**やらないこと:**
- T5 で着手条件を満たさなければ T6 は **実施しない** (= S-perf-2 完了)
- 全 link に hover prefetch を一律適用しない (限定導線のみ)

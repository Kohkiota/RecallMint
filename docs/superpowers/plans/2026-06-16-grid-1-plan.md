## Open Questions (実装着手前に方針確定が必要、 各案 + CC 推奨を明示)

### OQ-1: `useCardTagToggle` の正確な signature

- 案 A (CC 推奨): `useCardTagToggle({ userId, getCardContext }): (cardId, categoryId, optionId) => Promise<void>` 形。 `getCardContext(cardId)` は table レベル props (live data: categories / options / cardTagsByCardId Map) を closure capture した getter で、 toggle 内で `(categories, options, allAssignedOptionIds for that card, sameCategoryOptionIds)` を解決。 table 側は 1 回 instantiate、 戻り値 callback を各 TagCell に配る (OT 制約 1 + 2 を満たす)。
- 案 B: `useCardTagToggle({ userId, categories, options, cardTagsByCardId }): (cardId, categoryId, optionId) => Promise<void>` 形。 live data を直接 hook 引数で渡す (getter なし)。 単純だが live data 更新時に hook 戻り値の identity が変動 → 各 TagCell 再描画が増える可能性。
- 案 C: hook ではなく module 関数 `cardTagToggle(deps, cardId, categoryId, optionId): Promise<void>` 形で React 外。 表面積最小だが caller が deps を毎回手で渡す。

CC 推奨: **案 A**。 ① getter pattern で identity 安定 (deps closure を一度組めば再描画 propagation を最小化)、 ② OT 制約 1 (hook 内 useLiveQuery 禁止) + 制約 2 (table レベル 1 instantiate) を素直に満たす、 ③ `CardTagsSection` の hook 移行 (T2) でも `getCardContext` を内側で組めば 1 行差し替え可能。

### OQ-2: タグ列の先頭 K 個 の K 値 (初期提案)

- 案 K=3: 短いが見える badge が 3 個。 desktop でも mobile でも視覚的に詰まらない。
- 案 K=5 (CC 推奨): typical タグ件数 (per card) は 2-6 個想定 + ほとんどのカードで `+N` 非表示で済む。 mobile 横スクロールでも見える範囲。
- 案 K=可変 (desktop=5 / mobile=3): UX 最適だが画面幅判定の実装複雑度増。

CC 推奨: **K=5 (固定)**。 mobile / desktop 共通で挙動が単純、 視覚調整は実装時に screenshot で詰める。 5 でも溢れる場合は plan 凍結後の hotfix で K=3 に下げる手はある。

### OQ-3: TanStack に渡す join のシェイプ

- 案 J-A (CC 推奨): `Array<{ card: ExamDetailCard; tags: Array<{ category: ClientTagCategory; option: ClientTagOption }> }>` の flat array。 row = card、 tags は pre-resolved (= TagCell 内で再 lookup 不要)。
- 案 J-B: `Array<ExamDetailCard>` のみを data に渡し、 TagCell 内で `tagsByCardId.get(cardId)` + categories / options から解決。 join コストを cell render に分散。
- 案 J-C: `data` は card 主体 + `meta` に Map で全 join 結果を持つ。 row level と meta level の関心分離が曖昧。

CC 推奨: **案 J-A**。 useLiveQuery 解決時に 1 回 join → data prop は flat、 cell render は read-only。 T6 unit test も flat shape で組みやすい。 数百件規模で join 1 回は誤差 (Grid-0 perf 計測の prior art あり)。

### OQ-4: ViewToggle = shadcn `Tabs` か独自 button group か

- 案 V-A: shadcn `Tabs` component を新規追加 (`components/ui/tabs.tsx`)。 a11y / keyboard nav が build-in、 既存 shadcn 流儀 (`Tabs / TabsList / TabsTrigger`)。
- 案 V-B (CC 推奨): 独自 button group (2 button + aria-pressed)。 既存 `Button` (`components/ui/button.tsx`) を流用、 新規 file なし、 a11y は `role="group"` + `aria-pressed` で十分 (2 セグメントのため keyboard nav も Tab 2 回で完結)。
- 案 V-C: shadcn `ToggleGroup` 追加。

CC 推奨: **案 V-B**。 Grid-1 で 2 セグメントだけのために新規 shadcn component 追加は YAGNI。 Grid-2 以降で view が 3 つ以上になる場合に Tabs 化を再検討。

### OQ-5: Selection clear を conditional unmount 単独で済ませるか明示 `resetRowSelection` 併用か

- 案 S-A (CC 推奨): **conditional unmount 単独**。 spec §7 の選択方針通り、 `{view === 'table' && <ExamCardTable />}` で view='card' 時 unmount → React tree 解除で TanStack rowSelection state が自然消去。 明示 reset は冗長。
- 案 S-B: unmount + 明示 `table.resetRowSelection()` を view 切替時 `useEffect` で併用。 防御的だが二重経路。
- 案 S-C: 常時 mount + display:none + 明示 reset のみ。 spec §7 既定設計と背反。

CC 推奨: **案 S-A**。 unmount で自然消去 + T7 smoke で実機確認すれば充分。 二重経路 (S-B) は防御過剰で実害なし、 設計を読み解きにくくする。

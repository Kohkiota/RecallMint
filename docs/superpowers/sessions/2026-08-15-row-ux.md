## 3. 実装した契約

- **二役グリップ**: 1 button が drag activator と Popover trigger を兼ねる。追加の click 制御コードは**書いていない** — dnd-kit が距離制約下で「閾値未満の押下には click 抑止 listener をそもそも張らない」ため、≤4px は native click として menu に届き、>4px のドラッグでは document capture が click を止める。Space は keydown で `preventDefault` されドラッグ専用、Enter は menu に回る。
- **gating の分離**: `dragAvailable`(rows>=2・columnFilters 非依存)と `dragEnabled = dragAvailable && !locked && !pending`。dnd attributes / `aria-roledescription` / SR instructions 参照は **dragEnabled 時のみ**、`setActivatorNodeRef` は **dragAvailable の間は維持**(ドラッグ可能な状況で外すと KeyboardSensor の activator 判定が死ぬ)。native `disabled` は撤去し、menu 役はソート/フィルタ中も 1 枚でも生存する。
- **低コントラスト常時表示**: grip 50% / checkbox `opacity-50` + `checked:` で常時通常。hover 出現(基底 `opacity-0`)は不採用 — Tailwind v4 が `hover:` を `@media (hover:hover)` で包むためタッチ端末で永久不可視になる(spec §12 の NO-GO)。
- **a11y**: `lib/dnd/accessibility.ts` の日本語 announcements factory + instructions 2 定数を **DndContext 5 instance 全部**に配線。生 card/option id は文言に出さない(位置は sortable data の index/length のみ使用)。
- **footer**: `<tfoot>`(仮想化 spacer / memo 凍結 / `SortableContext.items` のいずれとも無縁)。gating 3 条件 = `!dataReady || positionLocked || movePending`。
- **`useAddCard`**: card id 同期採番 → `buildEmptyCard` → `onIdMinted` → 最初の await、という順序契約を hook 構造で保存。カードビューは挙動不変。

### 5.6 smoke で判明した事項(FAIL ではないが記録)

- **A. side peek の開状態は視覚・aria とも手掛かりが完全に不在**(follow-up ② の裁定材料)。peek 表示中の行の背景は**透明**で、強調は mouse hover に追従するだけ。`aria-pressed` / `aria-current` / `data-active` いずれも無し。加えて **peek の入口は grip → menu →「開く」の 1 経路のみ**(title cell からの起動は撤去済)。視覚利用者は peek 本体が見えるため実害は限定的だが、**SR 利用者は「どの行を開いているか」を知る手段が無い**。
- **B. keyboard drop 後の focus は grip に残る** — 行 DnD session §5.6-A の「drop 後 focus が body へ落ちる」から**改善**している(grip が menu trigger として mount され続けるため復帰先を失わない)。二役化の副次的な利得。
- **C. tag option の aria-label が「option を並べ替え: 経済」**と英単語混じり(既存文言・本 sprint の対象外)。日本語 UI としては軽微な粗で、follow-up 候補。
- **D. smoke 中に stg のデータが変化**: exam `090550a7` に **テストカード 2 枚**(「新規カード 4」= table footer 由来 / 「新規カード 5」= カードビュー由来)を追加、および「06」の相対位置が先頭 → 末尾へ(base_order 3391 → 6229)。いずれも smoke 操作の正当な結果で、DB の整合性(重複・逆転)は無し。**復旧は行っていない**(破壊的操作は OT 判断)。

### 5.7 method 上の注意(次に同じ smoke を回す人へ)

- **行が viewport 外にあると `page.mouse.down()` が要素に届かず、drag が無反応になる**(本 smoke で 1 度発生し、outbox 不変・並び不変の「偽 FAIL」に見えた)。本テーブルは 1 行 400〜600px と背が高く、3 行で既に viewport(720px)を超える。**drag 前に必ず `scrollIntoViewIfNeeded()` で対象 grip を可視域へ入れ、drop 先の y も viewport 内にクランプする**。
- **toast の undo は auto-dismiss で消える**。DB readback を挟むと間に合わないので、**移動 → undo click → その後に DB 確認**の順で 1 続きに実行する。
- ソート解除は header menu には無く(昇順 / 降順 / 固定表示のみ)、**条件バーの `aria-label="ソート解除: 番号"`** から行う。
- live region は前回の文言を保持するため、**新しい文言かどうかは内容で判別する**(取得タイミングだけでは stale と区別できない)。

1. **red 検証は「pin したもの」しか変異対象にできない。** Task 4 の実装者は 41 変異を個別に流して全て狙いどおり red にしたが、canonical が使い捨て worktree で**独立に変異試験**を行うと、実装者自身が意図的に変えた挙動(title 条件)と sprint の目玉である低コントラスト class が、**変異しても全 suite が green のまま**だった。red 検証が証明するのは「pin したものが効いているか」であって「pin し忘れがないか」ではない。**pin を red 検証した後、spec の要求リストの側を 1 行ずつ変異させて、pin されていない要求を探す**のが欠けていた半分。

   最終 review が同じ形の欠落をさらに 3 件見つけたことで、この教訓には運用形と**探す場所**まで判明した。3 件(`movePending` gate / tag site の announcements / grip の class)は**実装がすべて正しく、誤っていたのは「なぜ test しないか」の理由付けの方**だった —「plan の OT 修正 2 により test 化しない」(誤読。plan は逆に要求していた)/「plan は instructions だけ求めた」(要求の範囲を狭く読んだ)/「checkbox は pin したが grip を忘れた」(対称性の見落とし)。つまり **pin 漏れは「他でカバー済み」と思っている要求に集中する**。運用形は「red 検証の後、spec の要求リストを 1 要求ずつ scratch worktree で変異させる。**カバー済みと信じている要求こそ**含める」。
2. **gate の裏に隠れた契約は、別の観測点なら pin できる。** Task 5 で plan は「呼出側を filter 後 rows に差し替える変異で click test が fail する」ことを求めたが、`positionLocked` が sort/filter 中は button を disabled にするため、**rows が乖離する状態と click 可能な状態が排他**で、click 起点では原理的に観測できなかった(実装者が実際に変異を入れて 140 test green のままを確認)。しかし `baseOrders` / `count` は click 可能性と無関係に毎 render 計算されて子へ渡るため、**props 境界は常に生きた観測点**である。既存 capture wrapper で pin したところ、変異で狙いの 1 件だけが red になった。**変異させても落ちないとき、実装が正しいのか観測点が違うのかを切り分ける**。
3. **helper を共有にした瞬間、その helper の既存欠陥は自分の責任範囲に入る。** `cardLabel` の「空白のみラベルで title に落ちない」は本 sprint 以前からの挙動だが、SR 読み上げと共有にしたのは本 sprint であり、影響範囲を広げた当事者が直すのが筋。「既存挙動だから範囲外」は、範囲を広げた本人には使えない。
4. **IDE 診断は繰り返し嘘をつく。** 本 session では rule 71007(Server Action 誤検出)が 3 回、`Cannot find module 'react'` 級の致命的に見える診断が 2 回出たが、いずれも `git show HEAD:` 比較で既存 prop 由来、あるいは `pnpm typecheck` exit 0 で false と確認できた(reviewer の worktree 操作や build による TS server の混乱が原因)。**診断を根拠に動く前に、その診断が現物と一致するか自分で確認する**(行 DnD session 教訓 3 の再確認)。
5. **「不触 N 件」のような数え上げは、仕様変更で静かに嘘になる。** brief は既存 dnd test 16 件のうち「13 件は不触」と数えていたが、新 gating 下では ⑬ の主張が偽になるため書換が必須だった。**test の本数ではなく、各 test が何を主張しているかで数える**。

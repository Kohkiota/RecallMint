## 1. Step 0 Item 1-3: 実コード読み (前提検証)

### 1.1 inline-card-list.tsx の card_tags query 経路

`app/(app)/app/exams/[id]/_components/inline-card-list.tsx:88-108` の useLiveQuery callback:

```ts
const liveData = useLiveQuery(async () => {
  const db = getClientDb()
  const [cardRows, categories, options, cardTags] = await Promise.all([
    db.cards.where('exam_id').equals(examId).toArray(),
    db.tag_categories.toArray(),
    db.tag_options.toArray(),
    db.card_tags.toArray(),   // ★ L94: 全 scan
  ])
  // ...
  const tagsByCardId = new Map<string, ClientCardTag[]>()
  for (const t of cardTags) {
    const arr = tagsByCardId.get(t.card_id) ?? []
    arr.push(t)
    tagsByCardId.set(t.card_id, arr)
  }
  return { cards, categories, options, tagsByCardId }
}, [examId, userId])
```

- **L94 `db.card_tags.toArray()` = 全 scan が初回表示時に実在**。 (T-B1' のような「削除フロー click 時のみ発火」 ではない、 plan 主張は正しい)

- pagination / virtualization は無し: `cards.map(card => <li>...</li>)` で 1 画面に全 card 描画 (L270)

## 3. Step 0 Item 4 (追補): 構造的 micro-bench (scale 別)

現実データでは 0 = 計測対象なし。 fix の正味は「現実データ scale でなく将来 scale で初めて差が出る」 構造改善であるため、 isolated IDB に scenario 別 fixture を投入 (本番 stg 'recallmint' DB は触らず) → cleanup の 1 way で測定。

### 3.1 シナリオ (5 run avg / scenario)

`target_rows` = 計測対象 exam の card_tags 件数 (= page subset)、 `other_rows` = 別 exam の card_tags 件数 (= 全 scan が無駄に読み込む rows)。 計測 target は 50 cards × 4 tags = 200 target_rows 固定 (plan 完了条件 fixture 形)、 other は段階的に増やす。

| scenario | total rows | target rows | toArray (現状) | anyOf parallel getAll (fix) | 差 (toArray - anyOf) |
|---|---|---|---|---|---|
| **A: plan-fixture (1 exam 完結)** | 200 | 200 | **1.56 ms** | 3.56 ms | **-2.0 ms (fix が遅い)** |
| **B: typical multi-exam (+1000 他 exam tags)** | 1,200 | 200 | 9.82 ms | 5.5 ms | +4.3 ms (1.8x) |
| **C: heavy multi-exam (+5000 他 exam tags)** | 5,200 | 200 | **44.32 ms** | 4.9 ms | **+39.4 ms (9.0x)** |
| **D: extreme (+20000 他 exam tags)** | 20,200 | 200 | **176.82 ms** | 4.78 ms | **+172 ms (37x)** |

### 3.2 観察

1. **plan 完了条件の fixture (A: 50 card / 200 card_tags、 multi-exam 規定なし) = anyOf が遅い**。 page subset == 全件で page subset 化のメリットが消え、 multi-range query の overhead だけ残る。 つまり plan 完了条件の文面どおりに測ると **「fix で遅くなった」 という逆結果**になる。
2. typical (B、 ~1k 他 exam tags) で 1.8x、 heavy (C、 ~5k) で 9x、 extreme (D、 ~20k) で 37x。 anyOf は他 exam 件数に対して **平坦** (4.8-5.5ms)、 toArray は線形に膨らむ。
3. **体感閾値 (>50ms = jank が user 知覚レベル)** は scenario C 以上で超え始める。 typical scale ではまだ jank には届かない。

### 3.3 user scale の現実性

stg 本 user (komail9server+clerk_test) は 1 exam / 0 card_tags。 OT 本アカウント想定の使用シナリオ (試験を複数作る学習 user) でも、 短期は B 程度。 C-D は中長期 (数年継続 user) の想定。

## 4. plan 仕様への構造的疑問点 (実装前に解消必要)

### 4.1 memoize 設計 hazard

plan L105 「memoize key = `cards.map(c => c.id).sort().join(',')` 等の安定 key」 は **useLiveQuery callback 内で実装すると card_tags 変化検知を取りこぼす**:

- useLiveQuery は callback が触った store の change で再 fire する (Dexie 内部の subscription)
- callback 内で `if (cache.has(memoKey)) return cache.get(memoKey)` を入れると、 card_tags 変化 (add/remove) で callback は fire するが同 memo key (= cards id 集合不変) で stale を返す
- 結果: tag pill 更新が反映されない (= 描画 bug)

memoize の意図が「assembly 段 (`tagsByCardId` Map 構築) を skip」 なら OK だが、 plan 文言からは「fetch 結果を再利用」 とも読める。 **plan の memoize は仕様凍結 (spec) ではなく実装 hint 段階のため、 着手時に意図確認必要**。

候補解釈:
- (i) **memoize 不要案**: anyOf 化のみ実施、 memo は持たない。 useLiveQuery が card_tags 変化で再 fire したらそのまま再 fetch (anyOf は数 ms で軽い)。 シンプルで安全。
- (ii) **assembly memoize 案**: `tagsByCardId` Map 構築だけ useMemo で memo、 fetch は毎回 (= 影響軽微なので意味薄)。
- (iii) **plan 文言どおり fetch memoize 案**: 上述 stale bug を抱える、 不採用。

私は (i) を推奨 (最小差分 + bug free)。

### 4.2 Promise.all 構造の崩壊

現コード L90-95 は `cards / categories / options / card_tags` を Promise.all で並列 fetch。 fix で `card_tags` の `anyOf(pageCardIds)` に変えると **pageCardIds は cards に依存** → 並列化不可。

修正後の素直な形:
```ts
const [cardRows, categories, options] = await Promise.all([
  db.cards.where('exam_id').equals(examId).toArray(),
  db.tag_categories.toArray(),
  db.tag_options.toArray(),
])
const filteredCards = cardRows.filter(c => c.user_id === userId).sort(sortLikeServer)
const pageCardIds = filteredCards.map(c => c.id)
const cardTags = pageCardIds.length === 0
  ? []
  : await db.card_tags.where('card_id').anyOf(pageCardIds).toArray()
```

card_tags fetch が直列化されるが、 (i) anyOf 自体が 5 ms 程度 + (ii) cards fetch が先行で wait 不要なため total wall-clock は scenario C-D で大幅改善、 A でも数 ms regress 程度。 **構造的に正しい順序**。

### 4.3 `tag_categories` / `tag_options` も全 scan のまま

T-B5 scope 外だが念のため記録: L92-93 の `db.tag_categories.toArray()` / `db.tag_options.toArray()` は同様に全 scan。 user_id scope filter なし (Dexie schema には `user_id` index あり)。 こちらは tag マスタ件数が小規模なため scope 外と判断するが、 将来 audit で要再検討。

## 5. 判断分岐 (plan Step 0 規定どおり)

plan Step 0 規定:
> - 全 scan が初回表示に実在 + 実機で遅延あり → 実装
> - scan が実在しない or 既に絞り込み済 or **実機で遅延が無視できる** → close 候補

実機 baseline (現実データ):
- 全 scan 実在: **yes**
- 実機で遅延あり: **no** (現状 0 件 = 2.7 ms 以下、 体感不可)

将来 scale:
- typical multi-exam (B): 9.8 → 5.5 ms = 構造改善あるが体感外 (両者 <50ms)
- heavy / extreme (C, D): 44-177 ms → 5 ms = 体感差、 ただし数年使用想定の scale

**plan 文言の判定は「close 候補」**。 しかし fix 自体は構造改善で diff も小規模 (Y-1 anyOf precedent 流用)。 OT 判断材料:

### 5.1 選択肢

- **案 α (実装)**: 「将来 scale (C-D) で確実に効く構造改善、 diff 小、 anyOf precedent あり、 今やる」
- **案 β (close 候補)**: 「現実データ 0 件 + typical scale で体感差なし → T-B1' precedent 流用で close、 plan 完了条件 fixture (A) では fix が逆効果なので literal 検収不能、 Y-3 (実 user の card_tags 件数増加観測時) に再評価」
- **案 γ (実装 + 完了条件修正)**: 案 α + plan 完了条件の fixture を multi-exam 形 (B-C 相当) に書き直してから検収。 spec 凍結則 (CLAUDE.md) と plan 凍結則の境界に触れる: T-B5 は **spec ではなく plan 内 task** のため、 plan の完了条件は OT 承認で改訂可能。

私の推奨: **案 α**。 根拠:
- 構造的に正しい (Promise.all 順序変更も含めて筋が通る)
- 将来 scale で確実に効く (37x の余地はリスクではなく value)
- diff 小、 anyOf precedent (Y-1 #3 / T-B1' で fix 試行した形と同型) で実装 risk 低
- ただし plan 完了条件 fixture (A) は逆結果が出るため、 完了条件は **「multi-exam 形 fixture (B) で anyOf < toArray を確認」 に改訂** (案 γ の点で OT 承認必要)。

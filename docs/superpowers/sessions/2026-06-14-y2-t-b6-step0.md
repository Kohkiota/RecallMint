  const dueCount = useLiveQuery(
    async () => {
      const nowIso = (now ?? new Date()).toISOString()

        .cards.where('user_id')
        .equals(userId)

## §5 副作用 / scope 境界

### 5a. 不変条件 (T-B5 の「描画 pill 集合不変」 相当)

- **dueCount 数値が一致**: path A (現状) と path C (compound index `.count()` 想定) は同一の `due <= nowIso` semantics → bench で全 scale verify 一致 (400/1002/4008/20040)
- **dashboard 表示挙動不変**: `スマート復習（N件）` / `復習完了！` / skeleton の 3 状態の boundary が dueCount 数値だけに依存、 数値が一致するため UI 不変

### 5b. correctness リスク

| リスク | 評価 |
|---|---|
| **tenant isolation** | compound index 第 1 要素 `user_id` を `equals` fix で、 `[user_id+due]` index 経路で他 user に到達不能 (T-B4 と同 pattern) → 構造保証 |
| **lex 比較の安全性 (2026-06-14 二段補正)** | due = ISO8601 文字列、 query は `between([uid, '0'], [uid, nowIso], true, true)` の形 (lower bound `'0'` は ISO8601 (`'0001-...'` 以上) より lex で小さい正当な下限、 upper bound `nowIso` を **明示的に inclusive** にして元コード `due <= nowIso` と等価)。 **Dexie `.between(lower, upper, includeLower=true, includeUpper=false)` の default は `includeUpper=false` = upper exclusive** であり、 §補-B 初稿で「default `upperOpen=false` で inclusive」 と書いた箇所は事実誤認 (実コード probe で `due == nowIso` ぴったり行が exclude されることを §補-E で観測、 unit test も 72 vs 70 で catch)。 等価には第 4 引数 `true` で `includeUpper=true` を明示する。 初稿で upper を sentinel `'￿'` と書いた箇所は dueCount semantics を「全 user cards 件数」 に化けさせる誤りのため `nowIso` に補正済。 詳細は §補-B / §補-E。 |
| **count vs toArray** | plan L147 の `between(...)` で終わっており `.count()` 明記なし。 dashboard-actions の戻り値は `.length` のみ → **`.count()` 採用が ideal** (row 本体 fetch なし、 bench path C と同 cost)。 `.toArray().length` 経路は無駄に row materialize するため避ける |
| **subscription 範囲** | useLiveQuery は Dexie の table 変化 broadcast に reactive。 compound index に変えても subscription 範囲 (= cards table 全体) は不変、 over-subscription 増えない |

### 5c. migration 影響 (= plan 制約矛盾)

- 現 v6 → 新 v7 で `[user_id+due]` を **新規追加** 必要 (plan「新規 migration なし」 と矛盾)
- 形式: v2 / v4 / v5 / v6 と同形の純粋 index 追加。 store drop なし、 既存データ保持、 upgrade callback 不要
- migration cost: 既存 cards 行に対する index re-build が走る (Dexie / IndexedDB 自動)。 ローカル 10 cards で~5ms 想定、 50k で~数秒。 user 視点では DB open 時に 1 回 ペナルティ
- 同 plan 内 T-B7 (get-dexie-session-cards、 plan L152-159) も同 index 使用予定 → v7 で T-B6 / T-B7 共用 1 回追加で済む (両方を 1 commit で実装するか、 T-B6 で v7 を立てて T-B7 が乗るか)

### 5d. scope 外 / 周辺取りこぼし

| 項目 | 評価 |

### 案 α: そのまま実装 (plan 制約「新規 migration なし」 を破り、 v7 追加)
- **根拠**: 構造改善は明確 (8k cards 規模で 132ms → 22ms、 6x 改善)、 周辺 (T-B7) で同 index 流用 precedent 確立。 launch hardening 趣旨 (dashboard = 最頻 access) と一致
- **diff 規模**: dashboard-actions.tsx 数行 + lib/client-db.ts に v7 block 追加 + dashboard-actions.test.tsx の query expectation 更新 (= small/medium)
- **問題**: plan L147「新規 migration なし」 と矛盾、 plan 改訂なしでの実装は規律違反 (T-B5 の「memoize 不採用」 のような事後改訂precedent あり)

### 案 β: close 候補 (現実データで体感差なし → 後送り)
- **根拠**: 現実 test user (10 cards) で 20ms、 平均 user (~1k cards) でも 30ms 未満。 launch 直後の MVP では体感問題なし
- **再評価条件**: stg / prod の cards 件数 P95 が 2k を超えたら再着手。 retention 指標 (継続 user の cards 累積) 監視を OT と合意

- **diff 規模**: 0 (実装なし、 plan に close ノート追加 + Y-3 繰越提案のみ)

### 案 γ: 実装 + 完了条件改訂 (plan L147 改訂で「v7 新規追加 + T-B7 と共用」 を明文化) **← CC 推奨**

  1. 構造改善は明確 (案 α と同じ)、 audit 趣旨と整合
  2. plan の「既存 index」 前提が事実誤認なので、 plan を **そのままにして実装すると規律違反**。 改訂が必要

  4. T-B5 で plan を「memoize 不採用」 に事後改訂した precedent あり (sessions/2026-06-14-y2-t-b5-step0-redo.md §2c)、 同様の対応

  (当時の承認文面、 末尾の Dexie default 主張は §補-E で誤りと判明 → 現行の確定文面は plan B-perf.md L147 を参照)
  制約 (2026-06-14 改訂、 Step 0 §3 を反映): ... query = `db.cards.where('[user_id+due]').between([userId, '0'], [userId, nowIso]).count()` 形 ... upper bound nowIso を inclusive (Dexie .between() の default upperOpen=false) にして元コードの due <= nowIso と等価)。

### §補-E (2026-06-14 二段補正、 §補-B/§補-C の事実誤認の是正): Dexie `.between()` 既定値の確認 + boundary 全パターン probe

**経緯**: §補 (一段目補正) で `'￿'` → `nowIso` への upper bound 補正後、 OT 承認下で実装着手 → unit test (`dashboard-actions.test.tsx` の large multi-exam fixture) が 72 期待 vs 70 実測で fail。 isolated probe で「Dexie default は upper inclusive」 と書いた §補-B / §補-C の前提が事実誤認で、 **真は upper exclusive (Dexie `.between(lower, upper, includeLower=true, includeUpper=false)` の第 4 引数 default が `false`)** と判明。 OT 指示で全境界 probe を 1 回で潰した記録。

#### §補-E.1. Dexie `.between` 既定値の確認

Dexie API: `WhereClause.between(lower, upper, includeLower=true, includeUpper=false)`
- 第 3 引数 default = `true` (lower inclusive)
- 第 4 引数 default = **`false`** (upper **exclusive**)
- 元コード `c.due <= nowIso` (inclusive) と等価にするには第 4 引数 `true` を明示する必要あり。

#### §補-E.2. boundary 全パターン probe (isolated `tb6-boundary-probe` DB、 cleanup 済)

13 行 seed (U1 = 自 user 8 行 + U2 = 他 user 5 行)、 raw IDB `IDBKeyRange.bound` の openness flag で 3 query を比較:
- q1 = Dexie default 等価 (upper exclusive)、 第 4 引数 `false`
- q2 = 案 X (両端 inclusive)、 第 4 引数 `true`
- q3 = 元コード `cards.where('user_id').equals(uid).toArray().filter(c => c.due <= nowIso)`

`nowIso = '2026-04-22T12:00:00.000Z'`

| id | user | due | q1 (default) | q2 (案 X) | q3 (元) | q2=q3? |
|---|---|---|---|---|---|---|
| lo-zero | U1 | `'0'` | ✓ | ✓ | ✓ | ✓ |
| lo-iso-min | U1 | `'0001-01-01T00:00:00.000Z'` | ✓ | ✓ | ✓ | ✓ |
| past-1d | U1 | `'2026-04-21T12:00:00.000Z'` | ✓ | ✓ | ✓ | ✓ |
| past-1ms | U1 | `'2026-04-22T11:59:59.999Z'` | ✓ | ✓ | ✓ | ✓ |
| **now-exact** | U1 | `'2026-04-22T12:00:00.000Z'` (= nowIso ぴったり) | **✗** | **✓** | **✓** | ✓ |
| now-plus-1ms | U1 | `'2026-04-22T12:00:00.001Z'` | ✗ | ✗ | ✗ | ✓ |
| future-1d | U1 | `'2026-04-23T12:00:00.000Z'` | ✗ | ✗ | ✗ | ✓ |
| future-far | U1 | `'2099-01-01T00:00:00.000Z'` | ✗ | ✗ | ✗ | ✓ |
| other-zero / other-iso-min / other-past / other-now / other-future | U2 | (上記同値) | ✗ | ✗ | ✗ | ✓ |

count: q1=4 / q2=5 / q3=5。 q2 == q3 全 13 行一致、 q2 で他 user 混入 0 件。

#### §補-E.3. 結論

- 案 X (`between([uid,'0'],[uid,nowIso], true, true)`) は **全境界で元コード `c.due <= nowIso` と semantics 一致**。
- 唯一 q1 (default) が落とすのは `due == nowIso` ぴったり行 (now-exact)。 prod では `Date.now()` の sub-millisecond 解像度で実発生確率はほぼゼロだが、 unit test が 72 vs 70 で catch する形になっておりここで止めた。
- lower bound `'0'` は `due='0'` / `'0001-...'` の最下限を inclusive で拾える (案 X / 元 とも ✓)。
- tenant isolation は compound index 第 1 要素 user_id の equals fix で構造保証 (q2 他 user 混入 0)。
- L147 / §補-B / §5b 補記の「Dexie default upperOpen=false で inclusive」 文言は事実誤認だったため、 plan / session log 該当箇所を「default は upper exclusive、 等価には第 4 引数 `true` 明示が必要」 に書き換え (case-X.3 reflect 同 commit 内)。

**OT 最終承認 (2026-06-14、 二段補正後)**: L147 末尾 query を `between([userId, '0'], [userId, nowIso], true, true).count()` 形に確定。 regression test に `due == nowIso` 境界行を明示し、 boundary を test で守る。

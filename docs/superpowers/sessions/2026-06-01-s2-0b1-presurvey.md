## (B) OCR 完了後の自動反映

### 重要: アーキテクチャは「Dexie mirror が source of truth」

試験一覧・詳細とも、**表示は IndexedDB(Dexie) mirror の `useLiveQuery`** で行う。
RSC が fetch する `initialStatuses` / `initialCards` は **mirror 解決までの bootstrap のみ**
(`inline-card-list.tsx:76-80` `const cards = liveCards ?? initialCards`)。
→ mirror が更新されれば画面は自動で live 更新される。

mirror の更新は `runGuardedPull` (`lib/sync/pull.ts` → `/api/pull` で cursor 差分 pull)。
つまり「自動反映するか否か」=「OCR 完了を検知して `runGuardedPull` が走るか否か」。

### B-1. 「処理中バッジ」ポーラーの実体

`app/(app)/app/exams/_components/exam-status-live.tsx` (client, `ExamStatusProvider`):
- `/api/exams/status` を **5秒間隔**で poll (`POLL_INTERVAL_MS=5000`, `setInterval` :63)
- poll 対象は exam ごとの OCR status (`processing`|`failed`、完了は entry 消滅)
- **完了検知 (processing→消滅) で `runGuardedPull({reason:'ocr-complete'})`** (:33-38)
- processing が無ければ poll しない (failed のみは mount 時 1 回 reconcile)
- **このポーラーは試験一覧 page (`exams/page.tsx`) にのみマウント**。

### B-2. 試験一覧のデータ取得

`exams/page.tsx` (RSC) が `getExamStatusMap` を取り initial として渡すが、
list 表示は `ExamListLive` (client) が Dexie から `useLiveQuery`。
cache 戦略は Dexie local-first (server cache に依存しない)。

### B-3. 試験詳細のデータ取得

`exams/[id]/page.tsx` (RSC) が `getCardsForExam` を bootstrap として渡すが、
表示は `InlineCardList` が Dexie から `useLiveQuery` (:76-80)。
詳細 page にあるのは `ExamDetailPullGate` (`_components/exam-detail-pull-gate.tsx`):
- **mount 時に 1 回だけ** `runGuardedPull({reason:'exam-detail-mount'})` (:45)
- その直後 **`suppressAmbientPull()` で滞在中の ambient pull(mount/visibilitychange/online kick)を意図的に抑止** (:48)、unmount/examId 変化の cleanup で `resumeAmbientPull()` (:55)
- **polling はしない**。つまり詳細滞在中は「入口 1 回 pull のみ、以降は能動 pull を止める」設計。
- → B 実装で詳細にポーラーを足す場合、この suppress と整合させる必要あり
  (suppress は ambient kick 経路に効くが `runGuardedPull` 直呼びは bypass する設計 :12-14。新ポーラーも直呼びにすれば suppress と無干渉に共存可)。

### B-4. 根本原因 (エージェント初報の「RSC stale」説は誤り)

表示は mirror live query なので RSC initialCards の stale は実害なし。
`revalidatePath('/app/exams/[id]')` を足しても表示は live query を見るため効かない。
真の原因は **「OCR 完了を検知して pull するトリガーが、その画面に存在するか」**:

| シナリオ | pull トリガー | 結果 |
|---|---|---|
| 一覧を開いたまま OCR 完了 | ExamStatusLive poller (5s) → ocr-complete pull | 自動反映 ✓ |
| OCR 完了後に 一覧→詳細 へ遷移 | ExamDetailPullGate の mount pull | 反映 ✓ |
| **詳細を開いたまま OCR 完了** | **無し (詳細はポーラー無し、mount 時 1 回のみ)** | **反映されない ✗** |
| 別画面に居て OCR 完了 → 直接 詳細を開く | mount pull | 反映 ✓ |

→ 残る穴は「詳細ページ滞在中の OCR 完了」。これが B の対象であり、
pull-gate のコメントが言う「別 task」= 本 task。
(一覧も「一覧を開く前に完了 → その後一覧表示」は mount 時 reconcile で拾うため概ね OK。
ただし一覧側も完了検知は poll 経由なので最大 5 秒の遅延。)

### B-5. ポーリング相乗りの可否 / endpoint 構造

`/api/exams/status` レスポンス: `{ statuses: { [examId]: 'processing'|'failed' } }`
— OCR status のみ。新規 exam/card の中身は含まない。

新規 card の取り込み自体は **既存 `/api/pull` で完結**する (`runGuardedPull` が呼ぶ)。
よって status endpoint の拡張は不要。必要なのは「詳細ページでも完了を検知して
`runGuardedPull` を起こすトリガー」を足すこと。

`/api/pull` レスポンス:
`{ cards[], exams[], tombstones[], cursors:{cards,exams,tombstone} }` (cursor 差分)。

## 実装方針の選択肢 (推奨はしない、列挙のみ)

### (A) スリム化
- A-i: card 内 spacing のみ縮小 (`p-4→p-3`, card内 `space-y-3→space-y-2`)。波及最小。
- A-ii: list レベルも縮小 (list `space-y-3→space-y-2`, ul `space-y-2` 据置 or 縮小)。
- A-iii: option/field の `p-2` 据置 (tap target / layout-shift 制約のため触らない)。
  ※いずれも mobile (`md:` grid) には影響しない。

### (B) 自動反映
- B-i: 詳細ページにも status ポーラーを相乗り設置。`ExamStatusProvider`/`ExamStatusLive`
  相当 (5s poll → 完了検知 → `runGuardedPull`) を `exams/[id]` でも mount。
  処理中バッジを詳細にも出すなら自然。
- B-ii: 軽量版 — 詳細専用に「当該 exam の status だけ 5s poll し、完了で pull」する
  hook を `ExamDetailPullGate` に追加 (mount-once → conditional polling 化)。
  バッジ UI を増やさず最小改修。
- B-iii: poll を増やさず、`/api/pull` を一定間隔で叩く詳細専用 pull-loop にする
  (status endpoint を介さない)。ただし完了 signal が無いため常時 poll になりがち。
- 補足: いずれも server 側の revalidate 追加は不要 (表示は mirror live query)。

## 既存制約・依存
- mirror が source of truth。サーバ revalidate ではなく client pull が正攻法。
- `runGuardedPull` は guard 付き (多重 pull 抑制)。詳細に poll を足しても pull 関数は共通で安全。
- AI/OCR ルール: ポーリングは status endpoint (課金 API ではない) なので問題なし。
  ただし無限・高頻度 poll は CLAUDE.md 禁止 — 完了したら poll 停止する設計必須
  (既存 ExamStatusLive は processing 消滅で停止しており、これに倣う)。
- tap target / layout-shift 設計 (A-5) を壊さないこと。

# (B) 追加調査 — 問題理解の修正 (2026-06-01 追記)

当初の整理「詳細滞在中の OCR 完了が反映されない」は的外れだった。実際の問題は
**「OCR 開始 → すぐ一覧へ soft 移動 → 処理中の試験が一覧に行として出ない →
完了まで待っても出ない → リロードで初めて見える」**。以下、実コード根拠付きで再特定。

## BB-1. OCR 開始時の exam 行作成タイミング

`processUpload` (`upload/_actions/process.ts`) は**単一同期 Server Action**。
内部 `_processUpload` の **guard transaction (:252-374)** で:
- mode='new' のとき exam 行を INSERT (:332-336) — **OCR pipeline より前**
- source_documents を `status:'processing'` で INSERT (:354-366)
- この tx を commit してから OCR pipeline (`runOcrPipeline` :454) を実行

→ **exam の「容れ物」行は OCR 完了を待たず、処理開始直後に DB 確定している**。
ユーザー仮説の「数 poll 後には exam 行はある」は正しい。

完了時 (:530-546): cards bulk INSERT + `exams.card_count += N`。ただし
**`updatedAt: sql\`${exams.updatedAt}\`` で updated_at を凍結** (:542、一覧の
updatedAt DESC 順を乱さない意図)。→ **exam の updated_at は作成時刻 T0 のまま不変**。

補足: client (`upload-form.tsx` :433) は `await processUpload(fd)` で OCR 全長
ブロックする。一覧へ行けるのは **sidebar Link の soft navigation のみ**
(popstate/beforeunload guard は back/reload を止めるが Next Link soft nav は対象外、
:159 コメント)。

## BB-2. 新規 exam は一覧の mirror に入るか — 入らない

- 一覧の行表示は `ExamListLive` が **Dexie mirror (`db.exams`) を useLiveQuery 直読み**
  (`exam-list-live.tsx:27-49`)。RSC `getExamStatusMap` が供給するのは
  **バッジ status map だけで、一覧の行ソースではない**。
- mirror に exam が入る唯一経路は `runGuardedPull` → `pullDelta` → `/api/pull`
  (`getExamsDelta`, `updated_at >= since_exams`)。
- **`ExamStatusLive` poller (`/api/exams/status`) は mirror を一切書かない**。React
  context の status map (バッジ用) を更新するだけ。`runGuardedPull` を呼ぶのは
  **processing→completed の遷移時のみ** (`exam-status-live.tsx:80-84`)、かつ polling
  が稼働している場合だけ。
- **決定的事実**: `ExamStatusBadge` は ExamListLive が **mirror の各 exam 行を map した
  中**で描かれる (`:90-99`)。**mirror に行が無い処理中 exam は、行ごと出ない →
  バッジも出ない**。status map に entry があっても貼る先が無く無意味。

## BB-3. 「すぐ一覧へ soft 移動」時の bootstrap 挙動

- `PullTrigger` (mirror を埋める本体) は **/app layout に常駐** (`layout.tsx:53`)。
  layout 自身のコメント (:49-52):「**layout 持続中の内部 navigation では re-mount
  しないので重複発火しない**」。
- → upload→一覧 の soft navigation は同一 /app layout 内なので **PullTrigger は
  再発火しない** = 一覧到着時に新しい exams pull は走らない。
- 一覧 RSC は navigation ごとに再 render され `getExamStatusMap` も再実行されるが、
  それは**バッジ status map を更新するだけ**で mirror には触れない。
- PullTrigger が fire する契機は layout mount / visibilitychange→visible / online
  のみ。**soft route 遷移は契機に含まれない**。

## BB-4. ポーリングの開始タイミングと範囲

- ユーザーの言う「ポーリング」= `ExamStatusLive`。これは **一覧ページにのみマウント**。
  OCR 開始時には起動しない。**一覧ページ到着時**にマウントされ、しかも
  `initialSnapshot` (= 到着時の RSC `getExamStatusMap`) が **processing/failed を
  既に含む場合のみ** polling 開始 (`exam-status-live.tsx:52` 空なら return)。
- → 仮説「OCR 開始でポーリング既に開始」は**誤り**。どの画面でも回る poller は無い。
- mirror を埋める `PullTrigger` も「どの画面でも」ではなく layout mount 系契機のみ。

## BB-5. 真因の特定

「exam 行が開始時に作られていない」のではない (BB-1: 作られている)。
「RSC bootstrap timing」でもない (一覧の行は RSC ではなく mirror 由来)。

**真因 = 一覧の行が Dexie mirror 由来である一方、開始/soft 遷移のどの瞬間にも
新規 processing exam を mirror へ取り込む pull が発火しないこと。**
- `processUpload` は Server Action で client mirror を書けない。
- `upload-form` は開始時に pull しない。
- `PullTrigger` は soft 遷移で再発火しない (BB-3)。
- `ExamStatusLive` は status map を更新するだけで mirror を書かない (BB-2)。

結果、処理中は行ごと不可視。完了後に出るかは、`ExamStatusLive` の polling が
稼働していて完了遷移を捕まえ `ocr-complete` pull を撃てたか次第 (BB-4 の条件依存)。
リロードが効くのは hard load で **layout 再 mount → PullTrigger 発火 → delta pull**
が走り、mirror に exam (updated_at=T0 ≥ 保存 cursor) が入るため。

### 潜在リスク (副次、要注意)
exam の updated_at が T0 に凍結される (BB-1) ため、もし T0 以降に別 exam 更新で
exams cursor が T0 を追い越した後に delta pull すると、`updated_at >= since_exams`
で **この processing exam を取りこぼす**。本 flow では soft 遷移中に exams pull が
走らないので cursor は T0 を越えず、reload で拾える。だが将来 pull 契機を増やす
実装では「凍結 updated_at < cursor」での取りこぼしに注意。

## BB-6. 実装方針の選択肢 (列挙のみ、推奨なし)

- **方針1 — 開始時 mirror 取込**: `upload-form` の submit 直後に新規 exam を mirror に
  楽観 insert、または source_doc 行確定後に pull。Server Action が長時間ブロックする
  ため別 fire-and-forget が要りタイミングが繊細。
- **方針2 — 一覧到着で必ず pull**: 一覧マウント時に無条件 `runGuardedPull` を 1 回
  (PullTrigger とは別に、または PullTrigger を route 変化でも発火)。到着時に exam 行が
  既に DB にあれば即 mirror 反映。最小。「到着前に行が無かった」「他画面滞在」は未カバー。
- **方針3 — poller を mirror 同期に拡張**: `ExamStatusLive` が poll tick ごとに
  「status map に有るが mirror に無い exam」を検出したら `runGuardedPull` を撃つ +
  完了遷移でも撃つ (現状維持)。既存 poller への相乗りで「処理中の出現」と「完了反映」
  両方を mirror に反映。ただし poller 起動条件 (initialSnapshot 非空) は残る。
- **方針4 — 処理中検知を app 全体へ昇格**: layout に「processing>0 の間 poll し
  毎 tick `runGuardedPull`、0 で停止」する trigger を置く。ユーザー要望「どの画面に
  居ても開始 → 完了で勝手に一覧反映」に文言上もっとも忠実。変更は最大。
- 補足: いずれも server revalidate は不要 (一覧は mirror live query)。CLAUDE.md の
  無限/高頻度 poll 禁止に従い、processing が尽きたら必ず poll 停止 (既存
  `ExamStatusLive` の `nextProcessing.size===0 → stop` に倣う)。

## BB-7. 最小変更の所見 (要望: 「どの画面でも開始 → 完了で勝手に一覧追加」)

要望の literal な実現には **方針4 (app 全体の processing poll)** が最も忠実だが、
**既存資産の再利用で最小に寄せるなら方針3 + 方針2 の合わせ技**:
- 既存 `ExamStatusLive` の poll ループ (`/api/exams/status` 5s、processing 0 で停止、
  visibility 連動) は「いつまで poll するか」の制御として**ほぼそのまま使える**。
  不足は「mirror へ取り込む」だけ — tick の status 差分から
  「mirror 未所持の processing exam」or「完了遷移」を見て `runGuardedPull` を撃つ
  一文の追加で済む (status endpoint 拡張は不要、`/api/pull` が exam 差分を返す)。
- 「どの画面でも開始」を満たすには、この poll ループの起動を一覧ページ依存から
  剥がし layout 側へ寄せる必要がある (= 方針4 寄りになる)。一覧ページ内に留めるなら
  「OCR 開始した本人が結果を見るのは一覧 or result page」という UX 前提で
  方針2 (到着時 1 pull) + 方針3 (滞在中の完了反映) が現実的な最小。
- どこまで「どの画面でも」を満たすかは UX 判断 (OT 専権)。技術的には
  poll ループの設置場所 (一覧 page か layout か) が変更規模の分岐点。

# (B) 最終調査 — 1 本 poll で 2 フェーズ + 既存バッジ共存 (2026-06-01 追記)

設計目標: OCR ポーリングを「開始起点・画面非依存」に格上げし 1 本の poll で
フェーズ1 (exam 出現) → フェーズ2 (card 充填・完了で停止) を回し、既存バッジと共存。

## 軸1. OCR 完了の判定根拠 (フェーズ2 停止条件)

### C1-1. 完了判定とトランザクション順序 (process.ts)
`/api/exams/status` の status map は `source_documents.status` を畳んだもの
(`deriveExamStatuses`)。processing が map から消える契機 = **最新 source_document が
`completed` になること**。process.ts の commit 順序 (実コード):
1. guard tx (`:252-374`): exam INSERT + source_documents `status:'processing'` — **最初に commit**
2. OCR pipeline (`:454`)
3. **cards bulk INSERT + card_count 更新を 1 tx で commit** (`:530-546`)
4. **その後 別 tx で `source_documents.status='completed'` + upload_records commit** (`:588-608`)

→ **cards commit (手順3) は status='completed' (手順4) より前**。

### C1-2. 「card 全充填」と「completed」のタイミング保証 — 保証あり
status が completed に変わる時点で、cards は**直前の別 tx で既に commit 済**。
よって **completed 検知時点で cards は確実に pull 可能** (ラグは「completed の前に
cards が入る」方向のみで、欲しい順序と一致)。completed→cards のラグは存在しない。

### C1-3. 失敗時 (failed) の遷移と停止条件
`markFailed` (`:689-728`) が `status='failed'`。`deriveExamStatuses` は failed を
map に 'failed' で残す (completed のみ entry 消滅)。停止条件は既存の
`nextProcessing.size === 0` (`exam-status-live.tsx:88`) で、failed は
`processingIds` に入らないため **failed のみになれば poll 停止**。markFailed 自体が
失敗し processing 残骸化しても 15 分で `deriveExamStatuses` が failed 表示に倒す
(`source-doc-status.ts:79-82`) ので、poll は遅くとも 15 分で停止に向かう。
→ **停止条件: 「processing が map から消えた (completed) or failed 化」= 既存 logic で充足**。

## 軸2. poll の「開始起点・画面非依存」格上げと既存バッジ共存

### C2-1. 現状の結線と置き場所候補
現状: `ExamStatusProvider` は `exams/page.tsx:32` で render (一覧専属)。poll は
provider の useEffect 内。`ExamStatusBadge` は `ExamStatusContext` を購読し
`ExamListLive` 内 (provider 子孫) で描画。
画面非依存にする置き場所候補:
- (i) **/app layout に provider/poll を移設** (`PullTrigger` と同層 `layout.tsx`)。
  provider が全 /app ページの祖先になるため、どのページの `ExamStatusBadge` も購読可。
  poll は /app 内に居る限り画面跨ぎで継続。
- (ii) global client provider を layout で 1 個 mount (実質 (i) と同じ)。
制約: badge 購読側 (`ExamListLive` 等) が provider 子孫である必要 → layout 設置なら自動充足。

### C2-2. OCR 開始からの poll 起動配線
`processUpload` は**完了時に return する blocking Server Action** (`upload-form.tsx:433`
で await)。戻り値は完了後にしか来ないので**「開始」検知には使えない**。開始起点の
kick は client 側で submit 時に撃つしかない:
- `upload-form.tsx` の `handleSubmit` (`:497-504`) 時点で、layout 常駐 poller へ
  「poll 開始」signal を送る (context method / CustomEvent / BroadcastChannel /
  module-scope store のいずれか)。
- exam 行は submit 直後ではなくサーバ到達後の guard tx commit で出来るため、
  **単発 pull では取りこぼす** → **5s 間隔の繰り返し poll が race を吸収** (commit
  前の tick は空振り、commit 後の tick で拾う)。だから「単発 pull」ではなく
  「kick で poll ループ起動」が要る。

### C2-3. 既存 status context との共存
provider を layout へ移すだけなら **context API・`ExamStatusBadge` 購読側は無改修**。
seed 元が `exams/page.tsx` の RSC から layout RSC (または初期空 + 初回 poll 充填) に
変わる。後者なら badge は SSR 即時でなく初回 poll 後に出る (軽微)。badge 描画 logic は
不変。

### C2-4. poll ループ本体の流用可否 — そのまま流用可
既存ループ (5s `setInterval` / `nextProcessing.size===0` で恒久停止 /
visibilitychange 連動 start-stop / `inFlight` 二重起動防止、`exam-status-live.tsx:50-128`)
は**格上げ後もそのまま再利用できる**。変える/足すのは 2 点だけ:
- 起動契機: initialSnapshot 依存 (`:52` 空なら return) → kick でも起動できるよう拡張
- pull 発火: 現状「完了遷移時のみ」(`:80-84`) → **「processing がある tick でも
  runGuardedPull」を追加** (フェーズ1)。完了遷移の pull (フェーズ2) は現状維持。

### C2-5. 1 本の runGuardedPull で両フェーズ可能か — 可能
`runGuardedPull → pullDelta → /api/pull` は **cards / exams / tombstone を 1 レスポンス
で delta pull** (`pull.ts:120-144`, `route.ts:64-81`)。
- フェーズ1 (exam 出現) = exams delta、フェーズ2 (cards 充填) = cards delta。
- **同一 `runGuardedPull` 1 種で両方 mirror に入る**。別経路不要。
- card_count も cards mirror 集計なので cards delta で自動更新。

## 軸3. updated_at 凍結との整合

### C3-1. 取りこぼすか — 凍結のままで両フェーズとも拾える
schema: `exams.updatedAt` / `cards.updatedAt` とも `.defaultNow().$onUpdate(()=>new Date())`
(`schema.ts:234-237` / `:311-314`)。delta は両方 `gte(updated_at, since)` で **inclusive**
(`exams-pull.ts:35` / `cards-pull.ts:26`)。
- **フェーズ1**: exam は INSERT 時刻 T0 で updated_at=T0。exams cursor は過去 pull の
  max (= T0 より前) なので `T0 ≥ cursor` で**確実に拾う** (新規が最新なら gte inclusive)。
- **フェーズ2**: cards は完了時 INSERT で updated_at=Tc(>T0)。cards cursor < Tc なので
  **確実に拾う**。exam 自体は T0 凍結 (process.ts:542 が `$onUpdate` を明示抑止) だが、
  フェーズ1 pull 後 exams cursor=T0、フェーズ2 pull は `gte(T0)` inclusive で同 exam を
  無害に再取得 (or 既に mirror 在). **card_count は cards delta 由来なので exam 凍結に非依存**。

### C3-2. updated_at touch は必要か — 不要 (結論)
本目標 (exam 出現 + cards/件数 反映) は **exam.updated_at を touch せずに達成可能**。
touch が要るのは「完了で一覧の updated_at DESC 上位へ再 sort したい」場合だが、それは
process.ts:542 が**意図的に避けている挙動** (件数増減で並び順を乱さない)。
潜在 cursor 追い越しリスク (presurvey BB-5) は「T0 以降に別 exam 更新で exams cursor が
T0 を strict に超える」場合のみだが、(a) フェーズ1 で先に mirror 取込済なら後続 delta の
取りこぼしは upsert-only で無害、(b) gte inclusive で同時刻は拾える。よって
**touch 不要**。touch する場合の影響範囲: 一覧 updatedAt DESC 順が完了時刻に動く
(UX 変更) + process.ts:542 の意図に反する → 入れるなら別途 UX 合意が要る。

## 実装方針の選択肢 (列挙のみ、推奨なし)

- **方針P (page 据置・最小)**: provider/poll は一覧 page のまま。tick に
  「processing exam が mirror 未所持なら runGuardedPull」(フェーズ1) を 1 行追加。
  → 「一覧ページに居る間」だけ exam 出現 + 完了反映。画面非依存は満たさない。最小。
- **方針L (layout 格上げ・目標準拠)**: provider/poll を /app layout へ移設 + seed を
  layout RSC か初回 poll に + tick にフェーズ1 pull 追加 + 完了で停止 (現状維持)。
  → どのページに居ても OCR 中なら poll 継続。kick なしでも「OCR 中に /app に居れば
  初回 poll で processing 検知 → 以降継続」。
- **方針L+K (layout + 開始 kick)**: 方針L に upload submit 時の kick (CustomEvent /
  store) を足し、「OCR 開始した瞬間から」poll 起動を保証。race は 5s 繰返しで吸収。
  → 目標「開始起点・画面非依存」に最も忠実。変更最大 (layout / upload-form / provider)。
- 補足: いずれも server revalidate 不要、runGuardedPull 1 種で両フェーズ、
  updated_at touch 不要、停止条件は既存 logic 流用、バッジ描画は無改修。

## 最小変更の経路と分岐点
- **poll ループ・遷移検知・runGuardedPull・停止条件・バッジ context は全て既存資産で流用可**。
  純粋な新規実装は「**tick でのフェーズ1 pull の 1 行**」と「**起動契機の拡張**」のみ。
- **変更規模の分岐点 = poll の設置場所**:
  - 一覧 page のまま (方針P) → 数行。ただし「画面非依存」は得られない。
  - layout へ移設 (方針L / L+K) → provider 移設 + seed 経路 + (kick 配線) が増える。
    これが「開始起点・画面非依存」を満たす最小ライン。
- **kick の要否**が L と L+K の分岐: 「OCR 中に /app 内に居れば良い」なら kick 不要 (L)、
  「開始した瞬間から確実に」なら kick 要 (L+K)。どちらを取るかは UX 判断 (OT 専権)。

## updated_at touch の結論
**不要**。1 本の runGuardedPull (cards+exams delta, gte inclusive) でフェーズ1/2 とも
取りこぼさない。touch は一覧並び順を完了時刻に動かす UX 変更を伴い process.ts:542 の
意図に反するため、入れない方が整合する。

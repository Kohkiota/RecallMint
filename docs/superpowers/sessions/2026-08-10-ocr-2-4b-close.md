## 3. close 時点で **実証されていない**こと(取り繕わない)

- **§3 の失敗系 4 種は実機未観測**: DELETE 失敗 / 予算打ち切り / overdue 発火 / live-op skip。stg で自然発生させられなかったため。**unit test の pin のみ**(呼び出し順 pin・quota 境界・phase 優先順位・fail-safe の向き)
- **scheduler の実発火は未検証**(cron は production でのみ発火する)。prod 反映後に Vercel dashboard で確認する — kickoff で close 条件から除外済
- **lifecycle の「典型 24h 以内」は依然無保証**。得たのは 1 例の上下界のみで、常にこの範囲に収まる保証ではない。恒常監視は sweeper の overdue alert(72h・**listing 上限内の partial observation**)が担う
- **dead-man 監視は無い**: cron 停止 / `CRON_SECRET` 欠落 / route 障害は「alert 自体が実行されない」形で沈黙する。backstop = lifecycle + OT の随時手動 GET + prod 反映後チェックリスト。恒久監視は asset レーン整合 sprint で再訪(§3 spec §13)

## 4. §5 / §6 の結論(詳細は architecture.md §11)

- **§5 非要件(確定)**: ②-4b が保証するのは source object の**期限内削除**であり、削除後の個体履歴・元 filename・content identity の監査保存ではない。個体追跡を公開要件にするなら別 sprint で台帳を導入する。**公開前 gate で再判定**する項目
- **§6 2 レーン契約**: 共通不変条件 4 点 / レーン表(`src/` = 時間駆動・lifecycle backstop あり / asset = 行駆動・**lifecycle は張れない**)/ やってはいけない 2 つ(asset への lifecycle 追加・`src/` の行駆動化)/ 非対称の理由(記録がある側は遅延してよい)/ asset レーンの未解決 4 件

## 5. prod 反映の前提(OT・close 後)

1. **`CRON_SECRET` を Production scope にも登録**する。未登録だと production は 401 ではなく **gate throw → 500**(tier 差)。cron は production でのみ発火するため、未登録なら日次 run が毎日失敗し続ける
2. prod 反映後チェックリストに「Vercel dashboard の cron 実行履歴を随時確認」を追加(dead-man 監視の代替)
3. `pnpm run audit` の prod high(nanoid via postcss/next)は ②-4b 由来ではない(依存 diff 空)— 依存 sprint の OT 判断

# 開発プロセス Q&A(品質保証の仕組み)

`docs/app-overview.md` の補足。開発プロセスについて聞かれやすい質問への「そのまま話せる回答」+ 根拠の実測数字。
数字はすべて 2026-08-10 に実リポジトリを数えたもの(git log / find で再現可能)。

---

## Q1.「superpowers って何?」

**話す回答:**
> 「Claude Code(AI コーディングエージェント)の公式プラグインマーケットにあるオープンソースのプラグインで、実体は『手順書の集合』です。要件整理、実装計画、TDD、コードレビュー依頼、完了前検証……と作業の種類ごとに手順書(skill と呼ぶ)があって、AI は該当する手順書を読み込んでからでないと作業に入れない。つまり "AI の気分でやり方が変わる" のを手順書で固定するための仕組みです。」

**根拠・補足:**
- 例: 新機能なら brainstorming(要件確認)→ writing-plans(実装計画。**人間が承認するまで実装に入らない**)→ subagent-driven-development(タスクごとに真っさらな AI インスタンスが実装し、タスク間でレビュー)→ requesting-code-review(定型プロンプトのレビュー専任エージェント)→ verification-before-completion(「できました」と言う前に検証コマンドを**実際に実行して出力を見る**ことを強制)。
- skill は改変禁止で使う(レビュー用プロンプトのテンプレートを勝手に緩められない)。

## Q2.「どうやって動いてるの?強制力はあるの?」

**話す回答:**
> 「強制力は 2 層です。1 層目はプロンプト: セッション開始時に『該当する手順書を必ず起動せよ』という指示が自動で読み込まれる。2 層目は機械: hook というスクリプトが AI の終了時に走って、たとえば『レビュータグの無い feat/fix コミットがあると終了させない』を物理的にブロックします。さらにチェックを飛ばす `git commit --no-verify` は、書き方 6 通り全部を設定で拒否済みです。」

**根拠・補足:**
- Stop hook = `.claude/hooks/check-review.sh`(タグなし feat/fix を検出してブロック)。
- deny 設定 = `.claude/settings.json`。`--no-verify` / `-n` の全表記、さらに **`git push` / `curl` / `wget` / `ssh` も AI には拒否**(→ Q6 の核)。
- 「プロンプトだけなら AI が忘れるかも」への答え: だから最後の砦は必ず機械(hook・設定 deny・CI 的ゲート)に置いている。

## Q3.「この大量の docs は何?把握してるの?」

**話す回答:**
> 「docs は 971 ファイルありますが、役割がはっきり分かれています。人間が読む正本は少数 — ルール(CLAUDE.md)、設計の不変条件(architecture.md)、開発機構の説明(harness.md)、実装計画 13 本。これは読んで承認しています。残りの大半は AI の作業証跡です — 第二 AI レビューの原本が 454 件、作業ログが 222 件、失敗から作った再発防止ルールが 24 件。証跡は全部読む前提のものではなく、問題が起きたときに遡って検索するためのものです。『人が全行読む』の代わりに、機械ゲート+独立レビュー+人間の承認ポイントで品質を担保する設計にしています。」

**根拠(実測内訳):**

| 場所 | 件数 | 中身 | 人間が読む? |
|---|---|---|---|
| CLAUDE.md / docs/architecture.md / docs/harness.md | 3 | ルール・設計不変条件・機構(正本) | ◎ 読む |
| docs/plans/ | 13 | 実装前に承認した計画書 | ◎ 承認時に読む |
| docs/codex/ | 454 | 第二 AI(Codex)レビュー結果の原本 | △ 監査証跡 |
| docs/superpowers/sessions/ | 222 | 作業ログ(何をやり何を実測したか) | △ 遡及用 |
| docs/superpowers/lessons/ | 24 | 失敗の再発防止ルール | ○ 要点は把握 |
| docs/audit/ | 53 | テスト品質監査・依存脆弱性台帳 | ○ 結論は把握 |

- 正直ポイント: 「全部は読んでいません」と先に言い切ってよい。**読まなくても壊れない構造**(後述の 6 段防衛)が答えの本体。

## Q4.「TDD って具体的に何をどこまで保証してるの?」

**話す回答:**
> 「手順としては『失敗するテストを先に書き、実際に失敗するのを見てから、最小実装で通す』を skill が強制します。保証している範囲を正直に言うと: ①ドメインロジックの不変条件 — 復習アルゴリズムの再計算、課金の上限ガード、画像切り出しの座標計算、同期キューの結合規則など。②テナント分離 — 本物の PostgreSQL を立てて 2 ユーザーで相互に見えないことを毎スプリント検証。③API の契約。逆に保証していないのは、見た目、実機依存の挙動、外部 API の仕様変化 — そこはステージングでの実ブラウザ検証と人間確認で埋めます。テストが緑だから出荷、ではなく、テストは多段防衛の 1 段目という位置づけです。」

**根拠(実測):**
- テストファイル **309**(vitest)。うち実 PostgreSQL のテナント分離テスト **31** ファイル(`pnpm test:iso`。接続先を `127.0.0.1:5432/recallmint_test` 完全一致で強制し、誤って本番を叩けない作り)。契約テスト **14**。
- **さらに一歩踏み込んだ規律 = 「red 検証」**: テストを追加する変更では、そのテストが守る振る舞いを**わざと壊してテストが落ちることを実証**してからコミットする(「動くテスト」ではなく「検出するテスト」の証明)。コミットメッセージに記録が残り、現在 **57 コミット**。これはテスト自体の品質(検出力)への監査。
- 弱点も正直に: 既知の flaky テストが少数残っている(記録済み・対応方針あり)。

## Q5.「品質チェックは?『仕組みで壊れないようにしてる』って具体的に何?」

**話す回答(6 段の防衛ライン):**
> 「commit の前・push の前・本番の中、の 3 か所にゲートを置いています。具体的には 6 段です。」

1. **計画承認(人間)** — 実装前に計画書を人間が承認。承認前のコードは書かせない。
2. **実装中** — TDD + タスクごとに新しい AI インスタンスでレビュー(実装した本人 AI に自己採点させない)。
3. **commit 前 — AI 二重レビュー**: ① Claude の別インスタンスによる読み取り専用レビュー ② **別会社(OpenAI)の Codex による独立レビュー**。Codex には Claude の結論を見せず白紙で差分を見せる(引きずられ防止)。Critical / Important がゼロになるまで修正、上限 3 周で人間にエスカレーション。通った commit だけに `[reviewed]` タグ — **タグなしでは hook が終了をブロック**。
4. **スプリント完了ゲート(機械)**: lint 警告ゼロ / ユニットテスト / 実 PG テナント分離テスト / 依存脆弱性ゲート(high 以上は例外なく fail、受容には台帳記録必須)/ build + 本番でしか壊れない同梱問題の検証スクリプト。
5. **デプロイ境界(人間)**: AI は push 不可(→ Q6)。人間 push → ステージング反映 → **AI が実ブラウザで smoke 検証**(スクリーンショット・通信ログ・ブラウザ内 DB の中身を証拠として提出)→ 人間が本番反映を判断。**決済・認証・削除に触る修正は、人間の実機確認までレビュー完了扱いにしない**追加ルールあり。
6. **本番ランタイム**: 本番キーとテストキーの取り違えは起動時に即死 / RLS で他人のデータは DB 自体が遮断(事故っても被害半径は 1 ユーザー)/ webhook は署名検証+冪等 / AI 呼び出しは日次上限で暴走課金を遮断 / cron は秘密トークン必須・不備なら閉じる方向に倒す(fail-closed)。

**根拠(実測):** 全 1,639 コミット中 `[reviewed]` **636** / `[no-review]`(docs 等の意図的スキップ、タグ自体は必須)**1,017**。レビュー原本 454 件が repo に残存 = 「どのコミットが何のレビューを通ったか」を事後監査できる。

## Q6.「どう守られてるか分からないのに、本番デプロイできないよね」

**話す回答(これが本丸):**
> 「むしろ逆で、**AI は単独では本番に到達できない**ことが構造で保証されています。AI の実行環境は `git push` も `curl` も `ssh` も設定レベルで拒否していて、コードを外に出す手段がない。本番の鍵(Stripe live キーや本番環境変数)も AI には渡しておらず、本番切替は人間の手作業です。デプロイは必ず『人間が push → ステージングで AI が実ブラウザ検証+証拠提出 → 人間が確認して本番反映』の一方通行。つまり "AI を信用してデプロイ" ではなく、**機械ゲート・別会社の第二 AI・人間の 3 者を通過したものだけがデプロイされる**、という設計です。全コミットにレビュー経路のタグが付き、レビュー原本も 454 件残っているので、事後の監査も可能です。」

**ダメ押しの実例(聞かれたら):**
- 二重レビューは飾りではない: **片方の AI だけが見つけた欠陥が双方向に実在**する(Codex が Claude レビューの見逃しを拾った回も、その逆も、作業ログに記録あり)。
- レビューが 3 周で収束しなかったときに人間が裁定した実例もある(自動で押し切らない)。

## Q7.「hook が物理ブロックって、具体的にどこでどう実装されてるの?」

**話す回答:**
> 「hook は AI 本体の外側で動くただのスクリプトです。Claude Code という CLI が、AI が作業を終えようとするたびに `.claude/hooks/check-review.sh` を自動実行し、直近の feat/fix コミットにレビュータグが無ければ『終了拒否』を返して AI に差し戻す。判定するのは AI(モデル)ではなく CLI 側のプログラムなので、AI の判断では飛ばせません。抜け道になる `git commit --no-verify` も、AI のコマンド実行許可の層で 6 通りの書き方すべて拒否済みです。」

**実装の場所(聞かれたら見せられる):**
- 配線: `.claude/settings.json` の `hooks`(Stop イベント)に登録。AI がターンを終えるたびに CLI が実行。
- 中身: `check-review.sh` — 最後の feat/fix コミットに `[reviewed]` / `[no-review]` が無ければブロック判定を返す。さらに「テストだけ触ったコミット」には宣言トークン(red 検証 / 保証減 / 保証不変)が無いとブロック(テスト変更の分類を言語化させる規律)。
- コマンド拒否層: 同じ `settings.json` の deny リスト。`git push` / `curl` / `wget` / `ssh` / `--no-verify` 全表記は、**ツール呼び出しが実行される前に** CLI が拒否する。
- 補助: commit 時には lefthook(git の pre-commit)が ESLint を自動実行(`lefthook.yml`)。

**保証されること(機械で):**
- タグ無し feat/fix コミットのまま作業が終わる、は起こらない(形式の強制)。
- チェック飛ばしコミット・AI からの push は実行自体が不能。

**保証されないこと(正直に):**
- hook が見るのは**形式**。レビューの中身が十分だったか、宣言が正直かまでは機械は見ない。そこは ① レビュー原本 454 件が repo に残り事後照合できる ② 虚偽宣言は隠蔽として扱う明文ルール、の 2 つで担保。
- 設定や hook 自体を書き換えれば理屈上は無効化できる — ただしその変更自体が diff に現れてレビュー対象になるし、手動無効化はルールで禁止。「無効化が隠れて起こらない」ことまでが設計。

## Q8.「Codex レビューの組み込みって具体的にどう実装?それで何が保証されるの?」

**話す回答:**
> 「リポジトリ内のシェルスクリプト `scripts/ai/codex-review.sh` です。OpenAI の Codex CLI に『コミット前の差分』を白紙の状態でレビューさせ、結果を必ず `docs/codex/日付-トピック.md` に保存して、指摘を重大度別に数えます。Claude 側のレビュー結論は渡しません(引きずられ防止)。Critical と Important がゼロになるまで Claude が修正して再レビュー、上限 3 周で収束しなければ人間に上げます。合否はスクリプトの終了コードではなく、保存されたレポートの中身で判定します。」

**実装の詳細(場所つき):**
- 本体 `scripts/ai/codex-review.sh`: `codex exec review --uncommitted` を実行 → `docs/codex/` に md 保存 → `count-findings.sh` が `- [P0]` 形式の行だけを数えて集計(本文中に "P0" という単語が出ても誤カウントしない作り)。タイムアウト既定 600 秒。
- **「レビュー AI がこっそりコードを書き換えない」保証が二重**:
  1. 書き込み系のフラグ(apply 等)を一切渡さない
  2. `worktree-snapshot.sh` がレビュー前後の作業ツリーを**内容ベースで完全比較**(追跡ファイルの差分 + 未追跡ファイルの中身 + `.git/hooks` の中身まで)。1 バイトでも変わっていたら FAIL(exit 3)。pass 宣言の前に必ずこの照合を評価する。
- 語彙の統一: Codex の P0/P1 = Critical、P2 = Important、P3/P4 = Minor に写像し、Claude レビューと**同じ収束条件**(Critical 0 + Important 0)で扱う。
- 計画段階にも同種の仕組み(`codex-plan-review.sh`): 実装計画を確定する**前に**、調査結果と要件を主入力・計画ドラフトは添付扱いで渡し、独立に論点・抜けを挙げさせる(計画を承認させるのではなく、穴を探させる)。
- このスクリプト群自体にもユニットテストがある(同ディレクトリの `.test.ts`)。

**保証されること:**
- 独立性 — 別会社の AI が、こちらの結論を知らずに同じ差分を見る。
- 無害性 — レビューが作業ツリーを 1 バイトも変えていないことを照合で確認。
- 証跡 — 全実行がレポートとして残る(現在 454 件)。どのコミットが何を指摘され、どう収束したか遡れる。
- 停止性 — 収束しなければ自動で押し切らず、3 周で人間の裁定に上がる。

**保証されないこと(正直に):**
- 「Codex がすべての欠陥を見つける」ことは保証されない — どんなレビュアーでも同じ。だから二重レビュー+テスト+ステージング実ブラウザ検証の多段構成にしている。
- 見る範囲は「コミット前の差分」なので、すでにコミット済みの古いコードの問題は対象外 — そこはスプリント末の whole-repo ゲート(lint / テスト / 分離テスト / 脆弱性)が受け持つ。

## 先に自分から言うと信頼される「既知の弱点」リスト

指摘される前に自分から言えると強い:

1. 既知の flaky テストが少数残っている(記録・追跡済み)。
2. オフラインのコールドスタート(service worker)は意図的にスコープ外。
3. 画像の孤児 GC cron は実装中で未稼働(元ファイル掃除は稼働中)。
4. AI 二重レビューは人間レビューの完全代替ではない — だからこそ計画承認・push・本番反映という人間の関所を減らしていない。
5. RLS ポリシーの本番適用は運用者の手動作業(ドリフト検証スクリプトあり)。

## 一枚まとめ(口頭用)

```
書く前:  計画書を人間が承認
書く時:  TDD(red→green)+ タスク間レビュー
commit前: Claude レビュー + Codex(別会社)独立レビュー → タグ必須(hook が物理ブロック)
sprint末: lint 0 警告 / unit / 実PG分離テスト / 脆弱性ゲート / build+同梱検証
push:    人間のみ(AI は push・外部通信とも設定で拒否)
デプロイ: stg で AI が実ブラウザ検証+証拠 → 人間が本番判断
本番中:  キー取り違え即死 / RLS / webhook冪等 / AI日次上限 / cron fail-closed
```
